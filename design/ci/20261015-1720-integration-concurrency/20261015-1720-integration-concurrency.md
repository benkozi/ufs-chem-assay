# CI: `integration.yaml` pushes to develop queue instead of cancelling — the release bump push no longer kills the merge commit's run

Written 2026-10-15 after the merge of `feat: add baseline syncing utility` (#24, c0917de): its `simple-maccity` run on develop was cancelled by the python-semantic-release bump push (559e34f, 0.1.0-rc.5) about a minute later, and the bump's own run was skipped by design, so develop ended the release with no integration result at all. The fix aligns `integration.yaml`'s `concurrency` block with `ci.yaml`'s, which already settled the same question for the release job on 2026-10-06 (`design/feat/20261006-1250-psr-ci/20261006-1250-psr-ci.md`, Design section 3 and the last two conversational updates).

## Goal

Every merge to develop produces an end-to-end `simple-maccity` result, release or not. The push run must keep existing (it seeds the develop-scoped buildx and `build/` caches PR runs restore), and PR pushes must keep cancelling their own superseded runs.

## Pre-design audit

1. **The block as it was.** `integration.yaml` carried `concurrency: {group: integration-${{ github.ref }}, cancel-in-progress: true}` since the workflow was created (`design/feat/20260727-1633-simple-maccity-ci/20260727-1633-simple-maccity-ci.md`: "concurrency-cancelled per ref under its own group"). The cancel was chosen for PR pushes; a second push to develop within one run's lifetime was not considered because, before PSR, there was no such push.
2. **What PSR changed.** Since 2026-10-06 a merge that bumps the version is followed, roughly a minute later, by the release job pushing the bump commit to develop with the App token — a push that does trigger workflows (`design/feat/20261006-1250-psr-ci/...`, Design section 2). Both pushes land in the same `integration-refs/heads/develop` group.
3. **The skip that makes it total.** The `simple-maccity` job is gated on `!contains(github.event.head_commit.message, 'Automatically generated by python-semantic-release')` (same design, "`integration.yaml` `simple-maccity` gated on the marker") because a version bump changes nothing CECE-side. So the bump's run is skipped — correct on its own, but together with item 2 it means the cancelled merge run is never replaced.
4. **Evidence, from `gh run list --workflow=integration.yaml --branch develop`** (2026-10-15):

   | run | head | event | conclusion | title |
   | --- | --- | --- | --- | --- |
   | 38822586931 | c796045 | push | success | chore(ci): bump the actions group with 2 updates (#25) |
   | 38821620641 | 559e34f | push | skipped | 0.1.0-rc.5 |
   | 38821086911 | c0917de | push | cancelled | feat: add baseline syncing utility (#24) |
   | 38611387676 | 1e699cf | push | success | docs: add SI disclosure (#23) |
   | 37823994065 | 916f278 | push | skipped | 0.1.0-rc.4 |
   | 37823545612 | e55018b | push | cancelled | feat: remove concept of "examples" (#21) |
   | 37693199730 | 5236682 | push | skipped | 0.1.0-rc.3 |
   | 37692671449 | d2fac3e | push | cancelled | feat: add initial s3 integration (#20) |

   The pattern is exact: every merge that produced a release (`feat:`) was cancelled and its bump skipped; the merges that produced none (`docs:`, `chore(ci):`) completed. Since PSR went live no release-bearing merge has had an integration result.
5. **`ci.yaml` does not have the problem.** Its group is `ci-${{ github.ref }}` with `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` (settled 2026-10-06 so the in-flight release job could never be cancelled by its own bump push). For the same three commits its runs are 38821087037 (c0917de), 38821620876 (559e34f) and 38822586910 (c796045), all `success`: the bump push queued behind the merge run and ran after it.
6. **The cache seeding depends on the push run finishing.** The buildx `cache-to` and the `actions/cache` save for `cece/build` happen at the end of the push run; a cancelled run saves nothing under the develop scope, so PR runs after a release-bearing merge restored from the previous surviving develop run or rebuilt cold. The fix recovers that as a side effect.
7. **Docs.** Neither `design/design.md`'s "The integration job" bullet nor the README's "CI and releases" section describes the integration concurrency rule, so neither needs a change (user instruction: update them only if they describe it).

## Design

One expression changes:

```yaml
concurrency:
  group: integration-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

Behaviour by event:

- **`pull_request`**: unchanged. A new push to the PR head cancels the older run for that PR's `refs/pull/<n>/merge` ref.
- **`push` to develop**: the group still serialises runs on the ref, but a newer push now queues behind the in-progress one instead of cancelling it. The merge commit's run completes; the bump's run then starts and is skipped by the marker gate as before. Net: one real result per merge, one skipped run per release.

The header comment gains a sentence saying so, placed after the PSR-skip paragraph it depends on, because the skip is what turns the cancel from "noisy" into "no result".

Decisions:

- **Mirror `ci.yaml` rather than special-case the bump.** The alternative — keep `cancel-in-progress: true` and exclude PSR pushes from the group (for example `group: integration-${{ github.ref }}-${{ contains(github.event.head_commit.message, '...') }}`) — would also work but makes the group key depend on commit text and leaves the two workflows with different rules for the same ref. The `ci.yaml` rule is already documented, already reasoned about with the user, and is the behaviour wanted here too.
- **Queue, do not cancel, for any push to develop.** Two human merges in quick succession now run back to back instead of the second cancelling the first. That costs runner minutes (the job is about four minutes warm, up to the 60-minute budget cold) and gives a result for both commits; the second run's caches supersede the first's. The user wants the end-to-end result on every merge, so this is the intended trade.
- **The marker skip stays.** The bump commit still changes nothing CECE-side; running the suite for it would be a four-minute no-op.
- **Triggers, `continue-on-error`, the CECE pin and everything else stay as they are.**
