# Feature: ULID run identifier + run manifest

## Goal

Every test *run* (pytest session) gets a unique identifier so artifacts from
different runs can be told apart — in particular once stats CSVs from many
runs accumulate and get compared against baselines. The identifier is a
**ULID** (`python-ulid`): lexicographically sortable and
timestamp-encoding, so run ids order chronologically for free. The run's
resolved suite configuration is written to the output root as a **run
manifest** carrying the ULID.

## Design

### Generation and scope

- One ULID per pytest session, generated in `pytest_sessionstart` (alongside
  settings/suite loading) and stored on the pytest config; exposed to tests
  via a session-scoped `run_id` fixture (a 26-character ULID string).
- **Runtime-only**: the ULID is never read from configuration. `SuiteConfig`
  gains no such field, and unknown keys are rejected loudly rather than
  silently ignored (see strict base model below) — a `ulid:` in a suite
  file fails at load time.

### Strict base model for all config models

A shared base class enforces `extra="forbid"` across **both config model
families** — the suite config *and* the CECE driver config — so any unknown
key, at any nesting level, fails validation at load time instead of being
silently dropped (typo'd keys like `assertion:` or a misspelled stream field
included):

```python
# src/models/base.py
class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid")
```

- Every model in `models/cece_config.py` (`CeceConfig`, `Driver`, `Grid`,
  `Stream`, `SpeciesEntry`, `Output`, … — the full hierarchy) and
  `models/suite_config.py` (`SuiteConfig`, `Sweep`, `Assertions`,
  `Analysis`) switches its base from `BaseModel` to `StrictModel`, sharing
  the config in one place.
- The base is **not** frozen — `build_config()` mutates `CeceConfig`
  instances by design; strictness and immutability stay separate concerns.
- `RunManifest` inherits `StrictModel` too (plus its own `frozen=True`),
  keeping one convention for anything YAML-adjacent.
- Only checked-in / generated configs are parsed by these models, so
  forbidding extras carries no compatibility risk within the runner.
- Logged at test start, right after logging is configured:
  `starting run <ulid> (suite=<path>)` at INFO.

### Stats CSV inclusion

`VariableStats` gains a leading `run_id: str` column (first column, before
`combo`), populated by `compute_file_stats(..., run_id=...)` via the fixture.
Both the per-combo CSVs and the concatenated `descriptive_stats.csv` carry
it, so rows remain attributable when CSVs from multiple runs are later
combined or diffed against baselines.

### Run manifest

A new output-only pydantic model, written as YAML to the output root as soon
as the roots are realized (in the `combo_roots` fixture — early, so even a
run that dies mid-way leaves a manifest):

```python
class RunManifest(StrictModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    run_id: str            # the session ULID (its timestamp encodes start time)
    suite: SuiteConfig     # the resolved suite that ran (absolute config_path)
```

```
<output-root>/
  run.yaml                 # RunManifest: run_id + resolved suite config
  descriptive_stats.csv
  map-consd/...
```

The manifest records the suite *as resolved* (absolute `config_path`, all
defaults materialized), i.e. what actually ran rather than what the input
file said. It is output-only: nothing reads it back for control.

### Dependency

`python-ulid` added to the project dependencies.

## Ripples (standing process rules)

- **Harness tests**: `run_id` threading through `compute_file_stats` and the
  CSV writers (row helpers gain the field; column-order checks update via
  `model_fields`); a `RunManifest` serialization test (round-trips through
  YAML, `run_id` present); extra-key rejection tests for **both families** —
  a suite file with `ulid:` (top level) and a CECE config with an unknown
  key at a nested level (e.g. inside `driver:`) both fail validation.
  ULID-to-CSV threading is covered in `test_analysis` (a real ULID through
  `compute_file_stats` and both CSV layers) rather than the pipeline test,
  whose fabricated `.nc` files are empty stand-ins that xarray cannot open.
- **`design.md`**: artifact layout gains `run.yaml`; code layout gains
  `models/base.py`; dependency list gains `python-ulid`; the resolved
  decisions note that config models reject unknown keys via the shared
  strict base.
- **`README.md`**: results section gains `run.yaml` and the `run_id` CSV
  column.
- Pydantic models, never dataclasses.

## Non-goals

- No cross-run tooling (comparing/aggregating runs by id) — this feature
  only makes runs identifiable.
- No per-combo or per-test ids; the ULID identifies the session.

## Acceptance criteria

- `starting run <ulid> ...` appears once at session start; the same ULID is
  in every stats row (`run_id` column) of both CSV layers and in
  `<output-root>/run.yaml` alongside the resolved suite config.
- Two consecutive runs produce different, chronologically ordered ULIDs.
- A suite file containing an unknown key (e.g. `ulid:`) fails at load with a
  pydantic error; so does a CECE driver config with an unknown key at any
  nesting level.
- Harness passes without docker; integration keeps its expected shape
  (filename tests red per the known driver bug).
