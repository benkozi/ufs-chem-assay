# Feature: basic CI — containerized GitHub Actions + semantic-release

## Goal

Give the runner a first CI pipeline: a `Dockerfile` that packages the
complete toolchain (Python, uv, the locked dependency set, every
pre-commit tool), buildable locally with `docker buildx`, and a GitHub
Actions workflow that — on every pull request — builds that container
(cached), then runs pre-commit and the combo-test-runner harness tests
*inside* it. Releasing is a **manually dispatched** workflow that runs
python-semantic-release v10 against `develop` (release candidates)
and/or `main` (releases) — version-bump commit + git tag + changelog
only, pushed with the workflow's own token, with **no** GitHub Release
object, no PyPI upload, and no container pushed to any remote
registry.

## Pre-design audit (fresh facts, 2026-07-24)

Verified on `feat/initial-impl`.

1. **Nothing exists yet**: no `.github/`, no `Dockerfile`, no
   `.dockerignore`. `main` and `develop` both sit at the initial commit;
   all work lives on `feat/initial-impl`.
2. **Toolchain reality**: uv 0.10.7; the project venv runs Python
   3.14.3 (`requires-python = ">=3.11"`, no `.python-version` pin — the
   Dockerfile base image becomes the CI interpreter pin). `tool.uv
   package = false`: this is not a distributable package, so a release
   has no build artifacts by construction.
3. **`uv run ruff` is a silent PATH fallback** — ruff appears in
   neither `pyproject.toml` nor `uv.lock`; pre-commit's
   `language: system` hooks currently resolve `/opt/anaconda3/bin/ruff`
   0.12.0 (matching `.ruff_cache/0.12.0`). In any fresh container the
   ruff hooks fail. The image forces the fix: ruff must join the locked
   dev dependencies.
4. **python-semantic-release is absent** — not a dependency, no
   `[tool.semantic_release]` table. `project.version = "0.1.0"`; the
   repo has **zero tags**.
5. **The commit history is not conventional-commits** (subjects like
   `design/fix/20260724-1228-wrong-dimension-names.md`). PSR's default
   parser would compute *no* bump from any existing commit; version
   movement starts only with conventionally-formatted commits landing
   on `develop`/`main` after this feature.
6. **The CI test target is already hermetic**:
   `src/tests/combo_test_runner` is the docker-free harness suite
   (README: "runner harness only: fast, no docker"); tests that need
   `CECE_ROOT_DIR` set fake values into subprocess environments
   themselves (`test_root_dir_guards.py` uses tmp paths). No real CECE
   checkout, driver, or docker-in-docker is needed — "mocked (if
   necessary)" is already how the suite works, so CI sets no `CECE_*`
   variables at all.
7. **`.env` is machine-local and gitignored** — `Settings` reads a
   cwd-relative `.env`. The docker build context and the CI environment
   must never contain one (`.dockerignore` entry; CI checkouts won't
   have it anyway).
8. **pre-commit needs git and one isolated hook repo**
   (`pre-commit/pre-commit-hooks` v5.0.0 — a network fetch on first
   run); every other hook is `language: system` through `uv run`.
   Baking `pre-commit install-hooks` into the image removes the
   network dependency from CI runs.
9. **GitHub-hosted runners give every job a fresh VM.** A `localhost`
   registry is therefore *per-job*: it cannot literally carry an image
   between jobs. The real cross-job reuse mechanism is the buildx
   **GitHub Actions cache backend** (`type=gha`) — a later job's
   "build" is a full cache hit. The local registry's role is
   *intra*-job: the `docker-container` buildx driver holds images
   inside BuildKit, so the job pushes to a `registry:2` service on
   `localhost:5000` and `docker run`s from there (the documented
   buildx local-registry pattern, avoiding the slower `--load` tarball
   round-trip). The design says this plainly rather than pretending a
   registry persists across VMs.
10. **Official uv base images exist** (`ghcr.io/astral-sh/uv`), pinning
    uv + Python together, with the documented
    `--mount=type=cache,target=/root/.cache/uv` pattern for cached
    installs.
11. **The user's default buildx builder is Docker Build Cloud**
    (verified via `docker buildx ls`: `cloud-bkrlps-cece-builder*`,
    cloud driver, arm64 + amd64 nodes). Plain
    `docker buildx build --load …` therefore already builds on the
    cloud builder locally — no flags, no secrets, nothing special;
    `--load` pulls the result into the local daemon. Local dev is
    arm64, CI runners amd64; the cloud builder covers both natively,
    and CI's own builds stay on the hosted runner with the gha cache.
12. **Conventional-commit enforcement at commit time is a solved
    pre-commit shape**: hooks declared for the `commit-msg` stage run
    against the message of the commit *being created* (git passes the
    in-progress message file; failure aborts that very commit) —
    answering the "can that happen on the commit it is currently
    trying to check" question with yes. It needs the `commit-msg` hook
    type installed; `default_install_hook_types` in
    `.pre-commit-config.yaml` makes the existing plain
    `pre-commit install` do that. `pre-commit run --all-files` (CI)
    never runs commit-msg hooks — there is no message — so CI-side
    enforcement rides on the PR title instead, which is what a squash
    merge turns into the commit subject PSR eventually parses. The
    standard hook is `compilerla/conventional-pre-commit` — an
    isolated-env hook with zero project-dependency coupling, i.e. the
    same exception category the config already carves out for
    `pre-commit/pre-commit-hooks`, and its checker can be invoked
    manually (`pre-commit run conventional-pre-commit --hook-stage
    commit-msg --commit-msg-filename <file>`) against any text — the
    reuse the PR-title check builds on.
13. **Reference implementation for the release job**: the user's
    CATChem repo (`CATChem/.github/workflows/semantic-release.yml`) —
    a reusable (`workflow_call`) workflow exposing
    `new_release_version` / `new_release_published` / `is_prerelease`
    outputs, whose release job is: mint a GitHub App token → checkout
    with `fetch-depth: 0` and `persist-credentials: true` → the
    official `python-semantic-release/python-semantic-release@v10`
    action with that token. The action is a Docker action: it runs PSR
    v10 in *its own* container, reading `[tool.semantic_release]` from
    the repo's `pyproject.toml`, handling git identity, and exposing
    `version`/`released`/`tag`/`is_prerelease` outputs. The App token
    exists to bypass branch protection; the user has said to assume
    the plain GitHub token has all needed access, so that step drops
    out here. `id-token: write` in CATChem serves PyPI trusted
    publishing — nothing here publishes, so it drops out too.

## Design

Four phases. Infrastructure files (Dockerfile, workflow) have no unit
seam, so red-green here means: run the exact container commands locally
and watch them fail before the fix and pass after; the workflow itself
is verified by the first PR that carries it. Repo-code changes
(pyproject) stay under the normal test suite.

### Phase 1 — repo groundwork (make the toolchain hermetic)

- Add `ruff>=0.12,<0.13` to the `dev` dependency group (the formatting
  family the repo is already formatted with — closes audit item 3;
  `uv run ruff` then resolves from the venv on every machine and in
  the image).
- python-semantic-release is **not** added as a dependency (user
  direction): the GHA action is its only runner, so locking it would
  put an unused tool tree in every dev env and the image. Local
  `--noop` previews use an ephemeral
  `uv tool run --from 'python-semantic-release>=10,<11'
  semantic-release --noop version`, keeping the same major pin as the
  `@v10` action without touching the lock.
- Conventional-commit gate at commit time (audit item 12):
  `compilerla/conventional-pre-commit` at the `commit-msg` stage, plus
  `default_install_hook_types: [pre-commit, commit-msg]` so the
  README's existing `uv run pre-commit install` line keeps working
  unchanged. A non-conventional message aborts the commit being made.
- `[tool.semantic_release]` in `pyproject.toml` — the user's preferred
  block from another PSR implementation, adopted with a v10
  translation (two of its keys are v7-era and no longer exist:
  `upload_to_pypi` and `vcs_release`; their intent — publish nothing —
  is preserved by having no build/publish step at all, the release
  action input `vcs_release: false`, and locally the
  `--no-vcs-release` flag):

  ```toml
  [tool.semantic_release]
  version_toml = [
      "pyproject.toml:project.version",
  ]
  version_variables = []
  build_command = ""
  allow_zero_version = true
  commit_message = "{version}\n\nAutomatically generated by python-semantic-release [ci skip]"

  [tool.semantic_release.changelog]
  exclude_commit_patterns = [".*\\n\\nAutomatically\\ generated\\ by\\ python\\-semantic\\-release\\ \\[ci\\ skip\\]$"]

  [tool.semantic_release.branches.main]
  match = "(^main$)"
  prerelease = false

  [tool.semantic_release.branches.develop]
  match = "(^develop$)"
  prerelease = true
  ```

  Notes: the develop prerelease token defaults to `rc`, giving the
  required `X.Y.Z-rc.N` without extra config; the `[ci skip]` in the
  bump-commit message means GitHub Actions skips workflows on that
  commit (no CI self-trigger loop), and `exclude_commit_patterns`
  keeps those bump commits out of the changelog; the changelog itself
  is PSR's default `CHANGELOG.md` rendering (user decision — kept).
- `.dockerignore`: `.env`, `.git`, `.venv`, caches, `design/`,
  test output roots — the build context needs only
  `pyproject.toml`, `uv.lock`, and `.pre-commit-config.yaml` (source is
  bind-mounted at run time, never baked).
- `uv lock` refresh; full local test pass.

### Phase 2 — Dockerfile

- `FROM ghcr.io/astral-sh/uv:python3.14-bookworm-slim` — pins Python to
  what the project already develops against (3.14) and uv alongside it.
- `apt-get install git` (pre-commit and semantic-release both need it).
- `WORKDIR /app`; copy `pyproject.toml` + `uv.lock`; set
  `UV_PROJECT_ENVIRONMENT=/opt/venv` so the baked venv lives outside
  any bind mount; `RUN --mount=type=cache,target=/root/.cache/uv uv
  sync --frozen` (dev group included by default) — the uv cache mount
  is the "cache the uv installation" half; the sync that CI re-runs
  (below) is the "always install" half.
- Copy `.pre-commit-config.yaml`; set `PRE_COMMIT_HOME=/opt/pre-commit`
  and `RUN git init . && uv run pre-commit install-hooks` to bake the
  isolated hook environments (audit item 8 — now two of them:
  `pre-commit-hooks` and `conventional-pre-commit`) — no network at
  job time.
- Local build for testing:
  `docker buildx build --load -t combo-test-runner:dev .`
  On the user's machine this already runs on Docker Build Cloud —
  their selected default builder (audit item 11) — with `--load`
  pulling the image back into the local daemon; nothing special in
  the command. CI uses the hosted runner's buildx with the gha cache.
- Container contract (what CI and local testing both run, from the
  repo bind-mounted at `/repo`):

  ```sh
  docker run --rm -v "$PWD":/repo -w /repo combo-test-runner:dev \
    sh -c 'git config --global --add safe.directory /repo \
           && uv sync --frozen \
           && uv run pre-commit run --all-files'
  # and, separately:
  #        ... && uv run pytest src/tests/combo_test_runner
  ```

  `uv sync --frozen` at run time is deliberate and cheap: if the PR's
  lockfile drifted from the cached image layers, the venv catches up
  in seconds; otherwise it's a no-op ("always install in case things
  get out of date"). `safe.directory` handles the uid mismatch on the
  mounted checkout.

### Phase 3 — workflow `.github/workflows/ci.yaml`

- **Triggers**: `pull_request` (all PRs, any base), and `push` to
  `develop` and `main`. A concurrency group cancels superseded PR runs.
- **Job `build`** — `docker/setup-buildx-action` (docker-container
  driver), `docker/build-push-action` with
  `cache-from: type=gha` / `cache-to: type=gha,mode=max`, `push:
  false`. Its sole product is a warm build cache; nothing leaves the
  runner.
- **Jobs `pre-commit` and `tests`** (`needs: build`, parallel) — each:
  - `registry:2` **service container** on `localhost:5000`;
  - `setup-buildx-action` with `driver-opts: network=host` (so BuildKit
    can reach the service);
  - `build-push-action` with the same gha `cache-from` (full cache hit
    — this is the "re-used between jobs"), `push: true`,
    `tags: localhost:5000/combo-test-runner:ci`;
  - `docker run` of the Phase-2 container contract: pre-commit in one
    job, `uv run pytest src/tests/combo_test_runner` in the other. No
    `CECE_*` environment, no `.env` (audit items 6–7).
- **PR-title conventional-commit check** — an extra step in the
  `pre-commit` job, `pull_request` events only, reusing the *same*
  baked hook so the grammar has exactly one definition: write the
  title to a file and run
  `uv run pre-commit run conventional-pre-commit --hook-stage
  commit-msg --commit-msg-filename <file>` inside the container. The
  title reaches the shell **only via an environment variable**
  (step-level `env: PR_TITLE: ${{ github.event.pull_request.title }}`,
  then `printf '%s\n' "$PR_TITLE"` — never interpolated into the
  script text; PR titles are attacker-controlled and inline `${{ }}`
  expansion is the classic GHA injection). This is what makes
  squash-merge subjects — hence PSR's input — conventional even when
  a contributor's local hooks weren't installed.
- **Release: a separate, manual-only workflow**
  `.github/workflows/semantic-release.yml` — `on: workflow_dispatch`,
  not part of `ci.yaml` and triggered by no event (user direction:
  releases happen only when the operator runs them). The GitHub "Run
  workflow" branch picker *is* the develop-vs-main selector: the run
  executes against the chosen ref, and a first guard step fails fast
  unless `github.ref_name` is `develop` or `main` (PSR's branch
  regexes would also refuse other branches; the guard just says so
  clearly). Releasing both branches = two dispatches, one per branch.
  The job body mirrors the user's CATChem reference (audit item 13)
  minus its automation trappings:
  - checkout of the dispatched ref with `fetch-depth: 0` and
    `persist-credentials: true`, then
    `python-semantic-release/python-semantic-release@v10` with
    `github_token: ${{ github.token }}` and `vcs_release: false` (the
    input equivalent of `--no-vcs-release`: no GitHub Release object,
    and there is no publish step of any kind);
  - **push access**: workflow-level `permissions: contents: write` is
    what lets the action push the bump commit, tag, and
    `CHANGELOG.md` update back to the dispatched branch (user: assume
    the token has all needed access; CATChem's GitHub App token is
    the recorded upgrade path if branch protection ever blocks it),
    with CATChem's `id-token: write` dropped — that serves PyPI
    trusted publishing, and nothing here publishes;
  - no `workflow_call`/outputs plumbing — nothing consumes them in a
    manual flow (trivial to re-add if a caller ever appears).
  On `develop` the branch config yields `X.Y.Z-rc.N` prereleases; on
  `main`, full releases; the release *is* the version-bump commit +
  tag + changelog the action pushes. This workflow is the one
  deliberate exception to "run everything in the built container":
  the action runs PSR v10 in *its own* container (still
  containerized, just not ours) and reads the same
  `[tool.semantic_release]` config from `pyproject.toml`, so behavior
  is identical to a local ephemeral run of the same `>=10,<11` family
  (`uv tool run`, above) — PSR is not in the lock. The `[ci skip]`
  bump-commit message is belt-and-suspenders: pushes made with the
  default `github.token` don't trigger new workflow runs anyway, and
  `[ci skip]` keeps that true even if the token is later upgraded to
  an App token or PAT.
- Reading of the requirements this encodes: "runs on all pull
  requests" governs build + pre-commit + tests; `ci.yaml` keeps its
  `push` triggers on `develop`/`main` purely as post-merge validation
  of the merged state. Releases are decoupled from both: no CI event
  runs PSR, and the manual dispatch does not `needs:`-gate on CI jobs
  (it runs against whatever the branch tip is) — the operator's
  contract is to dispatch only on a green branch.

### Phase 4 — documentation

- README: new CI section — what runs on PRs, the container contract
  (so contributors can run exactly what CI runs, locally, with the
  buildx command above), the release flow, and the new **conventional
  commits** requirement (audit item 5: without it, PSR never bumps),
  now *enforced* rather than merely documented: the commit-msg hook
  rejects non-conventional messages at commit time (the existing
  `uv run pre-commit install` setup line stays valid via
  `default_install_hook_types`) and CI rejects non-conventional PR
  titles.
- `design/design.md`: CI/release subsection recording the same, plus
  the local-registry/gha-cache mechanics for future maintenance.

### Out of scope (deliberately)

- Publishing anything: no GHCR/registry image pushes, no GitHub
  Release objects, no PyPI, no changelog-file publication beyond what
  PSR commits.
- Driver integration in CI (`simple-maccity` needs the CECE checkout,
  the `cece/cece-dev` image, and a built driver — none of which CI
  has). CI runs the harness suite only, per requirements.
- Branch-protection / required-check configuration (repo settings, not
  files).
- Docker Build Cloud wiring (needs org endpoint + token secrets; the
  workflow and local command are already builder-agnostic — see open
  questions).

## Constraints

- pydantic models with `Field(description=...)` and no `Any` — n/a to
  this feature's files (no runtime Python changes), binding if any
  appear.
- Never commit — the user commits. (CI's semantic-release commits are
  the machine's own, out of that rule's scope, but flagged here since
  PSR *does* push commits and tags to `develop`/`main`.)
- README.md and `design/design.md` updated as part of implementation.
- No publishing of any kind (images, GitHub Releases, PyPI).

## Acceptance criteria

1. `docker buildx build` produces an image containing Python 3.14, uv,
   the frozen dependency set including ruff and
   python-semantic-release v10, and pre-baked pre-commit hook
   environments; `.env` can never enter the image.
2. Every PR triggers the workflow: container built with gha-cache
   reuse, then pre-commit `--all-files` and
   `pytest src/tests/combo_test_runner` both run *inside* the
   container pulled from the job-local `localhost:5000` registry — all
   with no `CECE_*` environment and no image pushed off-runner.
3. Later jobs' builds are cache hits (reuse between jobs via the gha
   backend; the per-job local registry serves the image to `docker
   run`).
4. `uv sync --frozen` executes on every CI job despite the baked venv
   (cache + always-install, both requirements met).
5. Releases happen **only** on manual dispatch of
   `semantic-release.yml`: no push, PR, or other event runs PSR.
   Dispatched against `develop` with conventional commits present →
   the official PSR action (plain `github.token` with
   `contents: write` push access, `vcs_release: false`) pushes a
   `X.Y.Z-rc.N` bump commit + tag + changelog update to `develop`
   (bump message carrying `[ci skip]`, so it triggers no workflow and
   appears in no changelog); dispatched against `main` → full release
   bump + tag; dispatched against any other branch → the guard fails
   the run. The changelog is PSR's default `CHANGELOG.md`; no GitHub
   Release object and no PyPI interaction exists anywhere.
6. A non-conventional commit message aborts the commit it belongs to
   (commit-msg stage, installed by the plain `pre-commit install`);
   a non-conventional PR title fails the PR's `pre-commit` job via
   the same baked hook, with the title passed injection-safely
   through an environment variable.
7. README and `design/design.md` document the CI contract, the local
   reproduction command, and the conventional-commits requirement
   (local hook + PR-title enforcement).
