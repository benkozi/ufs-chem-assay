# Feature: run the harness on RDHPC (Ursa first), without docker

Refines https://github.com/benkozi/ufs-chem-assay/issues/5.

## Goal

Run the full harness pipeline — driver execution across a suite's
combinations, per-combo assertions, stats, plots, baseline comparison —
on **Ursa** (NOAA RDHPCS), where docker does not exist, the driver is
built natively against the machine's spack-stack modules, MPI is blocked
on login nodes, and heavy work must go through Slurm. Locally nothing
changes: the docker path stays the default and byte-identical.

Three deliverables, in dependency order:

1. **A native execution runtime in the harness.** The driver (and the
   examples entrypoint) can be launched as a plain host process, with an
   optional launcher prefix (`srun …`), selected by a `platform` /
   `runtime` setting. Platform is detected and overridable; the default
   is `local`, which keeps docker.
2. **A higher-level entrypoint** — `ufs-chem-assay run --config-file=X`
   — that assembles a whole run from one YAML file: clone/update CECE,
   load the CECE modulefile and build the driver, stage data, run the
   CECE unit tests, run the harness — directly on a laptop, or as one
   Slurm batch job on Ursa. It generates reviewable shell scripts and
   supports `--dry-run`.
3. **A manual runbook for Ursa** (below) that the user can follow today,
   before or independently of (2), and that (2) automates step for step.

Out of scope (deliberately): Gaea-C6 and cloud platforms beyond leaving
an enum slot; Apptainer/Singularity execution (available on Ursa, but
the native path is what the issue asks for and what the CECE
modulefiles are built for); publishing baselines; any CATChem work.

## Pre-design audit (fresh facts, 2026-09-03)

Verified on `feat/run-on-rdhpc` at `b29b5ef`, the local CECE checkout
(`fix/all-examples-pass` at `b28ba69`), the RDHPCS docs, and the
`test-kokkos/build-test-kokkos.sh` reference script.

1. **Docker is assumed in exactly three places, all host-side and
   already isolated**: `runner.build_command` (`docker run … -v
   root:/work -w /work … <image> ./build/cece_standalone_driver
   <yaml>`), `examples.run_example_command` (same wrapping around
   `python3 examples/run-example.py`), and the path model —
   `resolution.resolve_output_roots` maps `--combo-output-root` to a
   `(host, /work-relative container)` pair, `ComboRoots` carries
   `host`/`container`/`needs_mount`, and `generated_combos` writes the
   *container* directory into each generated config (`output.directory`,
   `driver.log_file`). The `/combo_runs` second mount exists only for
   the pytest-tmp default root. Everything else (enumeration, stats,
   plots, comparison, report, run.yaml) reads host paths.
2. **The driver already runs natively in CECE's own tooling.**
   `examples/common.py::run_example` executes
   `<repo>/build/cece_standalone_driver <config relative to repo>` with
   `cwd=<repo root>` and no docker ("runs unchanged inside the dev
   container or natively, e.g. on HPC"), overriding the driver location
   via `CECE_EXAMPLES_DRIVER_PATH`. It sets
   `OMPI_ALLOW_RUN_AS_ROOT*` unconditionally ("harmless natively").
3. **Relative data paths resolve against the driver's cwd.** The shipped
   `cece_config_ex3.yaml` uses `file: "data/MACCity_4x5.nc"` and runs
   green in CI with cwd `/work`. The harness's own base config
   `src/tests/config/cece/simple-maccity.yaml` instead hard-codes the
   container path `file: /work/data/MACCity_4x5.nc` — the **one
   `/work` literal that reaches the driver** and would break natively.
   Since the docker command sets `-w /work` and the native runner will
   set `cwd=root_dir`, `data/MACCity_4x5.nc` is correct in both modes.
4. **CECE carries Ursa modulefiles**: `modulefiles/cece_ursa.gnu.lua`,
   `cece_ursa.intel.lua`, `cece_ursa.intelllvm.lua`, all on
   `/contrib/spack-stack/spack-stack-1.9.2/envs/ue-oneapi-2024.2.1`
   (or `ue-gcc-12.4.0`) plus `cece_common.lua` (hdf5, netcdf-c/-fortran,
   parallelio, esmf 8.8.0) and `nccmp`. `intelllvm` sets
   `CC=mpiicx CXX=mpiicpx FC=mpiifx`; `intel` sets `FC=mpiifort`
   (classic ifort — present in oneAPI 2024.2, gone in 2025). CECE's
   CMake finds MPI (`find_package(MPI REQUIRED)`), netCDF (config mode,
   then `NETCDF_C_ROOT`-style env vars that spack-stack modules set),
   optional Fortran, and **FetchContents kokkos 5.1.1, yaml-cpp,
   googletest, rapidcheck at configure time** — configure needs network,
   i.e. a login node (the kokkos script's 2026-08-25 compute-node
   configure died cloning googletest exactly this way).
5. **Ursa facts (docs.rdhpcs.noaa.gov, 2026-09-03)**: login nodes
   `ufe01-04` are for "editing and compiling code", job submission and
   monitoring — not computation, no MPI; partitions `u1-compute`
   (default) and `u1-service` (serial ≤64 cores/250 GB, 24 h); QOS
   `batch` (8 h, default), `debug` (30 min, highest priority),
   `windfall`, `urgent`, `long`; `sbatch`/`salloc`/`srun` require
   `-A <account>` and `-n`/`-N`; node sharing is on by default.
   Filesystems: `/scratch3`, `/scratch4` (Lustre, shared with Hera,
   project quotas, not backed up), `/scratch5` (VAST; `/purged` has a
   90-day purge). Python: `module load rdhpcs-python` /
   `rdhpcs-conda`; Anaconda channels prohibited, conda-forge only;
   environments belong in *project* space, not `$HOME` (quota).
   Containers: **Apptainer only — "Docker and Podman are not available
   on RDHPCS systems."** The docs say nothing about outbound network
   from compute nodes; the kokkos script's README records the
   constraint as fact ("compute nodes are network-restricted") and its
   Ursa runs (`misc.md`) confirm login-node `git clone` over SSH and
   FetchContent over HTTPS work.
6. **The reference script** (`build-test-kokkos.sh`) already encodes
   the operational pattern to copy: a per-platform config block
   (root dir, clone dir/url/branch, modulefile, `module purge`,
   toolchain probes, an `srun --account=epic --nodes=1 --ntasks=1
   --cpus-per-task=8 --time=…` test launcher), `--dry-run` that prints
   every command, clone-if-missing / `--update-source` fast-forward-only
   source handling, a never-delete root-dir precondition, timestamped
   tee'd logs under `<root>/logs/`, configure-log greps as
   pass/fail gates, tests under `srun` because "MPI is blocked on Ursa
   login nodes". It is bash; the requirement is the same behaviour in
   Python inside the uv environment.
7. **uv on Ursa**: the standalone installer
   (`curl -LsSf https://astral.sh/uv/install.sh | sh`) needs no root
   and no conda, installs to `~/.local/bin`, and `uv python install`
   fetches python-build-standalone — both network operations, both
   login-node work. The lock (`uv.lock`, `requires-python >=3.11`) has
   manylinux wheels for every dependency on CPython 3.11–3.13
   (cartopy 0.25.0: `cp311/cp312/cp313 manylinux_2_28_x86_64`); on
   **3.14 cartopy builds from source** (why the CI image installs
   `g++`). No `.python-version` is checked in; the repo's own venv and
   the Dockerfile are 3.14. On Ursa the interpreter is therefore pinned
   to 3.13 via `UV_PYTHON` in the generated environment, not in the
   tree. `uv sync --frozen` then needs network once; runs on compute
   nodes use `uv run --no-sync` (or the venv's `pytest` directly) with
   `UV_OFFLINE=1`.
8. **Session-level compute on the harness side**: `dask_client` starts
   a `LocalCluster` sized to all cores unless `CECE_DASK_NWORKERS` is
   set — on a shared compute node it must match the allocation
   (`SLURM_CPUS_PER_TASK`). Cartopy's first coastline render downloads
   Natural Earth data; offline the plots "degrade to data-only maps
   with a warning" (design.md) — acceptable on a compute node, or
   pre-warmed on the login node.
9. **Baselines**: `simple-maccity-suite.yaml` names three ULIDs under
   `CECE_BASELINE_ROOT_DIR`; the store has no public source, CI runs
   with `CECE_ENABLE_BASELINE_COMPARISONS=false`, and the stored
   baselines predate the merged driver's CF-1.9 output (they fail
   locally too — `design/feat/20260901-1701-rename-repo.md`,
   implementation notes). Ursa starts with comparisons off and a
   configurable root, exactly like CI.
10. **CECE unit tests** (issue item 4): `ctest --test-dir build` after
    building the `all` target; gtest discovery sets
    `FI_PROVIDER=tcp;I_MPI_FABRICS=shm` per test — the single-node MPI
    hints the native driver launch should carry too. The integration
    workflow builds only `cece_standalone_driver` (`--target`) because
    the test stack is expensive; the run config makes that a choice.
11. **Packaging**: `tool.uv package = false` ("there is nothing to
    build"), no `[build-system]`, flat modules under `src/` imported
    via `pythonpath = ["src"]`. A `[project.scripts]` console script
    requires an installable project; the Dockerfile copies only
    `pyproject.toml`/`uv.lock` and runs `uv sync --frozen`, which with a
    package would try to build from an absent tree — it needs
    `--no-install-project` there (CI's in-repo `uv sync --frozen`
    installs it editable). `test_dry_run.py` and the CI steps invoke
    pytest by path and are unaffected.
12. **design.md non-goal #1** says "No standalone CLI — pytest's
    command line is the only entry point." The requirement overrides it
    for orchestration only: pytest remains the *test* entry point, the
    CLI composes environment + pytest invocation and never re-implements
    test logic. Harness suite today: 217 tests.

## Design

### 1. Platform, runtime, launcher (settings)

Three new `Settings` fields (`CECE_*` environment, `.env`, or the
run-config file through the generated environment):

| setting                | env var          | values / default                                              |
|------------------------|------------------|---------------------------------------------------------------|
| `platform`             | `CECE_PLATFORM`  | `Platform` enum: `local` (default), `ursa`; detected when unset |
| `runtime`              | `CECE_RUNTIME`   | `Runtime` enum: `docker`, `native`; default derives from platform (`local`→`docker`, everything else→`native`) |
| `launcher`             | `CECE_LAUNCHER`  | string, word-split (`shlex`) command prefix for native driver runs; default `""`; Ursa run config sets `srun --ntasks=1` |

- `src/platforms.py`: `Platform(StrEnum)` and `detect_platform() ->
  Platform` — `socket.gethostname()` fullmatched against a per-platform
  regex table; no match → `LOCAL`. The Ursa pattern is a **first-run
  verification item** (record `hostname` on a login and a compute node;
  until then the pattern is the login-node form `ufe\d+.*` and the run
  config sets `platform: ursa` explicitly, which is the documented
  override — detection is a convenience, never load-bearing).
  `Runtime(StrEnum)` lives beside it. The pydantic field description
  states: explicit setting > detection > `local`.
- `Settings.runtime` defaults from `platform` in a `mode="before"`
  model validator (the model is frozen, so the default is filled in
  before construction, never assigned after), so `Settings()` on a
  laptop is `docker` and `Settings(platform="ursa")` is `native`
  without further input.
- `RunManifest` gains `platform` and `runtime` — run.yaml records where
  and how a run executed (the existing `cece_commit` pattern).
- A `--platform` pytest option is **not** added: `--cece-root-dir`
  exists because the root is per-invocation; platform/runtime are
  per-machine and belong in `.env`/environment, which the CLI writes.

### 2. Native driver execution (`runner.py`, `examples.py`, path model)

- `runner.build_command(settings, driver_yaml, output_mount)` becomes
  runtime-dispatching:
  - `docker` — unchanged, byte-for-byte (the existing tests pin it).
  - `native` — `[*shlex.split(settings.launcher), str(root_dir /
    settings.driver_path), str(driver_yaml)]`; `run_driver` passes
    `cwd=settings.root_dir` so the relative `./build/…` driver path and
    cwd-relative data paths resolve as they do under `-w /work`. No
    `OMPI_ALLOW_RUN_AS_ROOT*` (root-in-container only); the process
    inherits the caller's environment (modules, `I_MPI_FABRICS`, …) —
    environment is the batch script's job, not the harness's.
    `timeout_s` applies to the launcher process; under `srun` a timeout
    kills the step, which is the same failure mode as today's docker
    kill.
- `examples.run_example_command` gets the same dispatch: native →
  `["python3", str(root_dir / "examples/run-example.py"), "--example",
  eid]` with `cwd=root_dir` — `python3` from the environment, since the
  entrypoint is stdlib-only and CECE's own README invokes it that way
  (the harness venv interpreter would also work but couples CECE's
  script to the harness's Python). The examples session is not a Ursa
  target for this feature; it must simply not be docker-bound.
- Path model: `ComboRoots.container` is renamed **`driver`** (the root
  as the driver sees it) with `needs_mount` retained; `GeneratedCombo.
  container_yaml` → `driver_yaml`. In `native` runtime,
  `combo_roots` sets `driver = host` and `needs_mount = False` for both
  the explicit and the tmp-default root, so generated configs carry
  host paths. `resolve_output_roots(option, cece_root, runtime)`:
  docker keeps today's rule; native maps relative → `cece_root/rel`
  (same host location as docker, so `ufs-chem-assay-ci-output` lands
  in the checkout on every platform) and accepts any absolute host
  path (no `/work` requirement). The `--combo-output-root` help text
  and README wording change from "relative to /work in the container"
  to "relative to the CECE checkout".
- `src/tests/config/cece/simple-maccity.yaml`: `file:
  data/MACCity_4x5.nc` (audit item 3). Dry-run artifacts change by that
  one value; `test_maccity_pipeline`/`test_dry_run` expectations are
  updated where they assert the literal.

### 3. The `ufs-chem-assay` entrypoint

**Packaging.** `[project.scripts] ufs-chem-assay = "cli.main:main"`,
`[build-system]` hatchling with the wheel remapping `src/` to the
package root (`[tool.hatch.build.targets.wheel] only-include = ["src"]`,
`sources = {"src" = ""}`, tests excluded) so `models`, `combos`, `cli`
import exactly as they do under `pythonpath = ["src"]`; `tool.uv
package = true`; Dockerfile `uv sync --frozen --no-install-project`;
semantic-release `build_command` stays empty (nothing is published).
Fallback if packaging fights back: `uv run python -m cli …` with the
same code — the design does not depend on the console-script name.

**Code layout.**

```
src/
  platforms.py            # Platform / Runtime enums, detect_platform()
  cli/
    __init__.py
    main.py               # argparse: `run` subcommand, --config-file, --platform,
                          #   --stage (repeatable), --dry-run, --no-submit
    run_config.py         # RunConfig pydantic model (StrictModel), YAML loader,
                          #   platform-derived defaults
    stages.py             # one function per stage → ShellScript (text + purpose)
    shell.py              # script assembly, `bash` / `sbatch` execution, logs
scripts/
  local.yaml              # checked-in run configs: laptop (docker) …
  ursa.yaml               # … and Ursa (native + slurm); copy, edit account/paths
```

**Run config** (`RunConfig`, every field `Field(description=…)`;
pydantic models, no dataclasses; unknown keys rejected). The Ursa
template, values as decided here:

```yaml
platform: ursa                      # optional: detected when absent; --platform wins
root_dir: /scratch3/NCEPDEV/stmp/Benjamin.Koziol/my_stmp/ufs-chem-assay
                                    # everything the CLI creates lands here:
                                    #   CECE/ (unless cece.clone_dir), logs/, scripts/
cece:
  git_url: git@github.com:benkozi/CECE.git
  ref: fix/all-examples-pass        # branch or SHA; the integration workflow's ref
  clone_dir: null                   # default <root_dir>/CECE; an existing checkout
                                    #   is used as-is (fast-forward with update_source)
  update_source: false
  modulefile: cece_ursa.intelllvm   # from <clone>/modulefiles after `module purge`;
                                    #   null on local (no modules)
  cmake_args: [-DCMAKE_BUILD_TYPE=Release]
  build_jobs: 8
  targets: [cece_standalone_driver] # `all` to also build the unit-test stack
  run_tests: false                  # ctest under the launcher (needs `all`)
data:
  examples: [ex3]                   # download-example-data.py --example … (login node)
  warm_cartopy: true                # fetch Natural Earth 110m/50m on the login node
baselines:
  root_dir: null                    # CECE_BASELINE_ROOT_DIR
  enabled: false                    # CECE_ENABLE_BASELINE_COMPARISONS
harness:
  suite_config: simple-maccity-suite.yaml
  output_root: ufs-chem-assay-output   # relative → under the CECE checkout
  clean_root: true
  pytest_args: []                   # e.g. [-x, -k, map-consd]
  launcher: srun --ntasks=1         # CECE_LAUNCHER (native runtime only)
  env:                              # exported before pytest; single-node MPI hints
    I_MPI_FABRICS: shm
    FI_PROVIDER: tcp
  dask_nworkers: null               # null → the Slurm allocation's cpus
  run_timeout_s: 300
slurm:                              # null → stages run directly (local)
  account: epic
  qos: debug                        # 30 min cap; `batch` for the exhaustive suite
  partition: u1-compute
  time: "00:30:00"
  cpus: 8
  submit: true                      # false → write the sbatch script and stop
uv:
  cache_dir: null                   # UV_CACHE_DIR; default <root_dir>/uv-cache
                                    # (UV_PYTHON=3.13 belongs to the user's first
                                    #  `uv sync`, runbook step 2 — not a run knob)
```

`scripts/local.yaml` is the same shape with `platform: local`,
`modulefile: null`, `slurm: null`, `harness.launcher: ""`, `cece.ref`
pointing at the same branch, and no `uv` overrides — running it is the
laptop equivalent of the integration workflow (build via
`scripts/build-and-test-container.py --no-test --target
cece_standalone_driver`, i.e. the CLI's local build stage delegates to
CECE's container build script rather than reinventing it; the native
build stage is the one that runs cmake itself).

**Stages** (`--stage` repeatable; default: all, in this order). Each
stage renders to one shell script under `<root_dir>/scripts/` (named
`<NN>-<stage>.sh`, overwritten per invocation), logs to
`<root_dir>/logs/<stage>-<timestamp>.log`, and is executed with `bash`
on the current node **except** the last two, which on a Slurm platform
are concatenated into a single `sbatch` script:

| stage        | where (ursa)   | what                                                                                                                     |
|--------------|----------------|--------------------------------------------------------------------------------------------------------------------------|
| `source`     | login node     | clone `--recurse-submodules -b <ref>` if `clone_dir` missing; else use as-is, or `fetch` + `checkout` + `pull --ff-only` + `submodule update --init --recursive` with `update_source`; guard `extern/helm/libs`; log `git log -1` |
| `build`      | login node     | `module purge; module use <clone>/modulefiles; module load <modulefile>; module list; which $CC $CXX $FC cmake`; `cmake -S <clone> -B <clone>/build <cmake_args>` tee'd to `build/configure.log`; gates: `Found MPI`, `Found netCDF`/`NetCDF` line present; `cmake --build build --target <targets> --parallel <jobs>` |
| `data`       | login node     | from the harness checkout, `uv run --no-sync python <clone>/examples/download-example-data.py --example <ids> --dst-dir <clone>/data` (CECE's tooling needs Python ≥ 3.11; after `module purge` the OS `python3` is all that is left); optional cartopy warm-up the same way (`python -c "import cartopy.io.shapereader as s; …natural_earth(...)"`) |
| `cece-tests` | compute (job)  | `ctest --test-dir <clone>/build --output-on-failure` under the launcher; only when `run_tests` |
| `harness`    | compute (job)  | modules again (batch scripts start clean), `export CECE_ROOT_DIR CECE_PLATFORM=ursa CECE_RUNTIME=native CECE_LAUNCHER CECE_BASELINE_ROOT_DIR CECE_ENABLE_BASELINE_COMPARISONS CECE_DASK_NWORKERS=${SLURM_CPUS_PER_TASK} CECE_RUN_TIMEOUT_S UV_OFFLINE=1 <harness.env>`, then `uv run --no-sync pytest src/tests/test_driver_combos.py --suite-config=… --combo-output-root=… [--combo-clean-root] <pytest_args>` from the harness checkout |

`sbatch` header from `slurm:`: `-A account -q qos -p partition -N 1 -n 1
-c cpus -t time -J ufs-chem-assay -o <root_dir>/logs/slurm-%j.out`;
the CLI prints the job id and the `squeue -u $USER` / log paths, then
exits (it never waits for the job — `sacct`/the log tell the outcome;
a `--wait` is future work). `submit: false` or `--no-submit` writes the
script and prints the `sbatch` command instead. With `slurm: null`
the two stages run in-process with `bash`, which is the local path.

**Environment file.** The harness reads `.env` from its cwd; the CLI
does *not* write `.env` (it may hold the user's laptop paths) — it
exports the variables in the generated script, which beats `.env`
(environment > `.env` precedence already holds). The `harness` stage
also runs `uv sync --frozen` **only** when the venv is missing and the
stage runs on a login node; in the batch job it never syncs.

**`--dry-run`** renders every script, prints them with their paths, and
exits 0 without running `git`, `module`, `cmake`, `sbatch`, or pytest —
so the whole Ursa plan can be vetted on the laptop (the kokkos
script's convention; `--dry-run` on the pytest side keeps its existing
meaning and is reachable through `harness.pytest_args`).

**Safety rules** (from the reference script): the CLI never deletes
anything except the harness output root, and only via
`--combo-clean-root` when `clean_root` is true (the harness's own
guarded path); an existing `clone_dir` is never mutated without
`update_source`; `root_dir` is created if missing but never required
to be fresh (rebuilds are incremental — cmake handles it).

### 4. Manual runbook for Ursa (deliverable 3)

The implementation writes this section, as is, to **`docs/ursa-runbook.md`**
— the first file in a new `docs/` folder for operational documentation
(the README stays the quick start; design rationale stays here). Steps
1–5 are valid on the current tree (the harness suite and `--dry-run`
need no docker); steps 6–7 need the native runtime from section 2. The
CLI is `ufs-chem-assay run --config-file=scripts/ursa.yaml` over the
same steps, and the stage scripts it renders must stay recognisably
the runbook's commands — when one changes, the other does.

Conventions:

- `ROOT` is one scratch directory holding everything this runbook
  creates: `ROOT=/scratch3/NCEPDEV/stmp/Benjamin.Koziol/my_stmp/ufs-chem-assay`.
- `epic` / `debug` / `u1-compute` are the Slurm account, QOS, and
  partition used in the examples; substitute your own. `debug` caps
  jobs at 30 minutes, which fits `simple-maccity`; use `batch` (8 h)
  for the exhaustive suites.
- Steps 1–6 run on a **login node**: editing, compiling, downloads,
  and job submission are the allowed uses there. Nothing that needs
  network runs in the batch job (compute nodes are network-restricted).
- `$HOME` is quota-limited: caches, interpreters, and clones go under
  `ROOT`.

#### 1. uv (once)

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh     # installs ~/.local/bin/uv
export PATH="$HOME/.local/bin:$PATH"
export UV_CACHE_DIR=$ROOT/uv-cache UV_PYTHON_INSTALL_DIR=$ROOT/uv-python
```

No root, no conda, no `rdhpcs-python` module needed. Put the three
`export`s in your shell profile (or a small `source`-able file under
`ROOT`) so batch scripts and later logins see them.

#### 2. The harness

```bash
git clone git@github.com:benkozi/ufs-chem-assay.git $ROOT/ufs-chem-assay
cd $ROOT/ufs-chem-assay && git checkout feat/run-on-rdhpc
UV_PYTHON=3.13 uv sync --frozen        # downloads CPython 3.13 + wheels
uv run pytest src/tests/ufs_chem_assay # harness suite: hermetic, login-node safe
uv run pytest src/tests/test_driver_combos.py --dry-run   # no CECE needed
```

Python 3.13 rather than 3.14: every dependency has Linux wheels for
3.13 (cartopy included), so nothing compiles during the sync.

#### 3. CECE source

```bash
git clone --recurse-submodules -b fix/all-examples-pass \
    git@github.com:benkozi/CECE.git $ROOT/CECE
```

The branch is the one the integration workflow uses
(`.github/workflows/integration.yaml`, `CECE_REF`).

#### 4. Driver build (native, modules from the checkout)

```bash
module purge
module use $ROOT/CECE/modulefiles
module load cece_ursa.intelllvm && module list
which mpiicx mpiicpx mpiifx cmake
mkdir -p $ROOT/CECE/build
cmake -S $ROOT/CECE -B $ROOT/CECE/build -DCMAKE_BUILD_TYPE=Release \
    2>&1 | tee $ROOT/CECE/build/configure.log
grep -E "Found MPI|netCDF|Kokkos" $ROOT/CECE/build/configure.log
cmake --build $ROOT/CECE/build --target cece_standalone_driver --parallel 8
```

First-run checks:

- The modulefile's spack-stack environment must exist:
  `ls /contrib/spack-stack/spack-stack-1.9.2/envs/`. If `module load`

## Follow-up fix (2026-09-03): stats and plots select spatial fields only

Found while running the maccity suite through the CLI (implementation
notes above): the merged driver writes CF-1.9 cell bounds —
`lon_bnds (lon, lon_bnds_dim1)` and `lat_bnds (lat, lon_bnds_dim1)`,
both with a `units` attribute — as **data variables**, because the
`lon`/`lat` coordinates carry no `bounds:` attribute (CF requires it;
with it xarray would classify them as coordinates). The harness selects
variables as "everything in `ds.data_vars`": `analysis.compute_file_stats`
then emits six bounds rows per combo into `descriptive_stats.csv`, and
`plotting.render_combo_plots` tries to map the bounds tables,
`render_spatial_plot` asks them for `lat`/`lon`, and the `KeyError` is
logged by `logger.exception` and the plot skipped. `co` renders
normally; no test fails. The dimension assertion is unaffected (it
checks the suite's configured output fields only).

Decision (user, 2026-09-03): fix the selection in the harness — it does
not depend on CECE and closes the gap for any future auxiliary variable.
The CECE-side wart (missing `bounds` attributes; `lat_bnds` reusing the
`lon_bnds_dim1` dimension name instead of a shared `nv`/`bnds`) is
raised with CECE separately, not worked around here.

Rule: a **spatial field** is a data variable whose dimensions include
both `lat` and `lon`. One helper, `analysis.spatial_variables(ds)`,
returns their names in file order; `compute_file_stats` and
`render_combo_plots` use it, and anything skipped is logged once at
DEBUG. Choosing "carries lat and lon" over "the suite's configured
`output.fields`" keeps stats/plots independent of the suite config
(diagnostics the driver adds still get covered) and needs no change to
the suite model. Baseline comparison is untouched: it compares file
structure exactly, and bounds variables are part of that structure —
but the bias *plots* (`render_combo_bias_plots`) select through the
same helper, since a bounds table has no map either.

TDD: red tests in `test_analysis.py` (a driver-like file with a
`lon_bnds` data variable yields stats for the field only) and
`test_plotting.py` (the same file renders the field's PNG, no bounds
PNG, and nothing is logged at ERROR); then the helper and the two call
sites. `README.md` states the rule in the stats/plots paragraphs.

~~~markdown
**Title:** NetCDF writer: cell bounds are not linked to their coordinates (no `bounds` attribute) and `lat_bnds` reuses the `lon_bnds` dimension

## Summary

Since the CF-1.9 output changes, the standalone driver writes `lon_bnds` and `lat_bnds` cell-boundary variables. Two details of how they are written stop CF-aware readers from recognising them as boundaries:

1. The `lon` and `lat` coordinate variables carry no `bounds` attribute. CF (§7.1, *Cell Boundaries*) links a boundary variable to its coordinate only through that attribute; without it, readers such as xarray classify `lon_bnds`/`lat_bnds` as ordinary **data variables** alongside the emission fields.
2. Both boundary variables use a dimension named `lon_bnds_dim1`, so `lat_bnds` is dimensioned `(lat, lon_bnds_dim1)`. It works, but the conventional layout is one shared boundary dimension (`nv` or `bnds`, size 2) used by every `*_bnds` variable.

## Reproduce

```sh
./build/cece_standalone_driver <config with a MACCity CO stream, 72x46 grid>
python3 -c "import xarray as xr; print(xr.open_dataset('cece_20100101_010000.nc', decode_times=False))"
```

Output (trimmed):

```
Dimensions:   (lon: 72, lon_bnds_dim1: 2, lat: 46, time: 1, lev: 1)
Coordinates:
  * lon       (lon) float64 ...      units: degrees_east, long_name: longitude   <- no `bounds`
  * lat       (lat) float64 ...      units: degrees_north, long_name: latitude   <- no `bounds`
  * time      (time) float64 ...
  * lev       (lev) float64 ...
Dimensions without coordinates: lon_bnds_dim1
Data variables:
    lon_bnds  (lon, lon_bnds_dim1) float64   units: degrees_east
    lat_bnds  (lat, lon_bnds_dim1) float64   units: degrees_north
    co        (time, lev, lat, lon) float64  units: kg m-2 s-1
Attributes:
    Conventions:  CF-1.9
```

## Impact

Any consumer that iterates the file's data variables (statistics, plotting, comparison tooling) now sees two extra "fields" of shape `(72, 2)` and `(46, 2)`. The ufs-chem-assay harness hit this as a plotting `KeyError: 'lon'` on `lon_bnds` and bogus rows in its statistics CSV; it now filters on lat/lon dims, but the file itself should carry the link so every CF reader gets it right.

## Expected

```
dimensions:
    lon = 72 ; lat = 46 ; nv = 2 ; ...
variables:
    double lon(lon) ;
        lon:units = "degrees_east" ;
        lon:long_name = "longitude" ;
        lon:bounds = "lon_bnds" ;
    double lon_bnds(lon, nv) ;
    double lat(lat) ;
        lat:units = "degrees_north" ;
        lat:long_name = "latitude" ;
        lat:bounds = "lat_bnds" ;
    double lat_bnds(lat, nv) ;
```

Boundary variables inherit `units`/`long_name` from their coordinate under CF, so the attributes on `lon_bnds`/`lat_bnds` are optional; keeping them is harmless. `time` and `lev` bounds, if ever written, would use the same `nv` dimension.

- CECE `b28ba69` (`fix/all-examples-pass`, includes upstream `develop`), Docker dev image (`cece/cece-dev`, GCC 13, NetCDF-C 4.9)
- Reader: xarray 2026.4.0 / netCDF4-python 1.7.4
~~~

## Considered: `srun` instead of `sbatch` (2026-09-04, user question)

Decision: **stay with `sbatch` for now** and get it running on Ursa;
switch later if the interactive loop proves worth it. Findings, so the
switch is a known quantity:

- The script does not go away — its substance is the environment
  (modules, `CECE_*` exports, the pytest line); the `#SBATCH` lines
  are the only batch-specific part and are harmless comments under
  `srun`. The switch is a submission change, not a rendering change.
- Trade-offs: `srun … bash <script>` blocks the terminal, streams
  output live, returns the exit code to the CLI directly (no `--wait`
  or `sacct` needed), but sits through the queue wait and dies with the
  SSH session unless run under `tmux`. `sbatch` returns a job id,
  writes the log to a file, survives disconnects, and suits unattended
  or long runs (the exhaustive suites). Issue #5's "testing should run
  via `srun`" and the kokkos reference script (synchronous `srun` for
  tests) read more naturally as the `srun` mode.
- **Hazard when switching: the per-combo launcher.** Inside an
  `srun`-launched step, a nested `srun --ntasks=1` competes with its
  parent for the allocation's CPUs and waits until the step ends — the
  harness would hang until each combo's timeout — unless every inner
  call carries `--overlap` (Slurm ≥ 20.11). Inside an `sbatch`
  allocation the inner steps are fine, which is why today's template
  can set `launcher: srun --ntasks=1`. The inner launcher buys little
  either way (the session is already on the compute node; the driver is
  a single-rank process Python spawns and times out itself; steps add
  creation latency and `sacct` rows), so an `srun` mode would ship with
  `harness.launcher` empty and the knob left for multi-rank futures.
- Proposed shape, if adopted: `slurm.mode: srun | sbatch` (default
  `srun`); the CLI renders the same compute script and in `srun` mode
  runs `srun -A … -q … -p … -N 1 -n 1 -c … -t … bash <script>` through
  the existing streaming runner (log + exit code like any stage);
  `sbatch` mode keeps submit-and-report. Runbook step 7 gains the
  `srun` line with `sbatch` as the unattended alternative;
  `CECE_DASK_NWORKERS` keeps following `SLURM_CPUS_PER_TASK`, which
  `srun` sets too. Tests: mode-specific rendering/submission in
  `test_cli.py`, and the launcher-empty rule in `test_stages.py`.
