# Feature: python-semantic-release in CI — automatic releases, PR previews, credential verification

## Goal

Move releasing from the current manual-only `workflow_dispatch` to the `ufs-chem-container` shape:

1. **Automatic releases on push** to `develop` (`X.Y.Z-rc.N` prereleases) and `main` (releases), run by the official PSR v10 action from a reusable (`workflow_call`) `semantic-release.yml`, gated on the green `pre-commit` and `tests` jobs of `ci.yaml`.
2. **A release preview on every pull request** (and on manual dispatch): a dry run that evaluates both the merge-commit and the squash-merge outcome of the PR, and writes a "Semantic Release Plan" (current version, next version, tag, will-release, is-prerelease, projected diff of `pyproject.toml`/`uv.lock`/`CHANGELOG.md`) to the job summary. Nothing is tagged or pushed.
3. **A daily `verify-secrets.yml`** (cron + manual dispatch) that proves the PSR credentials still work: secrets present and well-formed, the GitHub App token can create and delete a ref on this repository, and the App sits in the bypass list of every ruleset that requires pull requests. It never runs on forks.
4. **No `[ci skip]` anywhere in PSR output.** Bump commits read `"{version}\n\nAutomatically generated by python-semantic-release"`, and CI avoids the self-trigger loop the way the container does: job-level `if:` conditions on the head commit's message, not GitHub's skip token.

Out of scope (unchanged): publishing anything. No GitHub Release object (`vcs_release: false`), no PyPI, no registry.

## Pre-design audit (fresh facts, 2026-10-06)

Verified on `feat/psr-ci` at `3d180ca` and against the live GitHub repository.

1. **What exists today.** `semantic-release.yml` is `workflow_dispatch`-only with a develop/main `case` guard, `permissions: contents: write`, checkout `fetch-depth: 0` + `persist-credentials: true`, then `python-semantic-release/python-semantic-release@v10` with `github_token: ${{ github.token }}` and `vcs_release: false`. `ci.yaml` (PRs + pushes to develop/main, `contents: read`, concurrency `ci-${{ github.ref }}` with `cancel-in-progress: true`) runs `build` → `pre-commit` (all files, plus a PR-title conventional-commit check) and `tests`, everything inside the toolchain image. `integration.yaml` runs the real `simple-maccity` suite on PRs to develop and pushes to develop (`continue-on-error`, 60-minute budget).
2. **`[tool.semantic_release]`** in `pyproject.toml`: `version_toml = ["pyproject.toml:project.version"]`, empty `build_command`, `allow_zero_version = true`, `commit_message = "{version}\n\nAutomatically generated by python-semantic-release [ci skip]"`, `changelog.exclude_commit_patterns` anchored on the same `[ci skip]` suffix, branch groups `main` (release) and `develop` (prerelease, default token `rc`). PSR is not a dependency; the action is its only runner; local previews use `uv tool run --from 'python-semantic-release>=10,<11' semantic-release --noop version`.
3. **The release push cannot work with `github.token` on this repository.** Ruleset `develop` (id 19711304, enforcement `active`) carries rules `deletion`, `non_fast_forward`, `pull_request` with **`bypass_actors: []`** and `current_user_can_bypass: never`. A `pull_request` rule rejects every direct push, including the workflow token's. The manual workflow was never exercised (`gh run list` shows only `ci`/`integration` runs), so this has not surfaced yet. `main` has no ruleset (yet). The container's answer — a GitHub App (`SEMVER_APP_ID`, `SEMVER_APP_PRIVATE_KEY`) added to the ruleset's bypass list — is therefore a requirement here, not the "upgrade path" the 2026-07-24 design recorded it as. Repository secrets could not be listed with the available token (HTTP 403); whether the App already exists is unknown.
4. **A GitHub App token's push triggers workflows; `GITHUB_TOKEN`'s does not.** With the App, the bump commit lands as a normal push to develop/main and starts `ci.yaml` and `integration.yaml`. This is the loop `[ci skip]` prevented and the reason the container gates its `release` job on `!contains(github.event.head_commit.message, 'Automatically generated by python-semantic-release')`.
5. **Version state.** One tag exists, `v0.1.0-rc.1` on `3af1373` (PR #1, the initial implementation), while `project.version` is still `0.1.0` and `uv.lock` records `ufs-chem-assay` at `0.1.0` (`source = { editable = "." }`; `tool.uv package = true`). Commits on develop since the tag: `feat: run simple CECE example in CI (#2)`, **`feat!: rename repository to ufs-chem-assay (#3)`**, `docs: remove design mention (#4)`, `feat: run on RDHPC (#6)`, `feat: application agnostic (#15)`. PSR's default `major_on_zero = true` turns the `feat!` into **`1.0.0-rc.1`** on the next develop release; with `major_on_zero = false` the same history yields `0.2.0-rc.1`. No `CHANGELOG.md` exists; PSR will create it on first release and the preview will show its first rendering.
6. **Merge strategy is squash.** Every merged PR appears as one commit titled from the PR (`(#N)` suffix); the ci.yaml PR-title check exists because of that. PSR v10's conventional parser defaults `parse_squash_commits = true`, which would turn every conventional-looking bullet in a squash body into its own version-bump candidate and changelog entry — the container disables it with a comment; so does this design.
7. **`uv.lock` carries the project version** (fact 5), so a bump commit that touches only `pyproject.toml` leaves the lock stale. `uv sync --frozen` (what the image and CI run) does not notice, but `uv lock --check` / `--locked` would, and the next unrelated `uv lock` churns the version line into someone else's PR. The container handles this with PSR's `build_command` (`pip install uv && uv lock --upgrade-package "$PACKAGE_NAME" && git add uv.lock`; PSR exports `PACKAGE_NAME` and `NEW_VERSION` to the build command's environment and its commit step commits the whole index, so the staged lock rides in the bump commit).
8. **Container reference, distilled.** `main.yml` (push/PR on main+develop, `workflow_dispatch`, `cancel-in-progress` only for PRs, `contents: write`) calls `lint.yml` always, `semantic-release.yml` with `dry_run: true` on PRs/dispatch (`release-preview`), and `semantic-release.yml` with `dry_run: false` on push when `github.repository == 'ufs-community/ufs-chem-container'` and the head commit is not a PSR commit (`release`, `needs: lint`). `semantic-release.yml` has two jobs: `verify-credentials` (skipped on forks via the repository check; `check-secrets` with `--allow-missing` on dry runs/PRs, else strict; mint App token; `check-permissions`) and `release` (App token if both secrets exist else `github.token`; checkout with that token, `fetch-depth: 0`; on dry runs: `prepare_release_preview.py --strategy merge` → PSR with `commit/tag/push: false` → `git diff HEAD` captured, then the same for `--strategy squash` when a PR title exists; on real runs: PSR with `commit/tag/push: true`; always: `report_release.py` writes the plan to `GITHUB_STEP_SUMMARY` and exports outputs). `lint.yml` additionally checks the **pushed** commit message on push events, skipping PSR commits. `verify-secrets.yml` runs daily at 06:00 UTC + dispatch, repository-guarded, and re-runs `check-secrets` (strict) + `check-permissions --branches develop main`. Its `pyproject.toml` PSR block differs from ours in: `commit_message` without `[ci skip]`, `exclude_commit_patterns` ending in `.*$`, the `build_command` above, `parse_squash_commits = false`, `prerelease_token = "rc"` spelled out, and `vcs_release = true` (a GitHub Release object — not adopted here, see Decisions).
9. **Toolchain for the glue.** The release workflow does not use the project image (the PSR action runs in its own container); its helper scripts run under the runner's `python3`, so they must be stdlib-only (argparse + logging + subprocess + json), as the container's are. `mypy` currently checks `files = ["src"]`; pytest's `pythonpath = ["src"]`. `.yamllint.yaml` already tolerates the bare `on:` key; `line-length: 120` applies to workflows.
10. **PSR action surface (v10.7.0 at refinement time).** Inputs used: `github_token`, `commit`, `tag`, `push`, `vcs_release` (plus `changelog`, `build`, `no_operation_mode`, `prerelease`, `force` unused). Outputs: `released`, `version`, `tag`, `is_prerelease`, `previous_version`, `commit_sha`, `release_notes`, `link`.

## Design

### 0. Decisions

- **Automatic on push supersedes manual-only** (the 2026-07-24 user direction). The issue asks for the container's fashion, and the container releases on every push to develop/main. `workflow_dispatch` on `ci.yaml` stays as a *preview* trigger for any branch; there is no manual production release path (recorded under Open questions as a one-line switch if wanted).
- **GitHub App credentials are required for production** (audit fact 3). `github.token` remains the fallback so previews — including fork PRs, which get no secrets — always work. The App needs `Contents: Read and write` on this repository and a bypass entry (`always`) on the `develop` ruleset and on `main`'s when one is created. These are operator steps outside the repository; `verify-secrets.yml` is what tells us whether they were done.
- **No `[ci skip]`; loop prevention by job condition.** Exactly the container's marker string, checked in three places: the `release` job in `ci.yaml`, the `simple-maccity` job in `integration.yaml` (a 60-minute CECE build on a version bump buys nothing), and the push-commit grammar check (a PSR commit is not conventional by design). `pre-commit` and `tests` *do* run on the bump commit: cheap, and the branch head always carries a CI status.
- **`major_on_zero = false`** (recommended; audit fact 5): the project is pre-1.0 and the next develop release should be `0.2.0-rc.1`, not `1.0.0-rc.1`. Flipping to `true` is the day the user decides to cut 1.0. Open question, with this as the default.
- **`vcs_release: false` kept.** The standing no-publish rule covers GitHub Release objects; the issue does not reopen it. The container's `vcs_release = true` is noted, not adopted.
- **`parse_squash_commits = false`**, with the container's comment, because this repository squash-merges (audit fact 6).
- **`build_command` refreshes `uv.lock`** (audit fact 7), copied from the container.
- **Scripts live in `.github/workflows/scripts/`** (mirror), stdlib-only, with `argparse` and stdlib `logging` rather than pydantic models and the harness `logs` module: they run on the bare runner before any `uv sync`, and pydantic is not available there. This is the one deliberate deviation from the "always do" list, and it is confined to CI glue. They are unit-tested from the harness suite by adding their directory to pytest's `pythonpath`.
- **Repository guard string**: `benkozi/ufs-chem-assay`, used in `ci.yaml` (`release`), `semantic-release.yml` (`verify-credentials`) and `verify-secrets.yml`. A move to `ufs-community` is a three-string edit (listed in the README next to `CECE_REPOSITORY`'s one-line retarget note).

### 1. `pyproject.toml` — the PSR block

```toml
# Releases run from CI (ci.yaml → semantic-release.yml) on every push to
# develop (X.Y.Z-rc.N) and main (X.Y.Z): version-bump commit + tag +
# CHANGELOG.md, nothing published. The bump commit carries the marker
# below and NOT [ci skip]: workflows gate on the marker themselves (see
# ci.yaml / integration.yaml), so the bump commit still gets pre-commit
# and tests. build_command keeps uv.lock's recorded project version in
# step with pyproject.toml (packaged project). PSR itself is not a
# dependency — the GHA action runs it; preview locally via
#   uv tool run --from 'python-semantic-release>=10,<11' semantic-release --noop version
[tool.semantic_release]
version_toml = [
    "pyproject.toml:project.version",
]
version_variables = []
build_command = """
pip install uv
uv lock --upgrade-package "$PACKAGE_NAME"
git add uv.lock
"""
allow_zero_version = true
major_on_zero = false
commit_message = "{version}\n\nAutomatically generated by python-semantic-release"

[tool.semantic_release.commit_parser_options]
# Parse only the squash-merge subject (the PR title). PSR v10 defaults this to
# true and would otherwise turn every conventional-looking bullet in a squash
# body into its own changelog entry and version-bump candidate.
parse_squash_commits = false

[tool.semantic_release.changelog]
exclude_commit_patterns = [".*\\n\\nAutomatically\\ generated\\ by\\ python\\-semantic\\-release.*$"]

[tool.semantic_release.branches.main]
match = "(^main$)"
prerelease = false

[tool.semantic_release.branches.develop]
match = "(^develop$)"
prerelease = true
prerelease_token = "rc"
```

Changes versus today: comment rewritten; `build_command`; `major_on_zero`; `commit_message` and `exclude_commit_patterns` without `[ci skip]`; `commit_parser_options`; `prerelease_token` explicit. Also: `[tool.mypy] files` gains `".github/workflows/scripts"`, and `[tool.pytest.ini_options] pythonpath` gains the same path.

### 2. `semantic-release.yml` — reusable, two jobs

`on: workflow_call` with inputs `dry_run` (bool, default false), `target_branch` (string, default `''`), `pr_title` (string, default `''`); outputs `current_version`, `new_release_version`, `new_release_published`, `is_prerelease`, `tag` from the `release` job. The old `workflow_dispatch` + branch guard goes (dispatch now lives on `ci.yaml` and means preview; PSR's branch regexes already refuse any ref outside develop/main for a real run). No `permissions:` block in the called workflow: it inherits the calling job's.

**Job `verify-credentials`** — `if: github.repository == 'benkozi/ufs-chem-assay'`; steps: checkout; `verify_semantic_release_credentials.py check-secrets` with `--allow-missing` when `inputs.dry_run || github.event_name == 'pull_request'` (writes `skip_verification=true` when the secrets are absent on a preview, fails otherwise); if not skipped: `actions/create-github-app-token@v3` (`client-id: SEMVER_APP_ID`, `private-key: SEMVER_APP_PRIVATE_KEY`), then `check-permissions --branches "<target_branch || base_ref || ref_name>"` with `GH_TOKEN` = the App token (installation lists this repo; create + delete `refs/tags/ci-perm-check-<run_id>` at `github.sha`; inspect rulesets with a `pull_request` rule and warn when the App is not an `always` bypass actor).

**Job `release`** — `needs: verify-credentials`, `if: !cancelled() && (needs.verify-credentials.result == 'success' || needs.verify-credentials.result == 'skipped')` (skipped = fork). Steps, in order:

1. Mint the App token only if both secrets are non-empty (`env` of the job; `if: env.SEMVER_APP_ID != '' && env.SEMVER_APP_PRIVATE_KEY != ''`).
2. Checkout: `fetch-depth: 0`, `token: ${{ steps.app-token.outputs.token || github.token }}`, `persist-credentials: true` (PSR pushes through the checkout's credential).
3. Preview only (`inputs.dry_run || github.event_name == 'pull_request'`): `prepare_release_preview.py --strategy merge` (tags `pr-merge-ref`/`pr-source-ref` once, then `checkout -B <target> pr-merge-ref` so PSR evaluates the PR's merge commit as if on the target branch; with no PR — dispatch on develop/main — this is "what would release right now"), PSR action with `commit: false`, `tag: false`, `push: false`, `vcs_release: false`, `git diff HEAD > /tmp/merge_preview.diff`.
4. Preview with a PR title: `prepare_release_preview.py --strategy squash` (reset to `origin/<target>`, `merge --squash pr-source-ref`, synthetic commit titled with the PR title, so PSR sees exactly the subject a squash merge will produce), PSR again (`commit/tag/push: false`), `git diff HEAD > /tmp/squash_preview.diff`.
5. Production (`!(inputs.dry_run || github.event_name == 'pull_request')`): PSR with `commit: true`, `tag: true`, `push: true`, `vcs_release: false`, `github_token` = App token or `github.token`.
6. Always: `report_release.py` with the three PSR step outputs (`version`/`tag`/`released` for prod, merge, squash), the two diff files, `TARGET`, `DRY_RUN`; it writes `GITHUB_OUTPUT` (`is_prerelease`, `target_branch`, `current_version`, `new_release_version`, `new_release_published`, `tag`) and appends the Markdown plan to `GITHUB_STEP_SUMMARY`.

### 3. `ci.yaml` — orchestration

- `on:` adds `workflow_dispatch` (preview against the picked branch; the branch picker *is* the target selector).
- `concurrency.cancel-in-progress: ${{ github.event_name == 'pull_request' }}`: a push run that is mid-release must never be cancelled by the bump commit's own push; the latter queues in the same `ci-refs/heads/<branch>` group and runs after, which is exactly the ordering wanted.
- Workflow-level `permissions: contents: read` stays. The `release` job alone sets `permissions: contents: write` (a `uses:` job may set its own; the called workflow cannot exceed it).
- New job `release-preview`: `if: github.event_name == 'pull_request' || github.event_name == 'workflow_dispatch'`, `uses: ./.github/workflows/semantic-release.yml` with `dry_run: true`, `target_branch: ${{ github.base_ref || github.ref_name }}`, `pr_title: ${{ github.event.pull_request.title || '' }}`, `secrets: inherit`. Not gated on `build`/`tests`: it is informational and should appear early in the PR checks.
- New job `release`: `if: github.repository == 'benkozi/ufs-chem-assay' && github.event_name == 'push' && !contains(github.event.head_commit.message, 'Automatically generated by python-semantic-release')`, `needs: [pre-commit, tests]` (a red branch does not release — stricter than the old "operator dispatches on green" contract, and automatic), `uses` the same workflow with `dry_run: false`, `target_branch: ${{ github.ref_name }}`, `secrets: inherit`.
- `pre-commit` job gains the container's **push-commit grammar check**: on `push` events, `git log -1 --pretty=%B` into a file and the baked `conventional-pre-commit` hook against it, exiting 0 early when the message contains the PSR marker. Runs inside the image like the PR-title check, the message passed via file, never interpolated.
- Header comment rewritten ("Releases are NOT here" is no longer true).

### 4. `integration.yaml`

`simple-maccity` gets `if: ${{ !contains(github.event.head_commit.message, 'Automatically generated by python-semantic-release') }}` (`head_commit` is absent on `pull_request`, `contains(null, …)` is false, so PR runs are unaffected). Header comment notes the gate.

### 5. `verify-secrets.yml` — daily

```yaml
name: verify-secrets
on:
  schedule:
    - cron: 0 6 * * *   # daily, 06:00 UTC
  workflow_dispatch:
concurrency:
  group: verify-secrets
  cancel-in-progress: true
permissions:
  contents: read
jobs:
  verify-semantic-release-credentials:
    if: github.repository == 'benkozi/ufs-chem-assay'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - check-secrets (strict: missing or malformed secrets fail the job)
      - actions/create-github-app-token@v3
      - check-permissions --branches develop main (GH_TOKEN = App token)
```

`contents: read` is enough: the write probe (create/delete a throwaway tag) goes through the App token, which is the credential under test. Scheduled workflows run only from the default branch (`develop`) and GitHub pauses them after 60 days without repository activity — a paused schedule is itself a signal worth knowing; the manual dispatch covers it. Forks never run it (repository guard, and the schedule is disabled on forks by GitHub anyway).

### 6. Helper scripts (`.github/workflows/scripts/`)

Ported from the container with its structure kept (subcommands, env-var defaults, `::error::`/`::warning::` workflow commands, `GITHUB_OUTPUT`/`GITHUB_STEP_SUMMARY` appends); the editorial "ponytail" comments are dropped; typed for mypy (`disallow_untyped_defs`), ruff-clean (ruff checks every `.py` it finds; `ruff.toml` needs no change).

- `verify_semantic_release_credentials.py` — `check-secrets [--allow-missing]` (presence; private key is not a path, has BEGIN/END markers, is not quoted) and `check-permissions --branches …` (installation repos, ref create/delete probe, ruleset bypass audit). Verbatim port apart from typing/comments.
- `prepare_release_preview.py` — `--strategy merge|squash`, `--target`, `--pr-title`; identical git choreography to the container.
- `report_release.py` — same CLI and outputs minus `--org`/`--image-name`; `describe_actions` lists what *this* repository's release does: git tag `<tag>` created; `CHANGELOG.md` updated and `pyproject.toml`/`uv.lock` bumped in a commit by python-semantic-release; "no GitHub Release object, nothing published". Dual (merge vs squash) table on PR previews, single table on dispatch/production, projected diffs in collapsible blocks.

Tests, under `src/tests/ufs_chem_assay/test_release_scripts.py` (the scripts import by module name once their directory is on pytest's `pythonpath`):

- `check_secrets`: missing + `allow_missing` → exit 0 and `skip_verification=true` in a tmp `GITHUB_OUTPUT`; missing strict → 1; path-looking key / no markers / quoted key → 1 with the matching `::error::`; valid → 0 and `skip_verification=false`.
- `report_release`: `is_prerelease`, `extract_version_from_toml`, `generate_report` for dual and single modes (table rows, action lines mention tag/changelog/pyproject/uv.lock and never a container), `determine_current_version` against a tmp git repo with a `v0.1.0-rc.1` tag; `main()` end-to-end writes both `GITHUB_OUTPUT` keys and the summary file.
- `prepare_release_preview`: tmp bare `origin` + clone with a target branch and a PR merge commit; `merge` strategy leaves HEAD at the merge ref on a branch named `<target>`; `squash` strategy produces one commit whose subject is the PR title on top of `origin/<target>`; missing target raises.
- `check_permissions`/`run_gh_api`: `gh` is mocked (`pytest-mock`) — installed-repo miss → 1, ref-create failure → 1, success path calls DELETE on the probe ref, ruleset without bypass → `::warning::` line.

## Risks and notes

- **Ruleset bypass is the single point of failure.** Without the App in the bypass list the production push fails at the very end of a run (after PSR has committed and tagged locally). The daily job and the `verify-credentials` gate exist to catch this before a merge does. The `check-permissions` warning (not error) on a missing bypass mirrors the container; it could be promoted to an error once the App is in place — noted under Future work.
- **PSR's `build_command` runs inside the action's container** (`pip install uv` each run, network needed) and `uv lock --upgrade-package ufs-chem-assay` re-resolves against the index; it should change only the project's own `version` line. The preview diff on this PR is where that is confirmed; if the lock churns beyond that line, pin with `uv lock --upgrade-package ufs-chem-assay --offline` or drop to a `sed` on the one line.
- **The bump commit is checked by `pre-commit`/`tests` and not by the grammar check** (marker skip). That is the container's behaviour and the correct one: `0.2.0-rc.1` is not a conventional subject.
- **Fork PRs** run the preview with a read-only `github.token`, no secrets, `verify-credentials` skipped: safe by construction (`commit/tag/push: false`). Forks never release (repository guard) and never run the daily job.
- **Both previews share one checkout**; `prepare_release_preview.py` resets the tree between strategies and tags the merge/source refs once. `git checkout -B <target>` on a detached PR checkout is the whole trick that lets PSR's branch regexes match.
- **`main` currently sits at the initial commit** with no ruleset; the first release there (a merge of develop) will need the same bypass if a ruleset is added first. `check-permissions --branches develop main` reports both.
- **`concurrency` ordering** relies on `cancel-in-progress` being false for pushes; if it is ever flipped back to `true`, the bump commit's push cancels the still-running release run (harmless after the push step, but muddles the record).
