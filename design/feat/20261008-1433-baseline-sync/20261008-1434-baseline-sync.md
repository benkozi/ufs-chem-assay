# Feature: publish baselines to the `ufs-chem` S3 bucket — a combination's output becomes `<store>/<ulid>/` with a manifest, and the suite is repointed

Refined 2026-10-08 from https://github.com/benkozi/ufs-chem-assay/issues/22 ("Add tool to synchronize new baselines to the `ufs-chem` S3 bucket"), starting from the "Deferred: baseline sourcing" section of `design/feat/20261007-1555-retire-examples/20261007-1555-retire-examples.md` (the store, the ULID invariant, the append-only rule, the publish-refuses-overwrite rule were all settled there with the user on 2026-10-07) and from issue #19's wrapper (`src/s3_sync.py`). This change is the **upload half**: publishing. The download half (the session syncing a pinned ULID it does not hold locally) stays deferred and is listed under Future work with what this change prepares for it.

## Goal

After a suite has run, one command turns the combinations the suite compares against into new baselines in the private bucket and repoints the suite at them:

1. **`ufs-chem-assay publish-baselines --output-root <root>`** (`src/baselines.py`, generic; the CLI subcommand in `cli/main.py`): for every `baseline_comparisons` entry of every suite the run executed, take the combination the entry selects, upload that combination's output directory as **`s3://ufs-chem/baselines/<combo ULID>/`** together with a **manifest** (`baseline.yaml`: application, the application commit the run was built from, when and by whom it was published, the run and combination identity, the effective parameters, the file list with digests, the ULID it supersedes), and **rewrite the entry's `ulid`** in the suite file to the new ULID. One `aws s3 sync` per baseline through the existing wrapper; the store is append-only (a prefix that already holds objects is refused).
2. **Only sound output becomes a baseline**: a combination is published only when its driver execution passed and none of its other tests failed — the comparison against the *old* baseline excepted, since a republish is exactly what follows an intentional driver change.
3. **`--dry-run`** (default off): the full plan — which combinations, why any are skipped, the manifest each would carry, the wrapper's own `(dryrun) upload:` lines — and nothing written anywhere. **`--no-suite-update`** (default off): publish, but leave the suite files alone (the new ULIDs are logged and in the manifests).
4. **Publish from the session itself**: `pytest --publish-baselines` (and the run config's `harness.publish_baselines: true`) runs the same publication at session end, so a run on Ursa or a laptop can refresh baselines without a second command; `--no-suite-update` applies there too.
5. **Application-agnostic by construction**: nothing in `baselines.py` knows CECE, and nothing needs to — a baseline is **the whole combination output directory** (user direction, 2026-10-08): the NetCDF, the generated config, the captured `.out`, the driver log, the stats and comparison CSVs, the overview and bias plots and GIFs, a slurm job script where there is one. Diagnostics an application adds later ride along with no hook; the comparison still reads the `*.nc` only, and the rest is reference material beside them in the bucket. The manifest lists every file.
6. **CECE `develop` is the driver** from this change on: ufs-community/CECE#154 merged on 2026-10-08, so every pin that pointed at its head branch moves to `ufs-community/CECE` + `develop` (audit fact 5).
7. **The integration use case is `simple-maccity`** — three combinations sweeping the interpolation algorithm (`mapalgo`), one baseline entry each: run it against `develop`, publish, run it again, and all three comparisons are green against baselines that carry manifests.

Out of scope: the session fetching a pinned ULID it lacks locally (the deferred download half — this change makes the manifest the marker it will use), pruning the store or the local cache, CI credentials for baselines (`integration.yaml` keeps `ASSAY_ENABLE_BASELINE_COMPARISONS: 'false'`), a store listing verb, generating `baseline_comparisons` entries for combinations that have none (Open questions).

## Design

### 0. Decisions

- **The suite's `baseline_comparisons` entries are the contract for what gets published.** Each entry already says *which combination* (the selector) and *which copy* (the ULID). Publishing a run means: for every entry, upload the selected combination's output as a new ULID and repoint the entry. Combinations with no entry are not baselines and are not published; a suite with no entries publishes nothing (logged). Bootstrapping a new suite is adding entries by hand (any syntactically valid ULID as the placeholder, then publish) — generating entries from combinations is an Open question with a default of "not now".
- **The baseline's ULID is the combination's runtime ULID** (`combo_id`, minted at enumeration, never derived from content or configuration — the retire-examples deferred item 5). Every run mints new ones, so a republish can never collide with an existing baseline, the store is append-only by construction, and "already published" is simply "the suite already pins this run's ULID" — detectable without the network.
- **The store is one harness-wide setting**: `Settings.baseline_store` / `ASSAY_BASELINE_STORE`, default `s3://ufs-chem/baselines`, an `s3://bucket/prefix` with a non-empty prefix (a bucket root is refused — the live test's `ufs-chem-assay-tests/` prefix and the baselines must never share a root the tool could touch), stored without a trailing slash; a baseline lives at `<store>/<ulid>/`, **flat** (the manifest, not the key, says which application and suite it belongs to; a per-application layout is recorded under Open questions). `--store` on the subcommand overrides for one invocation (the live test's hook).
- **Append-only, enforced**: before uploading, one `--dryrun` sync of `<store>/<ulid>/` into an empty temporary directory must list nothing; any `(dryrun) download:` line means the prefix is occupied and the baseline is **refused**, never merged or overwritten. The harness has no delete path for baselines at all (the wrapper's `delete` is never set here).
- **The manifest is `baseline.yaml`** (`BASELINE_MANIFEST = "baseline.yaml"`), a frozen pydantic `BaselineManifest` (section 1), written into the combination's output directory *before* the sync and uploaded with the files. It serves three readers: a human browsing the bucket, the future download half (a present manifest is the "synced" marker — no separate `.synced` file is needed), and the output root itself, where its presence records that the combination was published (and from where — the `store` field).
- **A baseline is the whole combination directory** (user direction, 2026-10-08, replacing an adapter hook that would have selected the NetCDF only): everything under `<root>/<combo_id>/`, subdirectories included, goes to `<store>/<ulid>/` as-is. The images and GIFs are the reference material the user wants beside the data; the `.out`, driver log, generated config, and stats CSVs make the baseline self-explaining without the output root. No adapter method, no file list to maintain, no per-application knowledge in `baselines.py`. The comparison side is untouched (it globs `*.nc` at the top level of both sides; everything else is invisible to it until a comparison for it is designed). The manifest's `files` lists every file with its path relative to the directory, size, and digest.
- **No copy, one unfiltered sync**: the combination directory is the sync source, the manifest having been written into it first. `only_show_errors=True` on the real transfer (the manifest lists the files; the `upload:` lines add nothing), `dry_run=True` on a dry run (the lines *are* the plan). The cache copy, when configured, is a `copytree` of the same directory.
- **The gate**: a combination is published only if, in the run's test outcomes, `test_driver_execution` **passed** and no other test of that combination **failed**, excluding `test_baseline_comparison` (the comparison against the old baseline is expected red when republishing). Skips are allowed (a suite with stats off skips those tests; a `--dry-run` session skips everything and therefore publishes nothing — the right outcome, no special case). The gate reads `test-report.csv` (CLI) or the same rows before they are written (session); one function, `publishable(rows_for_combo)`.
- **Upload first, then edit the suite.** The suite file is rewritten only after that baseline's sync returned 0, one entry at a time; a failed transfer leaves its entry untouched and the others proceed. If the upload succeeds and the edit fails (section 4's guards), the baseline is in the store, the ULID is logged, and the user edits by hand or simply re-runs — **a re-run resumes**: a combination directory whose own `baseline.yaml` names this ULID and this store is one the tool published before, so an occupied prefix is then "already in the store" rather than a refusal, the upload is skipped, and only the cache copy and the suite edit are redone. An unreferenced object in an append-only store is harmless either way.
- **The local cache is primed when it exists.** With `ASSAY_BASELINE_ROOT_DIR` set, a published baseline is also copied to `<root>/<ulid>/` (the files plus the manifest), so the very next local run compares against it with no download half yet; `<root>/<ulid>/` already existing is refused (never overwritten). With the setting unset nothing local is written — the harness never writes baselines into the cwd — and the user is told the next run will fail "configured but missing" until the download half exists or the directory is placed by hand.
- **Session-end publication is the same function**, called from `pytest_sessionfinish` after `test-report.csv` is written and before the plots (a plotting failure must not cost a publish; the report is on disk first). It is opt-in by flag (`--publish-baselines`), has no dry-run variant of its own (dry-run the output root with the subcommand afterwards), and never raises into pytest: failures are ERROR lines and leave the session's exit status alone (the tests' verdict is the tests').
- **`--no-suite-update` is a flag beside `--publish-baselines`** on both entry points and `harness.no_suite_update` in the run config, refused without the publish flag (a no-op flag is a misconfiguration).
- **CECE `develop`, now.** Every occurrence from audit fact 5 becomes `ufs-community/CECE` + `develop`; `benkozi/CECE` remains the user's fork for PRs and the harness needs nothing from it.
- **Credentials remain the CLI's** (no `profile` setting, no `AWS_*` in the harness): `AWS_PROFILE=<profile> uv run ufs-chem-assay publish-baselines …`. Missing or expired credentials fail the probe of the first baseline with the CLI's own message; nothing has been written at that point.

### 1. `src/baselines.py` — the module (generic; imports `s3_sync`, `logs`, `models.base`, `report`, `applications.base`)

```python
BASELINE_MANIFEST = "baseline.yaml"
COMPARISON_TEST = "test_baseline_comparison"   # excluded from the gate
DRIVER_TEST = "test_driver_execution"           # must have passed

class BaselineFile(StrictModel):            # frozen
    path: str = Field(description="Path relative to the baseline directory (posix; subdirectories such as plots-overview/)")
    bytes: int = Field(description="Size on disk at publication")
    sha256: str = Field(description="SHA-256 (lowercase hex) at publication")

class BaselineParameter(StrictModel):       # frozen; one combos.csv row
    target: str; field: str; value: str; swept: bool   # each with a description

class BaselineManifest(StrictModel):        # frozen; baseline.yaml
    ulid: str                      # == the combination's combo_id and the store key
    store: str                     # the s3://bucket/prefix it was published to
    application: str
    application_commit: str        # run.yaml's; publication refuses a null
    suite: str
    combo: str                     # canonical combination name
    run_id: str
    harness_version: str
    harness_commit: str | None
    platform: Platform; runtime: Runtime   # run.yaml's enums
    published_at: datetime         # UTC, timezone-aware
    published_by: str              # "<user>@<hostname>"
    superseded_ulid: str | None    # the entry's previous ulid; null when the suite was not updated or had none
    parameters: list[BaselineParameter]   # the combination's effective-parameter rows (combos.csv)
    files: list[BaselineFile]             # every file under the combination directory (the manifest itself excepted), sorted by path

Action = Literal["published", "would-publish", "skipped", "failed"]

class SuiteInput(StrictModel):              # frozen; one selected suite as the run executed it
    path: Path                              # the suite file (the edit target)
    suite: InstanceOf[SuiteConfig]
    baselines: dict[str, InstanceOf[BaselineComparison]]   # combination name -> entry (the session's resolution)
    combo_ids: dict[str, str]               # combination name -> the run's combo_id (the directory name)

class PublishRecord(StrictModel):           # frozen; one per baseline_comparisons entry
    suite: str; suite_path: Path; combo: str; ulid: str; previous_ulid: str
    source_dir: Path; store: str            # destination is f"{store}/{ulid}/"
    action: Action
    detail: str                            # gate verdict, "already published", the probe's finding, the error, ...
    suite_updated: bool

def publishable(rows: Sequence[TestReportRow]) -> tuple[bool, str]:
    """(ok, reason): DRIVER_TEST passed and nothing but COMPARISON_TEST failed; no rows -> not ok."""

def plan(run: RunManifest, suites: Sequence[SuiteInput], rows: Sequence[TestReportRow],
         output_root: Path, store: str) -> list[PublishRecord]:
    """Pure, in memory (both entry points): one record per entry, action 'would-publish', 'skipped'
    (gate, already pinned, no NetCDF) or 'failed' (null application_commit, directory missing)."""

def load_run(output_root: Path, app: Application, suites: Sequence[tuple[Path, SuiteConfig]]
             ) -> tuple[RunManifest, list[SuiteInput], list[TestReportRow]]:
    """The CLI's way to the plan's inputs: run.yaml, test-report.csv, and — per loaded suite —
    a re-enumeration against its base config, the entries resolved with
    comparison.resolve_baseline_comparisons, and combination names joined to combos.csv for the ids."""

def publish(records: Sequence[PublishRecord], *, run: RunManifest, output_root: Path,
            baseline_root: Path | None, dry_run: bool, suite_update: bool) -> list[PublishRecord]:
    """For each 'would-publish' record, in order: local manifest, probe, manifest write, sync, cache
    copy, suite edit — or, under dry_run, the probe and a --dryrun sync only. Reads combos.csv for the
    manifest's parameters. Never raises for one baseline's failure."""

def rewrite_suite_ulid(path: Path, old: str, new: str) -> None:
    """Textual: exactly one `ulid: <old>` line becomes `ulid: <new>`; reload check (section 4)."""
```

`load_run` (CLI only) reads `run.yaml` through `RunManifest` (its `_dispatch_suites` validator round-trips each recorded suite through its adapter), checks that the loaded suite files agree with the recorded suites by name and that their `baseline_comparisons` are equal to the recorded ones (a suite edited since the run — a selector changed, an entry added or removed — is an error naming the suite, not a wrong upload), re-enumerates each loaded suite's combinations against its base config (fresh ULIDs, but the canonical *names* are the run's), resolves the entries with `comparison.resolve_baseline_comparisons`, and joins each resolved name to `combos.csv` (`suite`, `name` → `combo_id`); a name absent from `combos.csv` is the same error. The session (section 5) builds `SuiteInput`s straight from its contexts and skips all of that.

`plan`, per entry: a null `application_commit` → every record `failed` ("run has no application commit"); the gate over the rows of that combination (`publishable`) → `skipped` with the reason; the suite already pinning this run's ULID → `skipped` ("already published"); `<output_root>/<combo_id>/` absent → `failed` ("combination directory missing"); no `*.nc` at its top level → `skipped` ("no NetCDF output: nothing to compare against" — a directory of logs alone is not a baseline, whatever else it holds); otherwise `would-publish`.

`publish`, per `would-publish` record: (1) **local manifest** — `<source_dir>/baseline.yaml` absent → a fresh publish; present and naming this `ulid` and this `store` → a **resume** (a previous attempt got at least as far as writing it); present with any other content → `failed` ("directory carries a manifest for <ulid> at <store>"; only a hand copy can produce this); (2) **probe** — `sync(S3SyncConfig(source=f"{store}/{ulid}/", destination=<empty tmp dir>, dry_run=True))`; a `(dryrun) download:` line means the prefix is occupied: fresh → `failed` ("prefix already holds objects; the store is append-only"), resume → the upload is skipped ("already in the store") and the steps continue; (3) **manifest write** (fresh only) — built from the run, the record, and the combination's `combos.csv` rows, digests over every file under the directory (`rglob`, the manifest itself excluded), written to `<source_dir>/baseline.yaml`; under dry run rendered to the log at INFO, not written; (4) **sync** (unless skipped) — `S3SyncConfig(source=source_dir, destination=f"{store}/{ulid}/", only_show_errors=not dry_run, dry_run=dry_run)`, no filters: the directory as it stands; nonzero → `failed` with the wrapper's output tail (the manifest stays in the directory, which is what makes the next run a resume — and the sync is reentrant, so a partial upload completes); (5) **cache** — when `baseline_root` is set and not dry run: `shutil.copytree(source_dir, baseline_root / ulid)`; an existing directory is left alone (a WARNING on a fresh publish, expected on a resume); a failure here is logged and the record stays `published`; (6) **suite** — when `suite_update` and not dry run: `rewrite_suite_ulid(suite_path, previous_ulid, ulid)`, `suite_updated=True`; its failure is logged with the ULID and the record stays `published`. Logging: one INFO line per record with the action and detail; ERROR for `failed`; the summary counts at the end (as `fetch` does).

Typing: no `Any`; `datetime` serialised ISO-8601 by pydantic (`mode="json"`); the manifest is written with `yaml.safe_dump(..., sort_keys=False)` of the JSON-mode dump — the manifest is output only, like `run.yaml`.

### 2. CLI — `cli/main.py`

```
ufs-chem-assay publish-baselines --output-root PATH
    [--application NAME] [--suite-config SELECTOR] [--store s3://bucket/prefix]
    [--dry-run] [--no-suite-update]
```

- `--output-root`: a host path to the directory holding `run.yaml` (the run config's `harness.output_root` is checkout-relative — the user passes `<checkout>/ufs-chem-assay-output`; under the docker runtime the host path, never `/work`). Missing `run.yaml` → one ERROR, exit 1.
- `--suite-config`: the same selector as `fetch` and pytest, resolved with `selection.resolve_suites` under the same settings, **defaulting to the run's suites**: a regex built from `run.yaml`'s suite names, `(?:simple-maccity)-suite\.yaml` (names `re.escape`d, joined with `|`), relying on the `X-suite.yaml` convention; the loaded names must equal the recorded names — otherwise the error names the missing ones and `--suite-config`. `--application` as for `fetch` (the flag beats `ASSAY_APPLICATION`; `run.yaml`'s `application` must agree).
- `--store`: overrides `Settings.baseline_store` for this call (same validation).
- `--no-suite-update`: `publish(..., suite_update=False)`.
- `--dry-run`: `publish(..., dry_run=True)` — the probe runs (it needs credentials, like the real thing), the wrapper's `--dryrun` lists each file it would upload, the manifest is logged, no file is written, no suite edited, no cache copied.
- Exit status: 1 when any record is `failed`, else 0 (`skipped` is reported, not fatal — a gated-out combination is already a red test). Summary line: `publish summary: 3 published, 0 skipped, 0 failed`.
- Settings come from the environment and `.env` as everywhere; `ASSAY_BASELINE_ROOT_DIR` decides the cache copy. No `root_dir` requirement: publication reads the output root and the suite files only (a `${CECE_ROOT_DIR}`-anchored suite still needs the root to load, as today).

Added to `SETTINGS_NOT_MIRRORED` as `"baseline_store",  # baselines.store`.

- `HarnessSection.publish_baselines: bool = Field(False, description="Pass --publish-baselines: publish the suites' compared combinations at session end and repoint the suites")`, `HarnessSection.no_suite_update: bool = Field(False, description="Pass --no-suite-update (with publish_baselines)")`; a model validator refuses `no_suite_update` without `publish_baselines`; `_harness` appends the flags after `--dry-run`. ### 4. Rewriting the suite file — `baselines.rewrite_suite_ulid`

Textual, because the files are commented and `yamlfix`-formatted (audit fact 4): the line pattern `^(\s*(?:-\s+)?ulid:\s*)(<old>)(\s*(?:#.*)?)$` (multiline, `<old>` escaped) must match **exactly once** — zero matches: the entry was edited since the run (error naming the file); two or more: two entries pin the same ULID (allowed by the model; the substitution would be ambiguous — error asking for a hand edit). The replacement keeps indentation, spacing, and any trailing comment. After writing, the file is reloaded through `applications.registry.load_suite` and must equal the previous model with that one entry's `ulid` changed (`model_dump()` equality after patching the old dump) — any other difference restores the original text and raises. `yamlfix` sees no change it would object to (a 26-character value for a 26-character value).

### 5. The pytest session — `src/tests/conftest.py`

- Options: `--publish-baselines` (flag) and `--no-suite-update` (flag; a `UsageError` at sessionstart without the former). `--dry-run` with `--publish-baselines` is allowed and publishes nothing (every combination's driver test skipped — the gate), with one INFO line saying so.
- `SuiteContext` gains `path: Path` (the suite file, from `resolve_suites`), so the session can edit the right file.
- `pytest_sessionfinish`, right after `write_test_report_csv`: when the flag is set, build one `SuiteInput` per context (`path`, `suite`, `context.baselines` as resolved at session start, `{combo.name: combo.combo_id}` from `context.combos`), re-read the `run.yaml` just written (one `RunManifest` path for both entry points), take the rows from `_REPORT_ROWS`, call `plan(...)` with `settings.baseline_store`, then `publish(...)` with `settings.baseline_root_dir`, `suite_update=not no_suite_update`, `dry_run=False`. Wrapped so that no exception escapes the hook (ERROR line; the session's exit status is the tests'). `enable_baseline_comparisons=False` does **not** block publication (publishing is how a store gets its first baselines; comparisons being off is about reading) — but it is logged, since the gate then never saw a comparison.

### 9. Edge cases and guards (consistency scan)

- **Two entries pinning the same ULID**: not refused by the model; `rewrite_suite_ulid` sees two matches and refuses (hand edit), after the upload — the baseline is in the store and the ULID logged.
- **The same output root published twice**: every record `skipped` ("already published": the suite pins this ULID); zero network.
- **A suite edited between the run and the publish** (a selector changed, an entry added): `load_run`'s equality check of the entries against `run.yaml` refuses the whole suite — the run no longer describes the file. An entry whose *ulid alone* changed (the user already repointed by hand) also fails the check; the message says what differs.
- **Multi-suite output roots**: records per suite; each suite file is edited independently; a failure in one suite's entry does not block another's.
- **A comprehensive run** (several applications) has one output root per application under `<output_root>/<application>`; the post-hoc command is run once per root, the session path publishes per session. Nothing spans applications.
- **A combination directory deleted after the run**: `failed` ("combination directory missing") — the run says it ran; the gate is checked first, so a gated-out combination's missing directory is just `skipped`.
- **A suite reverted after a publish** (`git checkout` of the suite, same output root, publish again): the directory's manifest names the ULID and store, the probe finds the prefix occupied → resume: no upload, the suite is repointed again. The same mechanism retries a failed suite edit and completes a partial upload.
- **A combination that failed its driver run**: `skipped` with the gate's reason; the previous ULID stays in the suite, so the old baseline keeps being compared against (honest red, as today).
- **`--publish-baselines` with `-k` or `--maxfail`**: combinations whose tests did not run have no `test_driver_execution` row → gate fails → `skipped` ("driver test did not run"); nothing from a partial session is published by accident.
- **A null `application_commit`** (checkout-less session): refused; the manifest's commit is the point of the issue's bullet.
- **The output directory contains a `baseline.yaml`**: naming this ULID and store → resume (above); anything else → `failed`, since only a hand copy of another combination's directory can produce it.
- **The probe needs `s3:ListBucket`**: a `--dryrun` download lists the prefix; an identity without it fails the probe rather than the upload — the policy for publishing is `s3:ListBucket` on the bucket plus `s3:PutObject` under `baselines/*` (no delete right is needed, by design).
- **Expired SSO**: the probe fails with the CLI's `ExpiredToken`; nothing written; `aws sso login` and rerun.
- **`aws` not on `PATH`**: `FileNotFoundError` from the wrapper at the first probe, with the README's install hint; nothing written.
- **The cache copy when `ASSAY_BASELINE_ROOT_DIR` is unset**: nothing local; a WARNING that the next local run needs the directory (or the download half); the Dropbox store on this Mac is set in `.env`, so the local use case primes it.
- **Dry run and credentials**: the dry run probes and `--dryrun`-syncs, so it needs credentials; a credential-less dry run fails like the real command would — a plan that silently skips the network would promise what the real run cannot do.
- **The manifest written, the sync failed, the user re-runs**: a resume; the manifest is not rewritten, so `published_at` is the first attempt's — accepted (the file list and digests are what matter, and they did not change). If the directory *did* change in between (a file added by hand), the uploaded set and the manifest disagree; nothing checks this today — the download half's integrity check (Future work) would catch it.
- **Timezone**: `published_at` is `datetime.now(timezone.utc)`; the string in YAML ends in `+00:00`.
- **Size**: a maccity combination directory is a few MB (three 47 KB NetCDF files, the PNG plots and GIFs, small text files); the exhaustive suites have no entries. No copy is made for the upload; the cache `copytree` is the only duplication and only when the cache is configured. An application whose combination directories grow large gets the `exclude` key (section 6) when that day comes.
- **Whole-directory download later**: the download half syncs `<store>/<ulid>/` back as a directory, plots included, so a cached baseline looks exactly like the published one — and the comparison keeps reading its top-level `*.nc` only.
- **A `.sbatch` job script, the `.out`, and `cece.log` carry host paths** (the output root, the checkout): informative, not secret, in a private bucket. Noted so no one is surprised reading a manifest.
- **`yamlfix` under pre-commit** on the rewritten suite: unchanged line shapes, so the hook is a no-op; the reload check runs regardless.

## Risks and notes

- **`atol: 0.0` across machines.** The republished baselines come from this Mac (the `cece/cece-dev` image under `linux/arm64`); CI runs the same image on `x86_64`. Bit-for-bit agreement between the two is plausible for this three-hour, single-species run but not guaranteed; the day CI compares (Future work, credentials), a per-entry `atol` in the suite is the documented knob. Nothing in this change decides it (Open questions).
- **A dirty application checkout publishes a non-reproducible commit** (audit fact 11): `application_commit` is the SHA alone. Mitigation now: the runbook and README say to publish from a clean checkout; a `-dirty` marker on the application side (and a refusal to publish from one) is cheap future work.
- **The store is append-only and the harness never deletes**: abandoned prefixes (a publish whose suite edit failed and was never retried, or republishes no one commits) accumulate at a few MB each here (whole directories, plots included) — negligible at this scale, and the `exclude` key (section 6) exists for the day a combination directory is not; the manifest makes each self-describing, and removal is a human decision outside the harness, as decided on 2026-10-07.
- **The suite edit lands in the working tree uncommitted.** That is the point (the user commits the repoint with a message naming the driver change), but an in-session publish on Ursa edits the harness checkout there; the runbook says so.
- **The probe is one extra `aws` call per baseline** (a `--dryrun` listing): seconds, and the only way to enforce append-only without a list verb. Acceptable; a `s3 ls`-based check would add a second verb to the wrapper for no gain.
- **Publishing from a `-k`-narrowed session** is prevented by the gate (no driver row → skipped), which also means a user who *meant* to publish one combination cannot — they publish the whole suite's compared set or nothing. A `--combo NAME` filter is easy to add if wanted (Future work).
- **The default selector relies on the `X-suite.yaml` convention** for the post-hoc path; a suite whose file name breaks the convention needs an explicit `--suite-config` — the error says so.
- **The flip to `ufs-community/CECE@develop` moves the integration job's build cache key** (new SHA): one cold build (~4 min) on the first run, incremental thereafter.
