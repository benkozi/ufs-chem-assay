# Feature: asynchronous Ursa runs — one `config/ursa.yaml`, one `run` call, every Ursa suite as its own session; pytest submits the jobs, `ufs-chem-assay watch` evaluates them when they finish

Refined 2026-11-04 from the seven requirement bullets in the appendix (the user's notes of the same morning, after the gcafs-anthro use case landed in `0.1.0-rc.9`). Today a run config names one suite selector and one job geometry, the harness stage blocks on the login node for as long as the longest driver job (hours for gcafs-anthro, under `tmux`), and running the two Ursa configurations means two run configs that differ in six keys. This change makes a run config carry **several named sessions** — each one pytest session, with its own output root and job geometry; makes the slurm runtime **submit every job up front and poll** instead of `sbatch --wait` one at a time; splits a session into a short **submit** half and a **resume** half that evaluates finished jobs; and adds **`ufs-chem-assay watch`**, the loop that notices finished sessions and evaluates them one after another. Publishing, benchmark recording and output upload keep running at the end of the (resume) session, so nothing about them changes except that two sessions may now reach the committed files at once — which gets a lock.

## Goal

From a login node, one command submits every Ursa configuration and returns within minutes; a second command, re-runnable at any time, finishes the work as jobs complete:

```bash
cd $ROOT/ufs-chem-assay
uv run ufs-chem-assay run --config-file=config/ursa.yaml            # source, build, data, then submits every configured session
uv run ufs-chem-assay watch                                          # polls Slurm; evaluates each session when its jobs are done
```

1. **`config/ursa.yaml` holds every Ursa session** under a new `sessions:` map — `simple-maccity` and `gcafs-anthro` as shipped, `exhaustive-maccity` as a commented third entry — each a small overlay on the file's `harness:`, `slurm:` and `baselines:` sections (the six keys gcafs-anthro changes today, nothing else). `config/ursa-gcafs-anthro.yaml` is retired; `--session NAME` (repeatable) narrows a `run` or `watch` to some sessions, exactly as `--application` narrows applications. Nothing is renamed: the requirement's `config/ursa-simple-maccity.yaml` is answered by the merge (Decision 2).
2. **Every session has its own output root**, `<output_root>/<session>` (`<output_root>/<application>/<session>` in a multi-application config), its own `run.yaml`, `run_id`, `benchmarks.csv`, plots, upload — one session's artifacts, unchanged in shape.
3. **The slurm runtime submits all of a session's jobs at once** (`sbatch --parsable`, no `--wait`), records them in **`<output root>/jobs.yaml`** (the job ledger), and each combination's `driver_run` waits for *its* job by polling `squeue`, taking the verdict from `sacct`. A session's wall time becomes the longest job plus its queue wait, not the sum.
4. **`pytest --submit-only`** stops after the ledger is written (every test skips with the job id); **`pytest --resume --combo-output-root <root>`** opens an existing root, adopts its `run_id` and combination ids from the ledger, waits for whatever is still running, and runs every test and the whole session-end pipeline (benchmarks, publish, plots, upload) over the finished jobs. Without either flag a session submits, waits and evaluates in one go — the shape every runtime has today, concurrent under slurm.
5. **`ufs-chem-assay watch`** reads the effective config `run` wrote, polls every selected session's ledger against `squeue` every `--interval` seconds, and when a session's jobs have all left the queue executes that session's rendered resume script (`06-resume-<application>-<session>.sh`) — one session at a time, so the committed files are written serially — until every selected session is evaluated. `ufs-chem-assay cancel --output-root <root>` scancels a session's live jobs; `clean_root` refuses to remove a root with live jobs.
6. **The committed files take a lock**: `append_benchmarks` and the suite-file repoint hold an exclusive `flock` on the file they rewrite, so two sessions ending at once (a `simple-maccity` session and an uncommented `exhaustive-maccity` one share `cece/maccity/benchmarks.csv`; two `watch` processes; a hand-run `--stage resume` beside `watch`) cannot interleave. `publish-baselines`, `record-benchmarks`, `upload-output` and their session flags are otherwise unchanged: they run at the end of the resume session, on the login node, with network.

## Pre-design audit (fresh facts, 2026-11-04)

Verified on `feature/async-runs` at `bef691a` (`0.1.0-rc.9`).

1. **The two Ursa templates differ in six keys.** `config/ursa.yaml` and `config/ursa-gcafs-anthro.yaml` are identical in `applications:`, `data:`, `baselines:`, `outputs:`, `uv:`, and in every `harness:`/`slurm:` key except `harness.suite_config` (`simple-maccity-suite.yaml` / `gcafs-anthro-suite.yaml`), `harness.run_timeout_s` (300 / 28800), `harness.env` (the two MPI hints / the same two plus seven single-thread variables), `slurm.cpus` (8 / 1), `slurm.srun_args` ('' / `--cpu-bind=cores`) and `slurm.extra_args` ('' / `--mem=0`). `slurm.qos` is `debug` in both (gcafs-anthro's comment says `batch` once `timeout_s` grows). Everything else — some 50 keys — is boilerplate duplicated by hand, with comments that already drift ("What differs from config/ursa.yaml is commented at each key").
2. **A session already runs several suites, but as one session.** `--suite-config` is a regex; every match loads into one session over one flat output root (`conftest.pytest_sessionstart`, `selection.resolve_suites`), with one `run_id`, one `ASSAY_SBATCH_ARGS`, one `ASSAY_JOB_ENV`, one `run_timeout_s` cap. gcafs-anthro and maccity need different geometries (fact 1), so "all Ursa suites" cannot be one session; it has to be several, which is what the requirement's "each run its own output directory" says too.
3. **The slurm runtime is synchronous per combination.** `runner._run_slurm_job` runs `sbatch --wait --parsable <script>` in a `Popen`, reads the job id from the first line, and `process.wait(timeout=timeout_s + slurm_queue_wait_s)`; on expiry it `scancel`s and raises `SlurmJobTimeout`. `driver_run` is a session-scoped fixture parametrized per (suite, combo), so pytest runs combo 1's job to completion (and its tests) before submitting combo 2's. Ursa queue waits are paid once per combination, serially. The job script is already written up front for every combination in `generated_combos` (dry runs included), so submission-in-bulk has its input ready.
4. **The job's verdict comes from `sbatch --wait`'s exit code**; `sacct` is consulted afterwards only for the benchmark columns (`benchmarks.slurm_accounting`, retried once, `ACCOUNTING[Platform.URSA] is Accounting.SACCT`). `parse_sacct` already yields `state` and `exit_code`, which is what an asynchronous wait needs for the verdict. `squeue` is not used anywhere yet.
5. **The CLI runs stage scripts strictly in sequence** (`cli/main._run`: render everything, then `run_bash` each path, stop at the first nonzero), one harness script per application (`05-harness-<application>.sh`, `_INDEX` reserves 04). `run_bash` streams the script's output to stdout and `<root_dir>/logs/<script>-<stamp>.log`. The README and runbook tell the user to run the harness stage under `tmux` because it lives as long as the suite.
6. **Session identity is minted, never read.** `run_id = str(ULID())` at sessionstart; `combo_id = str(ULID())` in `enumerate_combos`; `Combo` is a frozen dataclass (`values`, `combo_id`) whose `name` is canonical and deterministic. `baselines.plan.load_run` already re-enumerates a finished run and joins fresh combos to the run's ids by canonical name through `combos.csv` — the same join a resumed session needs, which means adopting recorded ids is an established pattern, not a new idea.
7. **The session-end pipeline is one function** (`pytest_sessionfinish`): test report → benchmarks (per-run file, per-combo file, `--record-benchmarks` append) → `--publish-baselines` → stats concat and overview plots → comparison concat and bias plots → `--upload-output`. Every step reads only the output root and the stash; nothing in it depends on *when* the jobs ran, only on the `.out`, the NetCDF, and the accounting. It is reusable as-is by a session that merely waited for jobs someone else submitted.
8. **The committed files are rewritten whole.** `benchmarks.append_benchmarks` reads the file, appends the new rows, writes the text back, reloads to validate, and restores the original on failure — read-modify-write with no lock. `baselines.suite.rewrite_suite_ulid` (via `publish._repoint`) and `staging.rewrite_suite_digests` rewrite a suite file in place. Two sessions appending to `src/tests/config/cece/maccity/benchmarks.csv` within the same second (two sessions that record to the same file ending together) would race; today that cannot happen because sessions are serial.
9. **Settings and run config mirror each other** (`cli/stages.settings_mirror_fields`, `SETTINGS_NOT_MIRRORED`, `test_templates_list_every_accepted_key`): a new setting needs its env var, its `harness:`/`slurm:` key, its export line, and a line in every template. `test_user_docs.test_templates_live_in_config` pins the template list to exactly `local.yaml`, `ursa-gcafs-anthro.yaml`, `ursa.yaml`; `test_gcafs_anthro_runbook_covers_the_use_case` pins the gcafs-anthro runbook to its own config file name. Both change with this design.
10. **`--combo-clean-root` removes a previous root wholesale** (`shutil.rmtree` after the `run.yaml` check). Once jobs outlive the session that submitted them, a second `run` could delete the directory their `.out` files are being written into.

## Design

### 0. Decisions

1. **A run config describes several sessions; a session is a named overlay.** `sessions:` is a top-level map, session name → `{harness: {…}, slurm: {…}, baselines: {…}}`, each key an override of the same-named top-level section. The base sections stay the complete surface (every key, as the mirror test demands); an overlay names only what differs. Overlays are one level deep: a key in an overlay replaces the base key's whole value (`env` is replaced, not merged — a session that wants the MPI hints restates them). No `sessions:` means one implicit, nameless session with today's paths and script names, so `config/local.yaml`, CI, and every existing command are untouched.
2. **One Ursa template, no rename.** `config/ursa.yaml` gains `sessions:` with `simple-maccity` and `gcafs-anthro` enabled and `exhaustive-maccity` as a commented entry; `config/ursa-gcafs-anthro.yaml` is deleted. The requirement's `config/ursa-simple-maccity.yaml` would have been a third file of the same boilerplate; `--session simple-maccity` is the selector it was going to be. Confirmed by the user (Open questions 1 and 2). A different *set* of sessions for a different purpose — a benchmarking sweep, a release check — is a second run config with its own `sessions:` map over the same base, selected by `--config-file`; within one file, `--session` selects.
3. **Each configured session is one pytest session with its own output root**, `<output_root>/<session>`. Two entries cannot share a pytest session because they differ in exports (`ASSAY_SBATCH_ARGS`, `ASSAY_JOB_ENV`, `ASSAY_RUN_TIMEOUT_S`) that are read once per session. Everything a session writes — `run.yaml`, `combos.csv`, `benchmarks.csv`, the combination directories, `upload.yaml` — stays per root, so publish, record, upload and download work per session with no change (Goal 6).
4. **Submit everything, then wait, by polling.** The slurm runtime stops using `sbatch --wait`. A session submits every combination's job script in enumeration order as soon as the scripts exist, records the **job ledger** `jobs.yaml`, and `driver_run` waits for its own job: `squeue` says whether the job is still in the queue, `sacct` says how it ended. One mechanism serves the single-session shape and the resumed shape alike (a resumed session cannot reattach to a `Popen`; polling needs only the job id). `--wait`'s exit code is replaced by `sacct`'s `ExitCode`/`State`, which the benchmark columns already read.
5. **Two halves of one session, two flags.** `--submit-only` ends the session once the ledger is complete (every combo test skips, naming the job); `--resume` opens an existing root and evaluates it. The run config's `harness.submit_only: true` (the Ursa template) renders the harness stage with `--submit-only` and a sixth stage, **`resume`**, with `--resume`; `false` (local, CI) renders today's single script. `run` never executes the resume stage unless asked (`--stage resume`); `watch` does. pytest stays the only place test logic lives: the resume session *is* the ordinary session minus submission.
6. **`watch` is the monitor loop, and it is dumb on purpose.** It reads the effective config, the ledgers and `squeue`; it runs the resume scripts `run` already rendered, serially, logging to `<root_dir>/logs/`; it is safe to kill and restart (a session already evaluated is skipped by its ledger's `evaluated_at`). It owns no test logic and no Slurm semantics beyond "is this job still queued".
7. **Concurrent writers get a lock, and `watch` serializes anyway.** `append_benchmarks` and the suite repoint take an exclusive `fcntl.flock` on the file they rewrite for the duration of the read-modify-write. The lock covers the case `watch` cannot (two sessions run by hand, or two `watch` processes); `watch`'s serial evaluation covers the case the lock cannot (a filesystem without working `flock`, Risks).
8. **Ids are adopted, never re-minted, on resume.** The resumed session takes `run_id` from `run.yaml` and each combination's `combo_id` from the ledger by (suite, canonical name); the selected suites must be exactly the recorded ones and the enumerated combinations exactly the ledger's, else a usage error naming the difference. `run.yaml`, `combos.csv`, the generated configs and the job scripts are the submit session's and are never rewritten by resume.
9. **A live root is protected.** `clean_root` (pytest's `--combo-clean-root`) refuses a root whose ledger lists a job still in `squeue`, naming `ufs-chem-assay cancel --output-root …`. `cancel` is the only thing that scancels on purpose; the per-job deadline is the only thing that scancels automatically (unchanged).
10. **No `tmux` requirement remains, and the runbook says so.** With `submit_only`, the harness stage returns in minutes; `watch` is cheap, idle between polls, and restartable, so dropping an SSH connection loses nothing. `tmux` becomes a convenience for watching, not a requirement for correctness.

### 1. The run config — `cli/run_config.py`

```yaml
sessions:  # one pytest session per entry, each under <output_root>/<session>; an entry overlays harness:/slurm:/baselines: above, one level deep
  simple-maccity: {}  # the base sections as written: simple-maccity-suite.yaml, 8 cores, debug
  gcafs-anthro:
    harness:
      suite_config: gcafs-anthro-suite.yaml
      run_timeout_s: 28800  # the batch cap: the suite's own timeout_s (1800 = --time=30 for now) is the job limit
      env:  # replaces harness.env: the MPI hints again, then the single-thread geometry
        I_MPI_FABRICS: shm
        FI_PROVIDER: tcp
        OMP_NUM_THREADS: 1
        OMP_PROC_BIND: spread
        OMP_PLACES: threads
        KOKKOS_NUM_THREADS: 1
        MKL_NUM_THREADS: 1
        OPENBLAS_NUM_THREADS: 1
        OPENBLAS_DEFAULT_NUM_THREADS: 1
    slurm:
      cpus: 1  # one core per task …
      srun_args: --cpu-bind=cores  # … bound
      extra_args: --mem=0  # the whole node's memory
  # exhaustive-maccity:  # a third session, documented but not shipped enabled — uncomment to run both exhaustive suites
  #   harness:
  #     suite_config: exhaustive-maccity-.*-suite.yaml  # both exhaustive suites, one session
  #   slurm:
  #     qos: batch  # 8 h; the debug QOS is 30 min
  #     queue_wait_s: 14400  # batch waits can be hours, and every job is submitted at once
```

- **`SessionOverlay(StrictModel)`**: `harness: dict[str, object]`, `slurm: dict[str, object]`, `baselines: dict[str, object]`, each `Field(default_factory=dict, description=…)`. `extra="forbid"`: a session may overlay only these three sections (`applications:`, `data:`, `outputs:`, `uv:` are run-wide: the checkout, the inputs, the store, the cache are the same whichever suite runs).
- **`RunConfig.sessions: dict[str, SessionOverlay] = Field(default_factory=dict, description=…)`**. Keys match `^[a-z0-9][a-z0-9-]*$` (they become directory and script names; a validator says so). An empty map is the same as an absent one.
- **`ResolvedSession(StrictModel)`**: `name: str | None`, `harness: HarnessSection`, `slurm: SlurmSection | None`, `baselines: BaselinesSection`. **`RunConfig.resolved_sessions() -> list[ResolvedSession]`**: without `sessions:`, one entry with `name=None` and the base sections; with it, one per key in file order, each section built as `Section.model_validate(base.model_dump() | overlay)` — so an unknown overlay key, a wrong type, or `no_suite_update` without `publish_baselines` fail with the usual pydantic message, prefixed `sessions.<name>.<section>:`. An overlay on `slurm:` when the base has none is a `ValueError` ("session X overlays slurm: but the config has no slurm: section"). A model validator resolves every session once at load so a bad overlay fails `from_yaml`, not the harness stage.
- **`--override sessions:gcafs-anthro:slurm:ntasks=4`** needs no new code: `apply_overrides` works on the raw mapping before validation, and the overlay is a mapping. The effective `run-config.yaml` dumps `sessions:` as validated.
- **Properties**: `session_names`, and `session_output_root(app, session)` replacing `cli/stages.application_output_root`: `<output_root>` / `<output_root>/<application>` / `<output_root>/<session>` / `<output_root>/<application>/<session>` by what the config has. `config.runtime` stays config-wide (`harness.runtime` is not overlayable: the platform's runtime is one thing).
- **`HarnessSection.submit_only: bool = Field(default=False, description="Pass --submit-only: the session submits every driver job, writes jobs.yaml and stops; ufs-chem-assay watch (or --stage resume) evaluates it later. Slurm runtime only")`**. Validator: `submit_only` with `pytest_dry_run` is fine (the dry run skips before submission); `submit_only` under a non-slurm runtime is an error at `from_yaml` ("submit_only needs the slurm runtime; <platform> runs <runtime>").
- **`SlurmSection.poll_s: int = Field(default=30, gt=0, description="ASSAY_SLURM_POLL_S: seconds between squeue polls while a job is queued or running")`**, exported like `queue_wait_s`; `SETTINGS_NOT_MIRRORED` gains `slurm_poll_s`.

### 2. Stages — `cli/stages.py`, `cli/main.py`

- **`Stage.RESUME = "resume"`** (`applications/base.py`, after `HARNESS`; shared like `data` and `harness`, so no adapter changes). `_INDEX[Stage.RESUME] = 6`. `_selected_stages(None)` returns every stage **but `resume`**: a plain `run` must not block on the evaluation it just deferred; `--stage resume` selects it explicitly (useful: a synchronous evaluation by hand, or a re-evaluation after a plotting fix). Requesting `resume` when `submit_only` is false is an error ("resume is rendered only with harness.submit_only: true").
- **Script names carry the session**: `ShellScript.name = f"{stage}-{app}"` today, `f"{stage}-{app}-{session}"` when the session is named — `05-harness-cece-gcafs-anthro.sh`, `06-resume-cece-gcafs-anthro.sh`; the nameless session keeps `05-harness-cece.sh` (the runbook test pins it).
- **`render_stage(stage, config, app, session, *, shared_data)`** takes the `ResolvedSession`. `_exports` reads `session.harness`, `session.slurm`, `session.baselines` instead of `config.harness` etc. (`ASSAY_RUN_TIMEOUT_S`, `ASSAY_SBATCH_ARGS`, `ASSAY_SRUN_ARGS`, `ASSAY_JOB_ENV`, `ASSAY_SLURM_QUEUE_WAIT_S`, `ASSAY_SLURM_POLL_S`, `ASSAY_ENABLE_BASELINE_COMPARISONS`, `ASSAY_BASELINE_ROOT_DIR`, `ASSAY_BASELINE_ATOL/RTOL` are the per-session ones; the rest are config-wide and render identically in every session's script).
- **The harness stage** (`_harness`): `--combo-output-root=<session_output_root>`; with `submit_only`, `--submit-only` is appended. **The resume stage** (`_resume`): the same exports, `cd`, and `uv run --no-sync pytest … --resume --combo-output-root=<same root>`, with every session flag the harness line has **except** `--combo-clean-root` and `--submit-only`, and never `--dry-run`. `--publish-baselines`, `--record-benchmarks`, `--upload-output`, `--no-suite-update`, `pytest_args` appear on **both** lines: the submit session performs the start-of-session probes (`check_reachable`, the usage-error pairings) so a misconfiguration fails before anything is submitted, then ignores the end-of-session actions with one INFO line ("deferred to --resume"); the resume session does them. `pytest_args` must be on both because `-k` decides which combinations exist in the session, and the two sessions must agree (Decision 8).
- **The data stage** (`_data`): one block per session — that session's exports, `cd`, `ufs-chem-assay fetch --application=<app> --suite-config=<session selector>` — deduplicated by (selector, baseline exports), then the adapter's data lines and the cartopy line once. `fetch` already pre-warms the pinned baselines under the session's baseline settings, so a session with `baselines.enabled` overlaid stages its own.
- **`run`**: `--session NAME` (`action="append"`, like `--application`); `_selected_sessions(config, requested)` errors on an unconfigured name. Render order stays stage-major, then application, then session: every source, every build, every data, every harness (one per application per session), and `resume` only if selected. Logging adds `sessions: a, b, c`.
- **Live-root guard**: before the harness stage's `--combo-clean-root` reaches pytest, nothing in the CLI checks the root; the check lives in the session (section 4) because `--combo-clean-root` is a pytest option a user can pass by hand too.

### 3. The job ledger and the asynchronous Slurm runtime — `src/jobs.py`, `runner.py`

**`src/jobs.py`** (new, generic; imports `logs`, `models.base`, `models.conventions`, `benchmarks.slurm_accounting`):

- **`SubmittedJob(StrictModel)`**: `suite: str`, `combo: str` (canonical name), `combo_id: str`, `job_id: str`, `script: Path` (the `.sbatch`), `out_path: Path`, `timeout_s: int`, `queue_wait_s: int`, `submitted_at: datetime` — every field described.
- **`JobLedger(StrictModel)`**: `run_id: str`, `application: str`, `submitted_by: str` (`user@host`), `jobs: list[SubmittedJob]`, `evaluated_at: datetime | None = None`, `exit_status: int | None = None` (pytest's session exit status, written by the evaluating session at sessionfinish). `CONVENTIONS.job_ledger = "jobs.yaml"`. `read_ledger(output_root)`, `write_ledger(ledger, output_root)` (`yaml.safe_dump`, keys in model order, written to `.jobs.yaml.tmp` and `os.replace`d so a reader never sees a partial file).
- **`submit_job(script: Path) -> str`**: `sbatch --parsable <script>`; the job id is the first `;`-separated field of stdout; a nonzero exit or an empty id raises `SlurmSubmissionError(CalledProcessError)` carrying sbatch's output.
- **`queue_states(job_ids) -> dict[str, str]`**: one `squeue -h -j <id,id,…> -o '%i %T'`; absent ids are not in the queue. `squeue`'s nonzero exit for an unknown id is treated as "not queued" (it prints to stderr and exits 1 when every id is gone), any other failure is logged and retried on the next poll.
- **`wait_for_job(job: SubmittedJob, *, poll_s: int, now: Callable[[], datetime] = …) -> SlurmAccounting`**: loop — if `job_id` is in `queue_states`: past the deadline (`submitted_at + timeout_s + queue_wait_s`) → `scancel`, raise `SlurmJobTimeout` (as today); otherwise sleep `poll_s`. Not queued → `slurm_accounting(job_id)` (the existing retry); `None` after the retry → `SlurmAccountingMissing` (a `RuntimeError` naming `sacct -j <id>`): the asynchronous wait cannot judge a job without accounting, and Ursa has it (`ACCOUNTING`). Returns the accounting; the caller judges it.
- **`cancel_jobs(ledger, *, dry_run) -> list[str]`**: `scancel` every ledger job still in `queue_states`; returns the ids.

**`runner.py`**: `_run_slurm_job` splits into **`submit_driver_job(settings, app_settings, driver_yaml, out_path, timeout_s) -> tuple[Path, str]`** (write the script — unchanged — then `jobs.submit_job`) and **`finish_driver_job(job: SubmittedJob, settings) -> DriverExecution`** (`wait_for_job`; read `out_path` — a job that never wrote leaves the `.out` missing: write sbatch's and sacct's words into it as today; print; `state` starting `TIMEOUT` or `CANCELLED` → `SlurmJobTimeout`-flavoured error, nonzero `exit_code` → `SlurmJobError(returncode, cmd, output, job_id)`; return `DriverExecution(job_id)`). `run_driver` keeps its signature for docker/native; the slurm branch is no longer reachable through it (the conftest calls the two halves), and `build_command`'s slurm case renders `sbatch --parsable <script>` (no `--wait`; the dry-run test that prints the command changes one word). `DriverExecution` gains `accounting: SlurmAccounting | None` so the conftest stops calling `slurm_accounting` a second time.

### 4. The pytest session — `src/tests/conftest.py`

Options: **`--submit-only`** ("slurm runtime: submit every combination's job, write jobs.yaml at the output root, and stop; every combo test skips naming its job id; evaluate later with --resume"), **`--resume`** ("open an existing output root (--combo-output-root, required): adopt its run_id and combination ids from jobs.yaml, wait for jobs still queued, run every test and the session-end pipeline"). Usage errors at sessionstart: either flag without the slurm runtime; both together; `--resume` with `--combo-clean-root`, with `--dry-run`, or without `--combo-output-root`; `--resume` on a root without `run.yaml` or `jobs.yaml`.

**Sessionstart, the live-root guard** (Decision 9): with `--combo-clean-root` and an existing root that has a ledger, `queue_states` over the ledger's ids; any still queued → usage error "output root X has N job(s) still in the Slurm queue (job ids …); wait for them (ufs-chem-assay watch) or cancel them (ufs-chem-assay cancel --output-root=X) before cleaning".

**Sessionstart under `--resume`**: `run_id` from `run.yaml` (`read_run`); the ledger read; the suites resolved from the selector as always and checked against `run.yaml`'s suite names exactly (the `publish-baselines` rule: "run X executed suite(s) … that the selection does not include"); combos enumerated as always, then **rebound**: for each context, each combo → `dataclasses.replace(combo, combo_id=ledger_id[(suite, combo.name)])`; a combo the ledger lacks, or a ledger entry no combo claims, is a usage error listing both sides (the suite file or `-k` changed since submission). `application_commit`: resolved as always; when it differs from `run.yaml`'s, one WARNING ("the checkout moved from X to Y since submission; the jobs ran the earlier build") — the row records what `run.yaml` says, because that is what ran. `_EXPLICIT_ROOTS` points at the existing root, nothing removed.

**`combo_roots` under `--resume`**: the root exists; `run.yaml` is **not** rewritten (Decision 8). **`generated_combos` under `--resume`**: no directories created, no configs or job scripts written, no `combos.csv`; `GeneratedCombo` is rebuilt in memory (`app.build_config` is deterministic; `driver_yaml` is the recorded name via `app.generated_config_path`) because `DriverRunResult.config` and the file-count assertion read it.

**A new session fixture `submitted_jobs: dict[str, SubmittedJob]`** (session-scoped, after `generated_combos`, slurm only; docker/native return `{}` and `driver_run` runs inline as today): under `--resume` the ledger's entries by `combo_id`; under `--dry-run` nothing (no ledger); otherwise every combination's job is submitted in enumeration order, the ledger rewritten after **each** submission (a failed submission mid-way leaves a truthful ledger and raises — the remaining combos' tests fail with the submission error, nothing is silently half-submitted). The stash gets `_LEDGER`.

**`driver_run` under slurm**: look up `submitted_jobs[combo_id]`; under `--submit-only` → `pytest.skip(f"submitted as Slurm job {job_id}; evaluate with --resume")`; otherwise `finish_driver_job`, the same `try/except` as today, `DriverRunResult` as today with **`duration_s = (accounting.end or now) - submitted_at`** (the field's description becomes "docker/native: the harness's clock around the call; slurm: submission to end, queue included"). The accounting rides in `execution.accounting` into `_ACCOUNTING`.

**Sessionfinish**: under `--submit-only` → log "N job(s) submitted for run <run_id>: jobs.yaml at <root>; evaluate with: ufs-chem-assay watch (or --stage resume)", write **no** `test-report.csv`/`benchmarks.csv` (there are no verdicts), return. Otherwise the pipeline runs unchanged, and under slurm the ledger is rewritten last with `evaluated_at` and `session.exitstatus` — after the upload, so an uploaded root carries a ledger that says "not yet evaluated" only if the session died before the end, which is the truth. `jobs.yaml` joins the "Results" tree in the README.

**Test reporting**: the resume session's `test-report.csv` is the run's; the submit session writes none, so no "all skipped" report ever shadows a real one. `--submit-only` with `--publish-baselines`/`--upload-output`: the start-of-session probes run, the actions are deferred with one INFO line (section 2).

### 5. `ufs-chem-assay watch` and `ufs-chem-assay cancel` — `cli/main.py`, `cli/watch.py`

- **`watch [--root-dir DIR] [--application NAME]… [--session NAME]… [--interval S] [--once]`**. The config is **`<root_dir>/scripts/run-config.yaml`**, the effective configuration the last `run` wrote (the file whose stated purpose is "re-runs the same configuration with no override list") — `watch` takes no `--config-file` and no `--override`, so the resume session's exports cannot drift from the submit session's. `--root-dir` defaults as `run`'s does; a missing effective config is an error naming `run`. `--interval` defaults to the config's `slurm.poll_s` (30 s).
- **Per tick**, for every selected (application, session): the output root (`session_output_root` resolved as the session resolves `--combo-output-root`: relative → under the checkout); no ledger → `not submitted`; a ledger → one `queue_states` call for all sessions' ids together, then counts: `queued` (PENDING, CONFIGURING…), `running`, `done` (not in the queue); `evaluated_at` → `evaluated (exit N)`. One INFO line per session per tick, e.g. `gcafs-anthro: 1 job(s): 0 queued, 0 running, 1 done; not evaluated`, and the tick's summary.
- **When a session has a ledger, no job in the queue and no `evaluated_at`**: run its resume script, `<root_dir>/scripts/06-resume-<app>[-<session>].sh`, through `run_bash` (its own timestamped log under `<root_dir>/logs/`), **one session at a time** in config order; a missing script is an error naming `run --dry-run` (which renders it). After it returns, re-read the ledger: `evaluated_at` set → done; not set (the session died) → reported `evaluation failed (exit N)` and left for the next `watch` (which will try again — a persistently failing resume is the user's to look at, and its log says why).
- **Ends** when every selected session is evaluated (exit 0 if every `exit_status` is 0, else 1 — pytest's own status, so a failed test is a nonzero `watch`), or after one tick with `--once` (exit 0; the report is the output). A session that is `not submitted` is waited for like a queued job — the loop has no way to know whether the harness stage is about to run it — and `--session` narrows what is waited for. SIGINT ends a tick cleanly; a resume session in flight is a child `bash` and inherits the signal, as any `run` stage does today.
- **`cancel --output-root PATH [--dry-run]`**: `read_ledger`, `cancel_jobs`; logs each id; a root without a ledger or with nothing queued is a no-op with a log line, exit 0. The resume session over a cancelled session finds `CANCELLED` in `sacct` and records every combination as failed/timeout, as a job killed by its limit is today.

### 6. The committed files under concurrency — `benchmarks.py`, `baselines/suite.py`, `staging.py`

- **`append_benchmarks`**: the whole read-modify-write runs under `fcntl.flock(fd, LOCK_EX)` on a descriptor opened on `repo_csv` itself in append mode (created empty when absent — the "absent" branch becomes "absent or empty", writing the header); the lock is released by closing after the reload check. No sidecar lock file, nothing new to gitignore. A small helper **`locked(path) -> ContextManager[None]`** in a new `src/fslock.py` (ten lines, `fcntl` only) so the suite rewriters share it.
- **`baselines.suite.rewrite_suite_ulid`** (what `publish._repoint` calls) and `staging.rewrite_suite_digests`, the only two suite-file rewriters: the same `locked(suite_path)` around read, edit, write.
- **Why both the lock and `watch`'s serialization** (Decision 7): `flock` on Lustre is honoured only on mounts with `flock`/`localflock`; if Ursa's scratch lacks it, the lock degrades to advisory-but-ineffective between nodes — and `watch` runs every resume on one node, serially, so the committed files are still written one session at a time in the supported workflow. The lock matters for two sessions started by hand on one node, which it fully covers.

### 7. Publish, record, upload in the asynchronous shape

Nothing changes in `baselines/`, `outputs.py`, or the three CLI subcommands: each works on one output root, and every session has one. What the design guarantees for them:

- They run **at the end of the resume session**, which `watch` runs on the login node (network), so `--publish-baselines` and `--upload-output` keep their fail-fast probes and their "run it afterwards from a node with network" fallbacks word for word.
- **Per-session uploads** land at `<store>/<run_id>/` — two sessions, two ULIDs, two prefixes; `download-output --ulid` brings one back. `upload.yaml` and `jobs.yaml` both travel with the root.
- **Two maccity sessions publishing** (`simple-maccity` and an uncommented `exhaustive-maccity`) repoint different suite files (`simple-maccity-suite.yaml`, the two exhaustive suites); two sessions of the *same* suite in one config is a configuration mistake the design does not prevent but the lock keeps consistent (the last publish wins the `ulid:` line, both baselines exist in the store).
- **`record-benchmarks`/`--record-benchmarks`** append under the lock; rows are keyed `(run_id, combo_id)`, both per session, so a re-run of a resume never duplicates.
- **A session evaluated twice** (`--stage resume` by hand after `watch`): the pipeline is idempotent — files rewritten, rows skipped as already recorded, a publish refused for a ULID the suite already pins, an upload resumed.

### 11. Edge cases and guards (consistency scan)

1. **A submission fails half-way** (sbatch rejects job 7 of 12): the ledger holds six jobs; `submitted_jobs` raises; the submit session ends nonzero; the six jobs run. `watch` sees a ledger whose jobs finish, evaluates it: six combos have results, six have no ledger entry → the resume's rebinding check fails ("6 combination(s) have no recorded job"). That is correct — the session is incomplete and says so; the remedy is `cancel`, then `run --stage harness --session X` again (its `clean_root` passes once nothing is queued).
2. **The resume session dies mid-wait** (login node reboot): nothing is lost — jobs are Slurm's, outputs are on disk, the ledger has no `evaluated_at`; the next `watch` runs the resume script again, which waits for whatever is left and evaluates everything. Idempotent by construction (Decision 8, section 7).
3. **A job is still queued past its deadline**: `wait_for_job` scancels and raises `SlurmJobTimeout`, exactly as `process.wait(timeout=…)` did; `driver_result` is `timeout`. The deadline counts from `submitted_at`, which is hours before the wait starts for a late combo in a long session — intended: the allowance is for the queue, and the queue has been holding the job since submission.
4. **All jobs submitted at once lengthen queue waits**: `queue_wait_s` is per job and starts at submission; the commented `exhaustive-maccity` entry shows 14400 for `batch`. The template comments say so. Submitting in bulk does not change Slurm's fairness; it only stops the harness from serializing what the scheduler would run in parallel.
5. **`sacct` has no row** (accounting lag longer than the retry): `SlurmAccountingMissing` fails that combination's `test_driver_execution` with the `sacct -j` command to run by hand; a re-run of the resume (`--stage resume`) after accounting catches up records it correctly. Not silently "passed".
6. **`--combo-clean-root` on a root with live jobs**: refused (Decision 9). On a root whose jobs are all done but never evaluated: removed as today — the user chose to clean; `watch` would otherwise have evaluated it.
7. **Two `watch` processes**: each takes the next unevaluated session; both may start the same session's resume. The lock keeps the committed files consistent; the second resume re-writes the same artifacts; the ledger's `evaluated_at` is whichever finished last. Harmless, wasteful, logged ("already being evaluated" cannot be known without a pid file, which the user declined — Open question 4).
8. **`--suite-config` regex selecting both maccity exhaustive suites into one session**: unchanged multi-suite session semantics (`<suite>/<combo>` ids, flat root); one ledger lists both suites' jobs.
9. **A dry run**: `pytest --dry-run --submit-only` submits nothing, writes no ledger, skips every test as today; `run --dry-run` renders `05-*` and `06-*` for every session and executes nothing; `watch --once` on an unsubmitted tree reports `not submitted` for every session.
10. **docker/native**: `submitted_jobs` is empty, `driver_run` runs inline, no ledger, no `jobs.yaml`; `--submit-only`/`--resume` are usage errors naming the runtime; `local.yaml` is byte-for-byte today's behaviour plus one documented key.
11. **`harness.pytest_args: [-x]`** (stop at first failure) with submit-all: `-x` stops the *evaluation* at the first failing combo while the remaining jobs still run or have run; their results are on disk and a `--stage resume` without `-x` evaluates them. Documented in the README beside `pytest_args`.
12. **`clean_root: true` and a resume by hand**: `--stage resume` never passes `--combo-clean-root` (section 2), so a hand-run resume cannot wipe the root it is meant to evaluate.
13. **The `.out` of a job that never started** (`sbatch` accepted, Slurm failed it before it wrote): `finish_driver_job` writes `sacct`'s state and the submission output into the `.out`, as the `--wait` path writes sbatch's words today.
14. **Multi-application configs**: `<output_root>/<app>/<session>`; script names `05-harness-<app>-<session>.sh`; `watch` loops applications × sessions. Nothing application-specific anywhere in this change (no adapter method added).

## Risks and notes

- **`flock` on Lustre.** Advisory locks across nodes need the mount's `flock` option; on one node they work regardless of the option on current kernels. `watch` evaluates on one node serially, so the supported workflow never relies on cross-node locking. Noted in the README beside the lock.
- **`squeue`/`sacct` availability and load.** One `squeue` per tick for all ids (not per job) and `sacct` once per finished job keep the scheduler traffic negligible at `poll_s: 30`. A site that throttles `squeue` shows up as logged retries, never as a wrong verdict.
- **The verdict moves from `sbatch --wait` to `sacct`.** `ExitCode` is `N:M`; `N` is the script's exit — `set -euo pipefail` plus `srun` make it the driver's. `State` covers what the exit code cannot (`TIMEOUT`, `CANCELLED`, `NODE_FAIL`, `OUT_OF_MEMORY` — all nonzero verdicts, `TIMEOUT` mapped to `timeout`, the rest to `failed` with the state in the row's `slurm_state`).
- **`duration_s` changes meaning under slurm** (submission → end, from accounting). Existing rows keep theirs; the column description says which runtime measures what. `wall_s`, `queue_s`, `elapsed_s` are unchanged and were always the precise ones.
- **Login-node etiquette.** The submit session and `watch` are mostly asleep; the resume session's analysis (dask, plots) is the same CPU the harness stage spends today. Nothing new runs on the login node that did not already.
- **More files, one more concept.** `jobs.yaml` and `06-resume-*.sh` are two new artifacts; both are the kind the harness already favours (a YAML record, a script a human can run by hand). The alternative — a background process per session with pids to track — was rejected: it is not restartable, not inspectable, and it would still need the ledger.
