# Feature: `ufs-chem-assay report` — one rollup of what went wrong (and right) across a run's sessions, from the roots alone, after `watch` or any time later

Refined 2026-11-05 from the conversation in the appendix, the morning after the first asynchronous Ursa run (`feature/async-runs` at `565d0dd`: two sessions submitted, watched, evaluated and uploaded). Today a failure is recorded truthfully but in four places — the session root's `test-report.csv` and `benchmarks.csv`, the ledger's exit status, the resume log's pytest summary, the combination's `.out` — and nothing stitches them together across sessions. This change adds **`ufs-chem-assay report`**: a file-reading utility that finds a run's session roots the way `watch` does (or takes one root, downloaded or not), classifies every session and every combination that did not come out clean, prints one readable summary with the reasons and the paths, writes the same as YAML on request, and exits nonzero when anything is wrong. `watch` ends with that same summary, through the same function.

## Goal

After `watch` (or instead of reading its log the next morning):

```bash
cd $ROOT/ufs-chem-assay
uv run ufs-chem-assay report                      # every session of the last `run`, from its effective config
uv run ufs-chem-assay report --session gcafs-anthro --tail 40
uv run ufs-chem-assay report --output-root ~/gcafs-runs/<run ULID>   # a downloaded root, on a laptop
```

1. **One line per session**: name, run ULID, state (`evaluated (exit 0)`, `evaluated (exit 1)`, `not evaluated`, `not submitted`, `submission incomplete`), the test counts (passed/failed/skipped), how many combinations ran clean, whether the root was uploaded and where.
2. **One block per issue**: the combination (suite, name, ULID), what kind of issue (the taxonomy in Design 2), the job id, Slurm state, exit code and duration when there is a job, the failed test names, the last `--tail` lines of the combination's `.out`, and the paths to open next (`.out`, `cece.log`, the combination directory, the resume log).
3. **Session-level issues too**: a resume session that died (the traceback or usage error pulled from its newest log), a submit that was refused half-way (the combinations without a job), a session never submitted, and the session-end pipeline's own errors (benchmarks, publish, upload) which today exist only as log lines.
4. **Exit code**: 0 when every selected session is evaluated with exit 0 and no issue was found; 1 otherwise — so `harness-run.sh` can end with `report` and mean it.
5. **`watch` ends with the same summary** instead of its one line naming sessions, and `--write PATH` saves the report as YAML (the `RunReport` model's dump) for anything that wants to read it back.
6. **Nothing but files are read.** No `squeue`, no `sacct`: the report is about what a run left behind, which is why it works on a downloaded root and after the jobs are long gone. Queue state stays `watch --once`'s business.

## Pre-design audit (fresh facts, 2026-11-05)

Verified on `feature/async-runs` at `565d0dd`.

1. **What a session root holds, and who reads it already.** `run.yaml` (`baselines.plan.read_run` → `RunManifest`: run id, application, suites, platform, runtime, launch); `test-report.csv` (`baselines.plan.read_test_report` → `TestReportRow`: pytest_name, suite, combo_id, combo, result in passed/failed/skipped); `benchmarks.csv` (`benchmarks.read_benchmarks_csv` → `BenchmarkRow`: `driver_result` passed/failed/timeout, `exit_code`, `slurm_job_id`, `slurm_state`, `duration_s`, `wall_s`, `queue_s`, `elapsed_s`, `nc_files`, `output_bytes`, `baseline_state`, `comparison_result`); `combos.csv` (every enumerated combination, `read_parameters`); `jobs.yaml` (`jobs.read_ledger` → `JobLedger`: `jobs[]`, `submitted_by`, `evaluated_at`, `exit_status`); `upload.yaml` (`outputs.OutputUploadRecord`: `run_id`, `store`, `destination`, `uploaded_at`, `uploaded_by`); per combination `<combo_id>.out`, `cece.log`, `<combo_id>/benchmarks.csv`, `.sbatch`. Every reader needed exists; none of them joins the files.
2. **`driver_result` says how the driver ended, not how the tests went.** `benchmarks._driver_result` is `passed` iff the driver call raised nothing and `test_driver_execution` passed; an assertion test failing afterwards (`test_nc_file_count`, `test_species_attributes`, …) leaves `driver_result: passed` and shows only in `test-report.csv`; a comparison failing shows in `comparison_result`. The report therefore needs both files to tell "the driver died" from "the driver ran, the output was wrong" from "the output differs from the baseline".
3. **The logs.** `cli.shell.run_bash` writes `<root_dir>/logs/<script stem>-<YYYYmmdd-HHMMSS>.log` per invocation (local time; several accumulate; newest by name). A resume log ends with pytest's `short test summary info` (the default `-r fE`: one `FAILED <nodeid> - <message>` line per failure) and contains the captured `----- driver output [<combo_id>] -----` blocks for failing tests only. The submit log carries `submitted combo <name> as Slurm job <id>` lines. The session-end pipeline's failures are `ERROR ufs-chem-assay.conftest:` lines (`benchmarks failed: …`, `publishing baselines failed: …`, `uploading output failed: …`) with the post-hoc command, and nothing else records them. A session that dies at start leaves a `UsageError` in the log and no artifact at all.
4. **`watch` already resolves the roots.** `cli.watch._load_effective(root_dir)` loads `<root_dir>/scripts/run-config.yaml`; `session_root(config, app, session)` resolves a session's output root exactly as the pytest session does; `watched_sessions` builds (application, session, root, resume script) in config order but refuses sessions without `submit_only` — right for `watch`, wrong for `report`, which must also summarize a session evaluated in place (a `local.yaml` run, or an Ursa session with `submit_only: false`). `watch`'s end is one INFO line naming sessions whose evaluation failed and whose tests failed, by label only.
5. **A downloaded root is a root.** `download-output --ulid X --dest D` lands the whole root at `D/X/` — `jobs.yaml` and `upload.yaml` included, logs excluded (they live under `<root_dir>/logs`, outside the root). A report over it has everything but the log-derived items.
6. **Failure shapes seen or designed so far** (the taxonomy's raw material): the driver fails or is killed by its limit (benchmark row `failed`/`timeout`, `slurm_state` FAILED/TIMEOUT/CANCELLED, dependent tests skipped "driver run failed"); the driver passes and an assertion test fails; the comparison fails; the resume session dies (`evaluated_at: null`, no test report, maybe a traceback in the log); `sbatch` refuses half-way (`jobs.yaml` shorter than `combos.csv`'s combination set; the submit session exits nonzero); a session never submitted (no ledger); the session-end pipeline logs an ERROR and the session still exits by its tests; `sacct` has no row (`SlurmAccountingMissing` fails `test_driver_execution` with the `sacct -j` command in the message).
7. **`src/report.py` exists** and is the `test-report.csv` row model; a CLI module needs another name.

## Design

### 0. Decisions

1. **A file reader with two entry points.** `src/cli/run_report.py` holds pure functions over paths — `summarize_session(root, *, logs_dir=None, tail=15) -> SessionSummary` and `render(report) -> list[str]` — plus the `report` subcommand's handler; `watch` imports the same two functions for its ending. No Slurm call anywhere in the module (Goal 6).
2. **The issues are a small closed taxonomy** (Design 2), each with the same shape (`Issue`), so the rendering is one loop and the YAML one list. A combination appears at most once, under its worst kind (driver before tests before comparison); session-level issues have no combination.
3. **Reuse, never re-read differently**: `read_run`, `read_test_report`, `read_benchmarks_csv`, `read_parameters` (for the enumerated set), `read_ledger`, `OutputUploadRecord.model_validate` on `upload.yaml`; the session roots from `watch.session_root` over `load_effective` (made public). `watch.watched_sessions` splits into `configured_sessions(config, applications, sessions, scripts_dir)` (every session, no `submit_only` rule) used by both, and `watch`'s own check on top.
4. **Logs are a bonus, never a requirement.** With `--root-dir` the newest `06-resume-<app>[-<session>]-*.log` (or, for a session evaluated in place, the newest `05-harness-…` log) supplies the pytest `FAILED … - message` lines, the pipeline `ERROR` lines and, for a dead session, the last traceback; with `--output-root` alone there are no logs and the report says `logs: none (output root given directly)`. Log parsing anchors on two stable prefixes only: pytest's `FAILED ` summary lines and the harness logger's ` ERROR ufs-chem-assay.` lines; anything else in a log is ignored.
5. **Output goes through the harness logger, one line per item**, as every subcommand's output does today (`fetch`'s summary, `watch`'s ticks); `--write PATH` dumps the `RunReport` model as YAML. No `print`.
6. **Exit 1 for any issue, including incompleteness.** A session not yet evaluated or not yet submitted is an issue of its own kind: after `watch` nothing should be in that state, and a report run midway should not say "fine".
7. **`watch` keeps its ticks and loses its last line**: after the loop it calls `summarize_session` per watched session and logs `render`'s lines; its exit code is unchanged in meaning (the sessions' statuses, a failed evaluation) and now agrees with `report`'s by construction (both derive from the same summaries).
8. **The report never writes into a root.** `--write` defaults to nothing; when given it is wherever the user says (the runbook suggests `$ROOT/logs/report-<stamp>.yaml`). A downloaded root stays byte-identical to the store's copy.

### 1. The models — `cli/run_report.py`

- **`IssueKind`** (`Literal`): `not-submitted`, `submission-incomplete`, `not-evaluated`, `driver-failed`, `driver-timeout`, `accounting-missing`, `test-failed`, `comparison-failed`, `pipeline-error`.
- **`Issue(StrictModel)`**: `kind: IssueKind`; `suite: str | None`, `combo: str | None`, `combo_id: str | None` (None for session-level kinds); `detail: str` (one sentence: the `FAILED` message, the ERROR line, "3 combination(s) have no recorded job: …"); `job_id: str | None`, `slurm_state: str | None`, `exit_code: int | None`, `duration_s: float | None`; `failed_tests: list[str]` (bare test names, `test_nc_file_count`); `out_tail: list[str]` (the last `tail` lines of the `.out`, empty when absent); `paths: list[Path]` (`.out`, `cece.log`, the combination directory, the log the detail came from — whichever exist). Every field described.
- **`SessionSummary(StrictModel)`**: `application: str`, `session: str | None`, `root: Path`, `run_id: str | None` (None without `run.yaml`), `state: Literal["not submitted", "submission incomplete", "not evaluated", "evaluated"]`, `exit_status: int | None`, `evaluated_at: datetime | None`, `submitted_by: str | None`, `combinations: int` (from `combos.csv`), `jobs: int` (from the ledger), `tests: dict[TestResult, int]`, `clean: int` (combinations with every test passed or skipped-by-design and `driver_result: passed`), `uploaded_to: str | None` (`upload.yaml`'s destination), `comparisons: dict[str, int]` (how the configured comparisons went, from the benchmark rows' `comparison_result` and `baseline_state`: `passed`, `failed`, `unpublished`, `off` — see Open question 4), `log: Path | None` (the newest resume/harness log read), `issues: list[Issue]`.
- **`RunReport(StrictModel)`**: `root_dir: Path | None`, `generated_at: datetime`, `sessions: list[SessionSummary]`; property `ok` (every session `evaluated`, exit 0, no issues).

### 2. Classifying one root — `summarize_session`

In this order, each step adding to `issues` and stopping where nothing further can be known:

1. **No `run.yaml`** → `state: not submitted`, one `not-submitted` issue ("no run.yaml at <root>; the harness stage has not run"), done. (A dry-run root has `run.yaml` and no ledger: under slurm that is `not submitted` as well — "run.yaml from a dry run, no jobs.yaml"; under docker/native it is an evaluated root without a ledger, step 3.)
2. **`run.yaml` and, under slurm (`run.runtime`), `jobs.yaml`**: the enumerated set from `combos.csv` (`combo_id`s) against the ledger's: combinations without a job → `submission-incomplete` with the names, state `submission incomplete`. `evaluated_at: null` → state `not evaluated`, one `not-evaluated` issue whose detail is the newest resume log's traceback or `UsageError` line when a log is available ("resume log <path>: <last ERROR/Error line>"), else "no evaluation yet (jobs.yaml has no evaluated_at)". Stop: there is no test report to read.
3. **Evaluated** (`evaluated_at` set, or no ledger under docker/native with a `test-report.csv`): `exit_status` from the ledger (None without one). Read `test-report.csv` and `benchmarks.csv`; counts by result. Per combination (grouped by `combo_id`):
   - benchmark `driver_result: timeout` → `driver-timeout`; `failed` → `driver-failed` — unless the `FAILED test_driver_execution` message names `sacct -j` → `accounting-missing`; detail from the pytest summary line when a log is at hand, else "driver <state>, exit <code>"; `out_tail` from the `.out`.
   - driver passed and any test other than `test_baseline_comparison` failed → `test-failed`, `failed_tests` listed, details from the matching `FAILED` lines.
   - `comparison_result: failed` (and nothing above) → `comparison-failed`, paths include the combination's `<combo_id>-stats-comparison.csv` and `plots-baselines/`.
   - everything else → counted in `clean`. A comparison that skipped is never an issue, but it is counted: `baseline_state: unpublished` → `comparisons.unpublished`; `comparison_result` None with `run.yaml` showing comparisons disabled or no entry for the combination → `comparisons.off`; passed/failed → their counts (a failed one is the `comparison-failed` issue above).
4. **Pipeline errors**: with a log, every ` ERROR ufs-chem-assay.` line after the last `passed`/`failed` pytest progress line → one `pipeline-error` each (detail: the line; the post-hoc command is in it already).
5. **Upload**: `upload.yaml` present → `uploaded_to`; absent and `run.yaml` says nothing about it (the flag is not recorded) → `None`, rendered as "not uploaded".

A `.out` missing for a failed combination (the session died before `finish_driver_job` wrote one) is reported as such in `out_tail` (`["(no .out: the job never wrote and no session judged it)"]`), not an error of the report.

### 3. Rendering

`render(report)` returns lines in this shape (the logger adds the stamp):

```
report: 2 session(s) under /scratch3/.../ufs-chem-assay-run (effective config of 2026-11-05 07:31)
simple-maccity  run 01M6N…  evaluated (exit 1)  tests 16 passed / 2 failed / 3 skipped  clean 2/3  comparisons 2 passed  uploaded s3://ufs-chem/assay-output/01M6N…
  [driver-timeout] simple-maccity/MACCITY.map-consd (01M6N…)  job 5120394 TIMEOUT exit 0  2154 s from submission
    FAILED test_driver_execution[MACCITY.map-consd] - driver run failed: Slurm job 5120394 timed out
    .out tail (15):
      | ...
    see: <root>/01M6N…/01M6N….out, <root>/01M6N…/cece.log, <root>/01M6N…/, $ROOT/logs/06-resume-cece-simple-maccity-20261105-0731.log
gcafs-anthro    run 01M6N…  evaluated (exit 0)  tests 7 passed / 0 failed / 1 skipped  clean 1/1  comparisons 1 unpublished  uploaded s3://…
report: 1 issue(s) in 1 of 2 session(s); exit 1
```

Sessions in config order; issues in combination order within a session, session-level ones first. `--tail 0` drops the `.out` lines; `--quiet` prints the session lines and the final line only (the YAML keeps everything).

### 4. The command and `watch` — `cli/main.py`, `cli/watch.py`

- **`report [--root-dir DIR] [--application NAME]… [--session NAME]… | --output-root PATH` `[--tail N] [--write PATH] [--quiet]`.** `--output-root` is exclusive with the three selection flags (argparse mutually exclusive group for `--root-dir`/`--output-root`; naming `--session` with `--output-root` is a usage error): the one root, `application`/`session` read from `run.yaml` (`session` is unknown there — rendered from the root's directory name, marked as such) and no logs. Otherwise the roots come from the effective config, exactly as `watch`'s, every configured session included (`configured_sessions`), and `logs_dir = <root_dir>/logs`. Exit: Decision 6.
- **`watch`** replaces its final `every session evaluated…` line with `render(RunReport(...))` over `summarize_session` of each watched root (its `logs_dir` is known), logged at INFO; the exit code computation stays as is. `--once` is unchanged (queue state is its point).
- **`watched_sessions`** becomes `configured_sessions` plus the `submit_only` check in `watch`'s own code path; `_load_effective` becomes `load_effective` (shared).

### 6. Edge cases (consistency scan)

1. **Several resume logs for one session** (watch restarted, `--stage resume` by hand): the newest by file name is read; the report names which. A session evaluated twice has one ledger state (the last) and one test report (the last): consistent with what the files say.
2. **A root cleaned and rerun** while an old log remains: the log's `FAILED` lines may not match the new test report. The report joins a `FAILED` line to an issue only when its `[<combo id or name>]` matches a combination the report already classified as failed from the files; unmatched lines are dropped. Files win, logs decorate.
3. **Multi-suite session**: test ids are `<suite>/<combo>` (conftest); the join uses `combo_id` from the report rows and the `[...]` id only for the detail line.
4. **Local/docker roots** (no ledger, no `submit_only`): `state: evaluated` from the presence of `test-report.csv`, `exit_status: None` (unknown), the newest `05-harness-…` log for the details. `report --root-dir` after `run --config-file=config/local.yaml` works.
5. **`--output-root` on a root with no `test-report.csv` and no ledger** (a crashed synchronous session): `not evaluated`, detail "no test-report.csv and no jobs.yaml".
6. **A combination skipped by `-k`**: not in the test report at all, in `combos.csv` and (slurm) the ledger: counted in `combinations`, in `jobs`, neither clean nor an issue — rendered in the session line as `n not run` when nonzero.
7. **Huge `.out`**: only the last `tail` lines are read (seek from the end); a binary or non-UTF-8 tail is decoded with replacement.
8. **Two applications**: one summary per (application, session), the application in the session line when the config has several.
9. **`watch` interrupted (130)**: no report (the loop did not end); `report` by hand gives the same picture.

## Risks and notes

- **Log parsing is best effort by design** (Decision 4): two anchors, files win on conflict. If pytest's summary format or the logger's format changes, the report loses detail lines, never correctness of the classification.
- **`exit_status` is unknown for roots evaluated without a ledger** (docker/native): the report says so rather than inferring 0 from "no failed rows".
- **One more subcommand**: the CLI's `Command` enum grows to nine entries; `test_every_command_has_a_handler` keeps them wired.
- **Not a dashboard.** A `status` view across runs in the store (by name and date, reading the ledgers' `submitted_by`/`evaluated_at`) stays in the async-runs design's future work; this report is about one run root set.

## Open questions (defaults applied)

1. **Command name**: `report` (default) vs `status`. `status` reads as "now" and would invite the queue state the design keeps out; `report` is after the fact.
2. **Should `watch --once` also print the report?** Default: no — `--once` is the queue tick; `report` is one more command away and does not need the effective config to be the last `run`'s.
3. **YAML output by default** into `<root_dir>/logs/`? Default: only with `--write` (Decision 8); `harness-run.sh` can pass it.
4. **Should `clean` require `comparison_result: passed`** when a comparison was configured? → **No, but the report says what the comparisons did** (resolved 2026-11-05 with the user). The comparison test skips for four reasons only — the driver failed (already a driver issue), comparisons are off (the run's own choice), no entry for the combination, or the pinned baseline is the unpublished placeholder (the cold start, expected once) — and every real comparison problem (a baseline that failed to stage, one missing from the root) *fails* the test, so nothing hides behind a skip. `clean` therefore ignores skipped comparisons, and the session line carries `comparisons N passed / N unpublished` (or `comparisons off`), from counts the benchmark rows already hold, so a cold-start run reads as clean with an unpublished baseline rather than silently clean. The strict alternative (an unpublished pin as a low-severity issue) was declined as noise during a configuration's first runs.
