## Goal and scope

Two things, in this order, for CECE only and one compiler (`oneapi`: `icx` / `icpx` / `ifx` with cray-mpich, as the weather model's C7 port sets them — not the Cray `cc` / `CC` / `ftn` wrappers the C6 file uses):

1. **Build CECE on a compute node** — the offline compile probe: the configure and the build each behind their own `srun`.
2. **Run CECE's unit tests on compute nodes** — one Slurm job, `ctest` on the node, each MPI test its own `srun` step.

Not in this first run: CATChem, the Kokkos smoke project, a second compiler, the driver sessions. Add them once CECE works (the last section says how).

One thing to know before starting: **CECE's test stack cannot be configured on a compute node**. It fetches GTest and RapidCheck at configure time. So "build on a compute node" is the libraries and the driver (`-DCECE_BUILD_TESTING=OFF`); the build stage then re-configures the same build directory on the login node with the tests on and builds them there, reusing the compute-built objects. The tests themselves run on compute nodes. Step 5 separates the two so the compute-node build is tested by itself first.

### Kokkos is not in the environment

`module avail kokkos kokkos-kernels arborx esmf mapl cmake python`, run with the whole stack loaded, listed `esmf`, `mapl`, `cmake` and `python` modules and **no `kokkos`, `kokkos-kernels` or `arborx`**. Both of the environment's module trees were on the path (`…/modules/intel-oneapi-compilers/2025.3.1` and `…/modules/cray-mpich/9.2.0/intel-oneapi-compilers/2025.3.1`), so this is not a hierarchy that had yet to open.

**Why, from the spack-stack 2.2.0 source** (tag `spack-stack-2.2.0`, read 2026-11-17): Kokkos is supported in 2.2.0 but is opt-in per site. `ufs-weather-model-env` has two variants, `kokkos` and `arborx`, both **off by default**; `configs/common/packages.yaml` fixes the versions they would build (`kokkos@5.1.1`, `kokkos-kernels@5.1.1`, `arborx@2.1`, each `+openmp +serial`). A site turns them on in its own `packages.yaml`: Ursa requires `+kokkos +arborx`, Gaea C6 requires `+kokkos`, and **Gaea C7's site config (added 2026-10-14, JCSDA/spack-stack#2161) has no such line**, at the tag and on `develop`. So the C7 install is as its config says: the absence is not a broken install, and nothing short of a config change and a rebuild will put the modules there.

### The cluster name

On Gaea the login nodes are not part of the compute cluster, and C6 jobs are submitted with `--clusters=c6`. The harness puts `slurm.extra_args` on its `sbatch` and `srun` lines, so `extra_args: --clusters=c7` covers submission. For everything after submission it relies on one thing: `sbatch --parsable` prints `<job id>;<cluster>` when the job went to a named cluster. The harness records that cluster with the job (`cluster:` in `tests.yaml` and `jobs.yaml`) and passes `-M <cluster>` to every later `squeue`, `sacct` and `scancel`. Nothing else is configured, and `SLURM_CLUSTERS` does not need to be set.

Check that one thing by hand before the first harness job, with a one-minute job of your own. The same job answers the filesystem question: whether a compute node sees the harness checkout and the environment under the names the login node uses, and can write under the run root.

```bash
cd $ROOT
sbatch --parsable --clusters=c7 -A epic -q normal -p batch -t 1 \
    --wrap "hostname; ls -d $HARNESS/modulefiles $ENV/modules/Core $(readlink -f $ENV)/modules/Core; touch $ROOT/compute-write-test && echo WRITE OK"   # expect: <job id>;c7
squeue -h -M c7 -j <job id> -o "%i %T"        # "<job id> PENDING" or RUNNING while it is queued
sacct -M c7 -j <job id> -P -n -o JobID,State,ExitCode,Elapsed   # a row once it has finished
cat $ROOT/slurm-<job id>.out                  # a compute-node hostname, the three directories, WRITE OK
```

Record all four outputs. If `ls` failed for the environment, the compute nodes do not have it under the name the login node uses: try the other form (`/autofs/ncrc-svm1_proj/epic/...`) in the same job, and use the one that works on both kinds of node in `c7-env.sh` and in the run config (the build bakes absolute paths in). If the job's output is missing or `touch` failed, the compute node could not write under `$ROOT`, which is not expected on `/gpfs/f7`: record the error (a quota or a permission on the directory is the likely cause) before going on, because the compute-node build and the test job need exactly that.

For the cluster name: If `sbatch` prints the job id alone (no `;c7`), the harness records no cluster and will ask `squeue` without `-M`; if step 1 showed that such a `squeue` does not list C7 jobs, the harness will then decide a job has left the queue the moment it is submitted. The fallback in that case is the environment variable the Slurm client commands read — `export SLURM_CLUSTERS=c7` in the shell that runs `ufs-chem-assay run` and `watch` — and it is a harness bug to report with the outputs above.

**If `watch` says the job is done the moment it was submitted**, or evaluates it with `no accounting for job …`: that is the cluster name (step 1). **If the MPI tests fail to start** (PMI errors, "unable to launch"): the single-rank tests still tell you the build works. For the multi-rank ones, try a preflag in the run config, `mpiexec_preflags: --mpi=cray_shasta` (or what `srun --mpi=list` offers), then **rebuild** (`--stage build`: the launcher is baked in at configure time) and resubmit. **If the MPI tests start but fail in the fabric** (libfabric / CXI errors): the weather model's C7 run job exports `FI_VERBS_PREFER_XRC=0`, `FI_CXI_RX_MATCH_MODE=hybrid`, `COMEX_EAGER_THRESHOLD=65536` and `FI_CXI_RDZV_THRESHOLD=65536` before its `srun`. Put the ones that help under the toolchain's `tests_env` and resubmit (no rebuild: they are exported in the job).

**If the job fails before ctest runs**: `tests-<job id>.out` has the reason; most likely the module block inside the job. A job that says `module: command not found` did not inherit Lmod: the harness sources `$MODULESHOME/init/bash` when `MODULESHOME` is set, and the weather model's C7 jobs source `/opt/cray/pe/lmod/lmod/init/bash` when `module` is missing — record which of the two the job needed. Submit the rendered script by hand to iterate (`sbatch $ROOT/scripts/04-test-cece-oneapi.sbatch`); a job submitted by hand is not tracked by `watch`, so read its `.out` directly.

**To run a few tests while iterating**: `--override applications:cece:tests:filter='^<regex>'` on the `--stage test` command (`ctest -R`); the stage re-renders the job with it.
