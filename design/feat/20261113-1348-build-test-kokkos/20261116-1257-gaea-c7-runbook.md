## Goal and scope

Two things, in this order, for CECE only and one compiler (`oneapi`, through the Cray wrappers):

1. **Build CECE on a compute node** — the offline compile probe: the configure and the build each behind their own `srun`.
2. **Run CECE's unit tests on compute nodes** — one Slurm job, `ctest` on the node, each MPI test its own `srun` step.

Not in this first run: CATChem, the Kokkos smoke project, a second compiler, the driver sessions. Add them once CECE works (the last section says how).

One thing to know before starting: **CECE's test stack cannot be configured on a compute node**. It fetches GTest and RapidCheck at configure time. So "build on a compute node" is the libraries and the driver (`-DCECE_BUILD_TESTING=OFF`); the build stage then re-configures the same build directory on the login node with the tests on and builds them there, reusing the compute-built objects. The tests themselves run on compute nodes. Step 5 separates the two so the compute-node build is tested by itself first.

## 1. Facts to collect first

Run these on a C7 login node and keep the output (a terminal log is fine; step 8 bundles everything).

### The cluster name

On Gaea the login nodes are not part of the compute cluster, and C6 jobs are submitted with `--clusters=c6`. The harness puts `slurm.extra_args` on its `sbatch` and `srun` lines, so `extra_args: --clusters=c7` covers submission. For everything after submission it relies on one thing: `sbatch --parsable` prints `<job id>;<cluster>` when the job went to a named cluster. The harness records that cluster with the job (`cluster:` in `tests.yaml` and `jobs.yaml`) and passes `-M <cluster>` to every later `squeue`, `sacct` and `scancel`. Nothing else is configured, and `SLURM_CLUSTERS` does not need to be set.

Check that one thing by hand before the first harness job, with a one-minute job of your own:

```bash
cd $ROOT
sbatch --parsable --clusters=c7 -A <ACCOUNT> -q <QOS> -p <PARTITION> -t 1 --wrap hostname   # expect: <job id>;c7
squeue -h -M c7 -j <job id> -o "%i %T"        # "<job id> PENDING" or RUNNING while it is queued
sacct -M c7 -j <job id> -P -n -o JobID,State,ExitCode,Elapsed   # a row once it has finished
```

Record all three outputs. If `sbatch` prints the job id alone (no `;c7`), the harness records no cluster and will ask `squeue` without `-M`; if step 1 showed that such a `squeue` does not list C7 jobs, the harness will then decide a job has left the queue the moment it is submitted. The fallback in that case is the environment variable the Slurm client commands read — `export SLURM_CLUSTERS=c7` in the shell that runs `ufs-chem-assay run` and `watch` — and it is a harness bug to report with the outputs above.

## 3. A draft C7 modulefile

The harness ships `modulefiles/ufs_gaeac6.oneapi.lua` (the UFS's C6 platform file plus the Kokkos packages) and `modulefiles/ufs_common.lua` (the libraries every UFS platform file loads). C7 needs its own platform file. Draft it outside the checkout, so the checkout stays clean until the file is known to work:

```bash
mkdir -p $ROOT/c7-modulefiles
cp $ROOT/ufs-chem-assay/modulefiles/ufs_gaeac6.oneapi.lua $ROOT/c7-modulefiles/ufs_gaeac7.oneapi.lua
$EDITOR $ROOT/c7-modulefiles/ufs_gaeac7.oneapi.lua
```

Edit, using the table from step 1:

- `stack_intel_ver` default → the compiler stack version `module avail stack-` showed; if the module is not named `stack-intel-oneapi-compilers`, change the `load(pathJoin(...))` line too.
- `stack_cray_mpich_ver` default → the MPI stack version; same note on the name.
- `setenv("CMAKE_Platform", "gaeac6.oneapi")` → `gaeac7.oneapi`.
- The two `unload(...)` lines (`darshan-runtime`, `cray-libsci`): keep them unless `module load` complains that they are not loaded.
- The header comment: say it is a C7 draft and what you changed.

Leave the environment-root block as it is (it is optional: the run config names the environment's `modules/Core` directly). Then test the file by hand, exactly as the harness will load it:

```bash
module reset
module use $ROOT/ufs-chem-assay/modulefiles     # ufs_common.lua
module use $ROOT/c7-modulefiles                 # the draft
module use $ENV/modules/Core                    # the environment
module load ufs_gaeac7.oneapi && module list
which cc CC ftn cmake ctest
echo "CC=$CC CXX=$CXX FC=$FC"
```

`ufs_common.lua` loads seventeen libraries (jasper, libpng, hdf5, netcdf-c, netcdf-fortran, parallelio, esmf, fms, bacio, crtm, g2, g2tmpl, ip, w3emc, gftl-shared, mapl, scotch) and the platform file then loads kokkos, kokkos-kernels and, tolerantly, arborx. An "unknown module" names what the environment lacks: record it, and comment that one entry out of a copy of `ufs_common.lua` in `$ROOT/c7-modulefiles` if CECE does not need it (CECE needs MPI, netCDF, ESMF, Kokkos; ArborX when the gate below is kept). If the UFS already has a C7 platform file on its spack-stack 2.2 branch, compare the draft against it and note the differences.

## 4. The run config

Save this as `$ROOT/gaea-c7-cece.yaml` (a personal run config, not part of the checkout) and replace the five `<…>` placeholders from the table. It validated and rendered on a laptop with dummy values on 2026-11-16.

```yaml
platform: gaea-c7
toolchains:
  oneapi:
    modulefile: ufs_gaeac7.oneapi
    modulepath:
      - modulefiles                     # relative: the harness checkout's (ufs_common.lua)
      - <ROOT>/c7-modulefiles           # the draft platform file from step 3
      - <ENV>/modules/Core              # the spack-stack 2.2 environment
    module_env: {}                      # pins, e.g. kokkos_ver: once `module avail` says what to pin
    toolchain_tools: [cc, CC, ftn, cmake, ctest]
    cmake_args:
      - -DCMAKE_CXX_FLAGS=-fp-model=precise   # IntelLLVM: CECE's axis tests need value-safe floating point
    mpi_launcher: srun                  # cray-mpich: every MPI test is its own `srun -n <ranks>` step
    mpiexec_preflags:                   # e.g. --mpi=cray_shasta, if the steps cannot find PMI (step 6)
    tests_env: {}
    configure_gates:
      - 'AXIS: ArborX .* found via find_package'   # remove if the environment has no arborx
applications:
  cece:
    git_url: git@github.com:benkozi/CECE.git
    ref: feat/prefer-find-package
    cmake_args:
      - -DCMAKE_BUILD_TYPE=Debug        # CECE's unit tests need a Debug build with ESMF
      - -DENABLE_ESMF=ON
    build_jobs: 8
    targets: [all]
    configure_gates:
      - 'CECE dependency Kokkos: system'
    build_node: compute
    build_minutes: 20                   # the time limit of each compile srun
    tests:
      enabled: true
      ntasks: 4                         # the largest rank count a CECE test asks for
      cpus: 8
      minutes: 15
slurm:
  account: <ACCOUNT>
  qos: <QOS>
  partition: <PARTITION>
  extra_args: --clusters=c7             # drop it if step 1 showed no cluster name is needed
```

With one toolchain in the map, no `--toolchain` flag is needed. Everything this run creates is under `$ROOT/oneapi/` (the CECE checkout and its `build/`, the tests root) plus `$ROOT/scripts/` and `$ROOT/logs/`.

## 5. Build CECE on a compute node

Render first and read what will run:

```bash
cd $ROOT/ufs-chem-assay
C7=(--config-file=$ROOT/gaea-c7-cece.yaml --application cece --root-dir $ROOT)
uv run ufs-chem-assay run "${C7[@]}" --stage source --stage build --stage test --dry-run
less $ROOT/scripts/02-build-cece-oneapi.sh $ROOT/scripts/04-test-cece-oneapi.sbatch
```

In `02-build-cece-oneapi.sh` check: `module reset` (not purge); the three `module use` lines; `which cc CC ftn cmake ctest`; two lines starting `srun -A <ACCOUNT> -q <QOS> -p <PARTITION> --clusters=c7 --nodes=1 --ntasks=1 --cpus-per-task=8 --time=20`, the first a `cmake -S … -B …` ending in `-DCECE_BUILD_TESTING=OFF -DMPIEXEC_EXECUTABLE="$(command -v srun)" -DMPIEXEC_NUMPROC_FLAG=-n`, the second `cmake --build`.

Clone, then build **with the tests off**, so the stage is the compute-node build and nothing else:

```bash
uv run ufs-chem-assay run "${C7[@]}" --stage source
uv run ufs-chem-assay run "${C7[@]}" --stage build --override applications:cece:tests:enabled=false
```

The build stage loads the modules in the login shell, then runs the configure and the build as two separate `srun` steps (two allocations: expect two queue waits). It checks the configure log before building; the lines it wants are:

```bash
grep -E "Found MPI|CECE dependency (Kokkos|ESMF): system|AXIS: ArborX" $ROOT/oneapi/CECE/build/configure.log
```

What to record: the queue wait and run time of each step (`$ROOT/logs/02-build-cece-oneapi-<stamp>.log`), whether the configure reached the network for anything (it should not), and the compilers the configure reported.

**If `srun` is refused from the login node** ("srun: error: … not supported on this node", or it hangs): the two compile lines can run inside an interactive allocation instead. Open one (`salloc --clusters=c7 -A <ACCOUNT> -q <QOS> -p <PARTITION> -N 1 -t 30`), load the modules as in step 3, and paste the two `srun … cmake …` lines from the rendered script with everything between `srun` and `cmake` removed. Record that this was needed: the harness then needs another way to reach a compute node on C7.

**If the compute-node configure fails on a download**: something reaches the network that `-DCECE_BUILD_TESTING=OFF` does not turn off. Keep the log, and continue on the login node with `--override applications:cece:build_node=login` to get to the tests.

## 6. Run CECE's tests on compute nodes

Build again with the tests on. The compute-node probe repeats (quickly: everything is built), then the login node re-configures with `-DCECE_BUILD_TESTING=ON` and builds the test stack:

```bash
uv run ufs-chem-assay run "${C7[@]}" --stage build
```

Then submit the test job and wait for it:

```bash
uv run ufs-chem-assay run "${C7[@]}" --stage test
uv run ufs-chem-assay watch --root-dir $ROOT --only tests
uv run ufs-chem-assay report --root-dir $ROOT --only tests
```

The test stage submits one job and returns. The job (`$ROOT/scripts/04-test-cece-oneapi.sbatch`) asks for one node, four tasks of eight cores, fifteen minutes; loads the same modules; and runs `ctest --test-dir build --output-on-failure --output-junit …` **directly on the node**, not behind `srun` — ctest is the launcher, and each MPI test is `srun -n <ranks> <test>` (what `mpi_launcher: srun` baked into the configure). `watch` polls the queue, and when the job has left it reads `sacct` and the junit report and prints a line like:

```
tests cece/oneapi: evaluated (exit 0), 577 passed / 0 failed / 0 skipped
```

Files, all under `$ROOT/oneapi/tests/cece/`: `tests.yaml` (the test ledger: the job id, what it ran against, the verdict), `tests-<job id>.out` (ctest's output, between a `tic:` and a `toc:` line), `tests-<job id>.xml` (the junit report), `benchmarks.csv` (one row per evaluated run).

**If `watch` says the job is done the moment it was submitted**, or evaluates it with `no accounting for job …`: that is the cluster name (step 1). Look at `cluster:` under `job:` in `$ROOT/oneapi/tests/cece/tests.yaml`: it should be `c7`. If it is `null`, `sbatch` did not report a cluster — `export SLURM_CLUSTERS=c7`, check `squeue -u $USER` lists the job, and run `watch` again once it has really finished; `uv run ufs-chem-assay evaluate-tests --root-dir $ROOT --application cece` re-reads a finished job by hand. If the ledger was already marked evaluated too early, resubmit: `uv run ufs-chem-assay submit-tests --root-dir $ROOT --application cece --resubmit`.

**If the MPI tests fail to start** (PMI errors, "unable to launch"): the single-rank tests still tell you the build works. For the multi-rank ones, try a preflag in the run config, `mpiexec_preflags: --mpi=cray_shasta` (or what `srun --mpi=list` offers), then **rebuild** (`--stage build`: the launcher is baked in at configure time) and resubmit. Record `srun --mpi=list`.

**If the job fails before ctest runs**: `tests-<job id>.out` has the reason; most likely the module block inside the job. Submit the rendered script by hand to iterate (`sbatch $ROOT/scripts/04-test-cece-oneapi.sbatch`); a job submitted by hand is not tracked by `watch`, so read its `.out` directly.

**To run a few tests while iterating**: `--override applications:cece:tests:filter='^<regex>'` on the `--stage test` command (`ctest -R`); the stage re-renders the job with it.

## 9. Next, once CECE works

Add the other two applications to `$ROOT/gaea-c7-cece.yaml` and run all three:

```yaml

    git_url: git@github.com:benkozi/CATChem.git
```


The smoke project is the quickest check of the environment by itself (no clone, one small build, one executable): if CECE's build is slow to debug, `--application kokkos-smoke` alone tells you whether the modules, the compilers and the compute-node build work at all.
