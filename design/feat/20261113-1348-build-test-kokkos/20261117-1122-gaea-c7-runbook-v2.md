## 4. Build on the login node

Start from a clean module environment. The stage scripts load their own modules, but the `uv run` that starts them runs in your shell, and after step 2 that shell has the environment's Python 3.13 packages loaded (`py-numpy`, `py-mpi4py`, …), which must not leak into the harness's own Python:

```bash
module reset; echo "PYTHONPATH=[$PYTHONPATH]"   # empty brackets
cd $HARNESS
C7=(--config-file=$ROOT/gaea-c7-cece.yaml --application cece --root-dir $ROOT)
uv run ufs-chem-assay run "${C7[@]}" --stage source --stage build --stage test --dry-run   # writes the scripts, runs nothing
uv run ufs-chem-assay run "${C7[@]}" --stage source                                        # clones CECE into $ROOT/oneapi/CECE
uv run ufs-chem-assay run "${C7[@]}" --stage build                                         # configure + build, on this node
grep -E "Found MPI|CECE dependency" $ROOT/oneapi/CECE/build/configure.log
```

The build stage loads the modules, runs one `cmake` configure (it fetches Kokkos, GTest and RapidCheck), checks the configure log, and builds with eight jobs. It stops with a message if the log lacks `Found MPI`, `CECE dependency ESMF: system` or `CECE dependency Kokkos: FetchContent`. The script it runs is `$ROOT/scripts/02-build-cece-oneapi.sh`; its log is under `$ROOT/logs/`.

## 5. Run the tests on a compute node

```bash
uv run ufs-chem-assay run "${C7[@]}" --stage test          # submits one job and returns
uv run ufs-chem-assay watch --root-dir $ROOT --only tests  # polls until the job is done, then evaluates it
uv run ufs-chem-assay report --root-dir $ROOT --only tests # the result again, any time later
```

`watch` ends with a line like `tests cece/oneapi: evaluated (exit 0), 778 passed / 0 failed / 1 skipped`. It is safe to stop and start again. The job's files are in `$ROOT/oneapi/tests/cece/`: `tests.yaml` (the record: job id, cluster, verdict), `tests-<job id>.out` (ctest's output), `tests-<job id>.xml` (the junit report).

## The ESMF 9 link patch

The branch the config names, `benkozi/CECE` at `feature/multi-tile-host-decomp`, carries this change once it is committed and pushed there (log entry of 2026-11-18, "the coupling branch"), and a fresh clone of it needs nothing. For a clone of any other branch, apply it once (the source stage leaves an existing clone alone). It removes the Fortran driver's `-cxxlib` from the `ESMF::ESMF` target that ESMF 9's own CMake package defines; the log entry of 2026-11-18 has the reasoning.

```bash
cd $ROOT/oneapi/CECE && git apply <<'EOF'
diff --git a/cmake/FindESMF.cmake b/cmake/FindESMF.cmake
index 33a4a7a..333618e 100644
--- a/cmake/FindESMF.cmake
+++ b/cmake/FindESMF.cmake
@@ -28,4 +28,15 @@ if(ESMF_FOUND)
     endif()
   endif()
+  # ESMF's own config package (9.0.0 betas onward) builds ESMF::ESMF from
+  # esmf.mk's Fortran link line. With the Intel compilers that line carries
+  # -cxxlib, an ifx driver option icpx rejects ("unknown argument"). CECE's
+  # libraries are linked by the C++ driver, which adds the C++ runtime itself.
+  foreach(_cece_esmf_prop INTERFACE_LINK_LIBRARIES INTERFACE_LINK_OPTIONS)
+    get_target_property(_cece_esmf_val ESMF::ESMF ${_cece_esmf_prop})
+    if(_cece_esmf_val)
+      list(FILTER _cece_esmf_val EXCLUDE REGEX "^-cxxlib")
+      set_target_properties(ESMF::ESMF PROPERTIES ${_cece_esmf_prop} "${_cece_esmf_val}")
+    endif()
+  endforeach()
   return()
 endif()
EOF
git -C $ROOT/oneapi/CECE status --short   # M cmake/FindESMF.cmake
```
