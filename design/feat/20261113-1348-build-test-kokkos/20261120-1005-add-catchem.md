## 1. Goal

CATChem gets what CECE got on Gaea C7: built and tested from `config/gaea-c7.yaml` against the spack-stack 2.2.0 environment, with the environment's Kokkos held by a gate, its tests built on a compute node and run on a compute node. Next to that compute-node build, CATChem gets a second build with MUSICA, on the login node. One run (`--application all`) does CECE and both CATChem builds; `watch` and `report` cover all three.

That needs one new harness concept, **build variants** (§2), designed so CECE can use it later and so every existing CECE config means what it means today. Two defects found while refining are fixed in the same piece of work: the harness's venv leaking into application configures (the issue the request names, §5), and a toolchain gate that only CECE can pass (§4.4).

Not in scope: a CATChem driver sweep (CATChem stays an application whose stages stop at `test`, as the parent design decided), `kokkos-smoke` on C7, Gaea C6.

## 2. What "sweeps" means here: build variants

The harness already uses "sweep" for something else: a suite's sweep is the dimension lists a pytest session enumerates into driver combos (`combos.py`, `models/suite_config.py`), and CATChem has no driver (`applications/nodriver.py` refuses every sweep method). The requirement's bullets describe something different: two builds of one application with different options, on different nodes, each tested on its own. This design reads "sweeps" as that — **a sweep over build configurations** — and calls one entry a *build variant*. §8 Q1 asks to confirm the reading; the alternative (a CATChem driver adapter with suites) is a much larger piece of work and is not designed here.

### 2.1 The run config

An application section gains an optional map, `builds:`, of variant name → overlay:

```yaml
applications:
  catchem:
    git_url: git@github.com:benkozi/CATChem.git
    ref: feature/cece-coupling-proto
    cmake_args: [-DCMAKE_BUILD_TYPE=Debug, -DCATCHEM_ENABLE_KOKKOS=ON, -DCATCHEM_BUILD_NUOPC=ON]
    builds:
      compute:   # Kokkos on, MUSICA off: the whole build, tests included, on a compute node
        cmake_args: [-DCMAKE_BUILD_TYPE=Debug, -DCATCHEM_ENABLE_KOKKOS=ON, -DCATCHEM_BUILD_MUSICA=OFF, -DCATCHEM_BUILD_NUOPC=ON]
        build_node: compute
      musica:    # MUSICA fetches at configure time: login node only
        cmake_args: [-DCMAKE_BUILD_TYPE=Debug, -DCATCHEM_ENABLE_KOKKOS=ON, -DCATCHEM_BUILD_MUSICA=ON, -DCATCHEM_BUILD_NUOPC=ON]
        build_node: login
```

- **Overlay keys**: `cmake_args`, `build_node`, `build_minutes`, `build_jobs`, `targets`, `configure_gates`, `tests` (the whole `tests:` section). Not overlayable: `git_url`, `ref`, `clone_dir`, `update_source` (one checkout per toolchain serves every variant) and the module keys (those belong to the toolchain).
- **Precedence**, after the toolchain overlay: an overlaid key replaces the application's value whole (the rule `sessions:` already uses), except `configure_gates`, which are unioned (the toolchain rule). The toolchain's `cmake_args` are still appended last, so `-fp-model=precise` reaches every variant. Replace rather than append for `cmake_args` because CMake keeps the last of two `-D` definitions silently: an appended `-DCATCHEM_BUILD_MUSICA=OFF` after an inherited `=ON` would work, but the configure line would read as contradicting itself.
- **No `builds:`** means one unnamed build, exactly as today: `<checkout>/build`, today's tests root, today's script names. Every existing config (all CECE configs, `config/local.yaml`, `config/ursa.yaml`) keeps its meaning without an edit — the compatibility the requirement asks for.
- `--build NAME [NAME ...]` or `--build all` on `run`, `watch` and `report` selects variants. With no flag, every variant of the selected applications runs (§8 Q3). `selected_builds` joins `selected_toolchains` in the effective `run-config.yaml`.

### 2.2 Paths and names

| | Unnamed build (today) | Variant `<v>` |
|---|---|---|
| Checkout | `<root>/<toolchain>/<App>` | the same checkout: the source stage runs once per application and toolchain |
| Build directory | `<checkout>/build` | `<checkout>/build-<v>` |
| Tests root | `<root>/<toolchain>/tests/<app>` | `<root>/<toolchain>/tests/<app>/<v>` |
| Scripts | `02-build-<app>-<toolchain>.sh` | `02-build-<app>-<toolchain>-<v>.sh`, the same for `04-test-…` and its `.sbatch` |
| Labels | `tests catchem/oneapi` | `tests catchem/oneapi/compute` |

Order inside a run: application-major as today, variants in map order inside each application's build and test stages. A failed variant does not stop the next one (the toolchain loop's rule); the summary has one line per variant, and the exit status is the first failure's.

### 2.3 Records

`TestJob` / the test ledger and `TestBenchmarkRow` gain `build` (the variant name, null for the unnamed build). The committed per-application `tests-benchmarks.csv` gains the column once, the way `build_type` was added (header migration, empty for old rows). `report` and `watch` label by variant; `cancel --tests-root` and `record-benchmarks --tests-root` work per tests root, so they need nothing new.

### 2.4 Driver sessions

The data and harness stages run a driver against one build. Until an application with a driver uses `builds:`, nothing changes; a config that gives CECE `builds:` and also selects a session is refused with a message naming the missing choice (`harness.build: <variant>`), rather than guessing. Designing that key properly waits for the first CECE variant (§8 Q4).

## 3. CATChem's two builds

| | `compute` | `musica` |
|---|---|---|
| Kokkos | on, the environment's (`Using system Kokkos` gate) | on, the environment's (same gate) |
| MUSICA | off | on |
| Where it builds | a compute node: configure and compile as two `srun` steps | the login node |
| yaml-cpp | the environment's, `-DCATCHEM_USE_SYSTEM_YAML_CPP=ON` (§3.2) | the environment's (§3.2) |
| Tests built | yes, on the compute node | yes, on the login node with the build |
| Tests run | test job on a compute node | test job on a compute node |

Facts from the checkout (`df9b41a`) the table rests on:

- **The compute build needs no network**, so it is the whole build, tests included, with no login-node finish. Outside the MUSICA submodule, CATChem's configure downloads exactly one thing: Kokkos, and only when `find_package(Kokkos)` fails (`CMakeLists.txt:158`), which the gate rules out. yaml-cpp is vendored (`src/external/CMakeLists.txt:91`, a `SOURCE_DIR` declaration), and `tests/CMakeLists.txt` uses plain `add_test` with no GoogleTest or other download. The adapter already treats such a build as whole: its offline arguments equal its arguments when MUSICA is off, so `OfflineBuild` is `None` and no finish is rendered (`applications/catchem/cli.py:_build`).
- **MUSICA requires Kokkos**: the configure stops with "CATCHEM_BUILD_MUSICA=ON requires CATCHEM_ENABLE_KOKKOS=ON". MUSICA builds also add two tests that exist only there, `test_catchem_photolysis` and `test_catchem_gaschem` (`tests/CMakeLists.txt:769` on).
- **Every CATChem test is single-rank**: no `MPIEXEC`, `mpirun` or `srun` in `tests/CMakeLists.txt`. `tests.ntasks: 1`, `cpus: 8` for the OpenMP Kokkos tests, as `config/ursa-kokkos.yaml` already says.

Adapter changes (`applications/catchem/cli.py`):

1. **"Kokkos always on"** becomes a validation rule: every CATChem build must carry `-DCATCHEM_ENABLE_KOKKOS=ON` (today it is a default that can be dropped).
2. **"MUSICA on, login node only"** becomes a validation rule: `-DCATCHEM_BUILD_MUSICA=ON` with `build_node: compute` is refused, with the reason (MUSICA fetches micm, TUV-x and their configuration at configure time).
3. **The MUSICA swap goes**: today `build_node: compute` builds a MUSICA-off probe on the compute node and then finishes the same build directory on the login node with MUSICA on, so the tests that run are the MUSICA build's. The two variants replace that, and a compute build is then always the whole build. A config without `builds:` that says `build_node: compute` with MUSICA on, as `config/ursa-kokkos.yaml` does today, is refused by rule 2 and has to choose; the shipped templates are changed in the same piece of work (§6).

### 3.1 Risks for the first C7 build

- **ESMF 9's `-cxxlib`.** CATChem's ESMF lookup accepts the `ESMF::ESMF` target from ESMF 9's own CMake package, the target that broke CECE's link on C7 (`icpx: error: unknown argument: '-cxxlib'`). In the checkout, none of the ten test executables that link with the C++ driver (`LINKER_LANGUAGE CXX`) links ESMF directly, so the failure may not recur; the NUOPC libraries can still bring ESMF in transitively. The first build answers it; the CECE fix (dropping `-cxxlib` from the imported target) is the template if it does.
- **yaml-cpp against ESMF's own.** See §3.2: the reason CATChem vendors yaml-cpp is a clash with ESMF, and taking the environment's gives that up.
- **C++20 for MUSICA.** CATChem builds with C++17 except MUSICA builds, which need C++20; `icpx` 2025.3 supports it, but the `musica` variant is the first C++20 CATChem build on C7.

### 3.2 yaml-cpp from the environment (round 2, Q5)

"try to take the environment's (i.e. spack-stack)" → both variants pass `-DCATCHEM_USE_SYSTEM_YAML_CPP=ON` where the environment has a yaml-cpp module, which on C7 is `yaml-cpp/0.8.0`, loaded by `modulefiles/ufs_gaeac7.oneapi.lua` since 2026-11-20 for CECE.

How CATChem chooses (checkout `df9b41a`): in a NUOPC build it uses its vendored yaml-cpp unless `CATCHEM_USE_SYSTEM_YAML_CPP` is on (`CMakeLists.txt:468`); with it on, `find_package(yaml-cpp QUIET)` runs, and if that finds nothing `src/external/CMakeLists.txt` falls back to the vendored copy **silently apart from one status line**, `yaml-cpp not found on system, using internal version`. It prints nothing when it does find the system copy. So the gate cannot be a line to require, the way CECE's `CECE dependency yaml-cpp: system` is.

The check, adapter-owned like CECE's ESMF gate and rendered only when `-DCATCHEM_USE_SYSTEM_YAML_CPP=ON` is among the build's `cmake_args`, after each configure of that build:

1. The configure log must **not** contain `yaml-cpp not found on system, using internal version` — the fallback, which otherwise would pass unnoticed.
2. `CMakeCache.txt` must have a `yaml-cpp_DIR` entry that is not `…-NOTFOUND`; the build log prints it, so the log names the install that was used (`…/yaml-cpp-0.8.0-v2ydpsz/lib64/cmake/yaml-cpp` on C7, if it matches CECE's).

Not chosen: a `configure_refusals:` key for every application, a general "must not match" list beside `configure_gates`. One adapter needs it today; it can become general if a second does. Also not chosen: asking CATChem to print `Using system yaml-cpp …` like its Kokkos line. That is a good change to propose upstream, but the harness should not wait for it.

Where it applies: `config/gaea-c7.yaml` only, for now. Ursa's modulefiles load no yaml-cpp and whether its environments carry one has not been checked; with the flag on and nothing found, the check would fail every Ursa CATChem build. `config/ursa-kokkos.yaml` keeps the vendored copy until its environment is checked and its modulefile loads yaml-cpp (a follow-up, not in this piece of work).

**The risk CATChem's comment names.** The vendored copy exists because "static libesmf.a in Spack/UFS environments embeds an internal yaml-cpp (~0.6.x) in the global ::YAML namespace". If C7's ESMF 9.0.0b17 carries such a copy with visible symbols, CATChem (and CECE, which already links the system yaml-cpp and ESMF in one process) would hold two `YAML::` implementations, which is undefined behaviour that need not show in a test. CECE's 778 passing tests say nothing either way. Checked before the first CATChem build, with the environment loaded in a subshell:

```bash
( module reset; export esmf_ver=9.0.0b17 mapl_ver=2.69.1-esmf-9.0.0b17; module use $HARNESS/modulefiles; module use /ncrc/proj/epic/spack-stack/c7/spack-stack-2.2.0/envs/ue-oneapi-2025.3.1/modules/Core; module load ufs_gaeac7.oneapi; L=$(dirname $ESMFMKFILE); ls $L/libesmf*; nm -DC --defined-only $L/libesmf.so 2>/dev/null | grep -c ' YAML::' )
```

A count of 0 (or only a static `libesmf.a` that nothing here links) means no clash; a nonzero count is a finding for CECE as much as CATChem, and the fallback is `-DCATCHEM_USE_SYSTEM_YAML_CPP=OFF` in the C7 template.

## 5. The issue: the harness's venv in application builds

Every C7 build log has `AXIS: Active Virtual Environment detected. Prioritizing: …/ufs-chem-assay/.venv`. That is HELM's AXIS (`libs/axis/CMakeLists.txt`, near the top): if `CONDA_PREFIX` is set, else if `VIRTUAL_ENV` is set, it **prepends that directory to `CMAKE_PREFIX_PATH`**. So every `find_package` after it looks in the harness's venv first, for Kokkos, ArborX, yaml-cpp and netCDF as much as for Python; a CMake package that a Python wheel happens to install there would win over the environment's. It is there because the stage scripts inherit the environment of `uv run ufs-chem-assay run`, which sets `VIRTUAL_ENV` and puts `<venv>/bin` first on `PATH`; `module reset` does not touch either. The test job inherits them too, through `sbatch`.

Fix, in the harness, for every application:

- The build stage and the test job start with the same lines, before the module block: drop `$VIRTUAL_ENV/bin` from `PATH`, then `unset VIRTUAL_ENV CONDA_PREFIX`. One helper in `cli/stages.py`, used by `cmake_stage` (so CECE, CATChem and `kokkos-smoke` all get it) and by the test job template.
- The harness's own `uv run --no-sync …` lines later in the same scripts need neither variable: uv finds the project's venv from the working directory (`cd <harness>` precedes each of them).
- `CONDA_PREFIX` is unset as well because AXIS prefers it, and a conda base environment active in the user's shell would otherwise take the venv's place.
- Not chosen: a configure gate that the log lacks the AXIS line. That would test one library's message; the rendered lines are what the harness owns, and the C7 log is the check.

Verification on C7: the configure log no longer has the AXIS "Active Virtual Environment" (or "Active Conda environment") line, and the dependency lines are unchanged.
