# Refined design (2026-11-23)

## 1. What has to stay in bash, and what doesn't

Two steps can only be done by a shell before the harness starts:

- `module reset`: `module` is a shell function that changes the calling shell's environment. A Python process cannot run it on itself, and the `uv` and `git` that follow must see the reset environment.
- `git pull`: it must happen before the harness code that runs is loaded. Pulling from inside `ufs-chem-assay` would run the old checkout's code against the new one.

Everything else the scripts do is ordinary harness work, and today it is done in bash against the harness from outside: `run` then `watch` with the exit statuses combined, copying a root's files, `report` called through `uv run` inside a subshell, a `record-benchmarks` loop over discovered tests roots. In Python it gets what the rest of the harness has and the scripts don't:

- one configuration system: flags over `ASSAY_*` environment over `.env` over defaults (`src/settings.py`, pydantic-settings), instead of `ops/env.sh` beside `.env`;
- pydantic fields with descriptions, so a setting's name is checked and documented, and an ops value cannot collide with a harness setting (it is one);
- the harness logger and its `[command]` tags, instead of `echo`;
- plain pytest under the 100% coverage rule, instead of bash run against stubbed `uv` and `git`;
- no bash 3.2 constraints for the laptop.

So `ops/` keeps one bootstrap of about ten lines (§5), and the rest moves into `ufs-chem-assay` (§2–§4).

## 2. Settings: the machine's paths in `.env`

`.env` at the harness checkout's root is already the per-machine, gitignored file ("Per-machine configuration for ufs-chem-assay"), read by `Settings` from the current directory (`CONVENTIONS.env_file`). Every command below runs from the checkout (the bootstrap `cd`s there; on the laptop you run `uv run` in it), so it reads that file. Three new `Settings` fields, each `Path | None = Field(None, description=...)`, with `~` expanded by a validator (dotenv does not expand it):

| Field | Variable | Used by | Meaning |
|---|---|---|---|
| `root_dir` | `ASSAY_ROOT_DIR` | `run`, `watch`, `report`, `transfer` | The run root when `--root-dir` is absent. A fresh root per test is one `.env` line (or one `export`). |
| `run_config_file` | `ASSAY_RUN_CONFIG_FILE` | `run` | `--config-file` when the flag is absent; relative to the harness checkout. The flag stops being required; with neither, `run` errors naming both. |
| `transfer_dir` | `ASSAY_TRANSFER_DIR` | `transfer`, `record-benchmarks --transfer` | The directory transfers go in: on C7 where `transfer` writes (inside the transfer git repo), on the laptop where the synced copies are read. One name for the same directory on both machines. |

Precedence of the run root: `--root-dir` > `ASSAY_ROOT_DIR` > the run config file's `root_dir` > the harness checkout's parent (today's derivation). `.env` is per machine and the run config is committed, so the machine wins over the file, as a flag does; `run` logs which source gave the root. `watch` and `report` have no config file: `--root-dir` > `ASSAY_ROOT_DIR` > the checkout's parent.

`ASSAY_ROOT_DIR` is the run root; an application's `<PREFIX>_ROOT_DIR` (`CECE_ROOT_DIR`) is that application's checkout. The names follow `--root-dir` and the run config's `root_dir`; the field description says which is which.

The pytest sessions that stage scripts run also read this `.env` (they `cd` to the checkout). The new fields are unused there and harmless.

C7's `.env` (the laptop's has only `assay_transfer_dir`, pointing at the Dropbox copy):

```bash

assay_run_config_file=config/gaea-c7.yaml
assay_transfer_dir=~/l/c7-epic-proj-shared/git/benkozi-work/transfer
```

`uv`'s own directories (`UV_CACHE_DIR`, `UV_PYTHON_INSTALL_DIR`) cannot come from `.env`: uv needs them before the harness starts. They go in uv's per-user configuration on C7, `~/.config/uv/uv.toml`, read by every `uv` call (the bootstrap, `transfer`, an interactive `uv run`), with `cache-dir` and `python-install-dir` set to today's `env.sh` values (§8 Q3). The stage scripts' uv cache is the run config's `uv.cache_dir` and is unchanged.

## 3. `run --watch` and the run transcript

`run --watch`: after the stages, `run` watches the same root in-process, as `assay-run.sh` does today:

- it watches whatever the stages returned: a failed build still leaves the other builds' test jobs submitted, and `watch` evaluates and reports them;
- it is skipped under `--dry-run`, when no selected stage leaves anything to wait for (no `test`, `harness` or `resume`), and when the stages wrote no effective config;
- the exit status is the stages' when they failed, else watch's; the last line says both: `run: stages exit N, watch exit M` (or `watch skipped: <why>`).

`watch`'s handler body is factored into one function taking the root and watch's options, called by `watch` and by `run --watch` with watch's defaults. No watch options on `run` (YAGNI: `watch` alone still takes them).

The transcript: `run` adds a log file handler, `<root>/logs/run-<YYYYmmdd-HHMMSS>.log`, as soon as the root is known (the directory created first), with the same format and `[command]` tag as the terminal. Everything the harness logs from then on, watch's lines included, lands there; the stage scripts' own output stays in their stage logs, as now. The facts `assay-run.sh` echoed go to the log at run start instead: hostname, the harness's version and commit, `LD_LIBRARY_PATH` and `PYTHONPATH` as `run` sees them (after the bootstrap's `module reset`), the root and its source. That replaces `tee`, and the bootstrap's own output (`module reset`, `git pull`) stays on the terminal only.

## 4. `transfer` and `record-benchmarks --transfer`

### 4.1 `ufs-chem-assay transfer [--root-dir DIR] [--transfer-dir DIR] [--name NAME] [--dry-run]`

Today's `assay-transfer.sh`, as a command:

- name: `--name`, default `assay-<YYYYmmdd-HHMM>`; destination `<transfer_dir>/<name>`. An existing destination is refused (today `mkdir -p` merges into it silently) (§8 Q4).
- copies, the same set as today: `logs/`; `scripts/*.yaml`, `*.sh`, `*.sbatch`; every `<toolchain>/tests/`; each `<toolchain>/<checkout>/build*/CMakeCache.txt` to `cmake/<same path>`. The globs are one module-level tuple, so the copied set is named once.
- `report.txt`: the report rendered in-process on the live root (the `report` command's own functions), written to the destination; report's issues do not fail the transfer (exit 1 from report is still the report).
- git, in the transfer repo (`cwd=<transfer_dir>`): `git pull`, `git add -f <name>`, `git commit -m <name>`, `git push`, each logged before it runs; the first that fails stops the transfer with its command and exit status, and the copy stays in place. This is your command committing to your transfer repo, as the bash script does today; the harness repository is never touched.
- the last line: `transfer: pushed <destination> (<size>)`.
- `--dry-run` logs what would be copied and the git commands, and writes nothing.

### 4.2 `ufs-chem-assay record-benchmarks --transfer DIR|NAME [--dry-run]`

A third member of record-benchmarks' mutually exclusive `--output-root`/`--tests-root` group, replacing `assay-benchmarks.sh`:

- a bare name resolves under `transfer_dir` (`--transfer assay-20261123-1405`); a path is used as given;
- a directory without `scripts/run-config.yaml` is not a transfer directory: refused, exit 1;
- the tests roots are `<transfer>/<toolchain>/tests/<application>[/<build>]/` holding both `tests.yaml` and `benchmarks.csv`, in sorted order, each recorded exactly as `--tests-root` records one (`_record_tests`), so runs already recorded are skipped;
- one root failing does not stop the others; the exit is 1 if any failed;
- no tests root: logged, exit 0;
- no `git diff`: each target already logs `<file>: N appended, M already recorded; review the diff and commit it`.

```bash
#!/usr/bin/env bash
# ops/assay-run.sh: what only a shell can do before the harness (module reset,
# git pull), then `ufs-chem-assay run --watch`. Paths come from .env.
#
#   ops/assay-run.sh [<run arguments>]   none: the daily selection below
set -euo pipefail
cd "$(dirname "${BASH_SOURCE[0]}")/.."
case ":$PATH:" in *":$HOME/.local/bin:"*) ;; *) export PATH="$HOME/.local/bin:$PATH" ;; esac  # uv

if command -v module > /dev/null 2>&1; then module reset; else echo "assay-run: no module command; no module reset"; fi
set -u
git pull
[ $# -gt 0 ] || set -- --application all --stage source --stage build --stage test
exec uv run ufs-chem-assay run --watch "$@"
```

### Q1, expanded: where the daily selection lives

`run` needs an application selection (`--application`, required today) and takes an optional stage selection (`--stage`, default: every stage but `resume`). The daily one on C7 is `--application all --stage source --stage build --stage test`. The question is where that default lives, which decides what happens when you add one argument, e.g. `ops/assay-run.sh --build musica`.

- A. The bootstrap's default arguments (§5's `[ $# -gt 0 ] || set -- --application all --stage source ...`). With no arguments you get the daily run. With any argument the default is dropped whole, so `ops/assay-run.sh --build musica` is `run --build musica` with no `--application`, which `run` rejects; you must write the whole selection (`--application catchem --stage build --stage test --build musica`). Simple, but the all-or-nothing replacement is the gotcha `env.sh`'s per-variable defaults avoided.
- B. Settings, per flag: `run_applications` (`ASSAY_RUN_APPLICATIONS`) and `run_stages` (`ASSAY_RUN_STAGES`), space-separated lists in `.env` (decoded like `suite_config_search_path`, `NoDecode`), each the default of its own flag: `--application` given replaces only the applications, `--stage` given replaces only the stages, and `--application` stops being required (neither the flag nor the setting: `run` errors naming both). `ops/assay-run.sh --build musica` then runs the `.env` applications and stages for the musica build only. Per config rather than per machine or person, and committed, so every C7 user gets the same daily run and changing yours is a commit. With Q2's "settings always win", B would still override it.

## Round 3 (2026-11-23): one argument, a YAML path

Asked: Q1 gets complicated; the best solution is that the ops entry point accepts exactly one argument, the path of a YAML file that configures the run. What are the implications?

Read here as: `ops/assay-run.sh <run config>` takes that one argument and nothing else, and the file says everything about the run (root, selection, where its transfer goes). The harness CLI keeps its flags, which stay overrides on the file, for ad hoc runs outside the bootstrap.

### What already exists

Most of this is in the run config already:

- `RunConfig` has `selected_toolchains`, `selected_applications`, `selected_stages` and `selected_builds` (`src/cli/run_config/config.py`). `run` writes them into the effective config (`<root>/scripts/run-config.yaml`), whose comment in `run.py` says it "re-runs the same run with no override list".
- `selected_applications`, `selected_toolchains` and `selected_builds` are already read back when their flag is absent (`src/cli/selectors.py`): with no `--application`, the config's `selected_applications`, else every application.
- `root_dir` is already a run config key (precedence: `--root-dir`, the file, the checkout's parent).

What is missing: `--application` is `required=True`, so the file's selection is never reached by `run`; `selected_stages(args.stage)` ignores the config's `selected_stages`; the four fields are described as "not a key to write by hand"; and a per-person file has no way to reuse `config/gaea-c7.yaml` without copying it.

### Implications

1. The `.env` settings go away. §2's `root_dir`, `run_config_file` and `transfer_dir` settings, and round 2's `run_applications`/`run_stages`, are all dropped: the YAML holds them. Q2 (settings over the file) is moot. `.env` is unchanged by this design. The multi-word list parsing and the `ASSAY_APPLICATION`/`ASSAY_RUN_APPLICATIONS` near-collision go with them.

2. The selection keys become keys you write. `selected_*` keep their names; their descriptions change to "the X this run selects (the flag wins); `run` records what it ran here". `run` changes: `--application` stops being required (the file's `selected_applications`, else every application, as the selector already does for a recorded config), and `--stage` falls back to the file's `selected_stages`, else today's default (every stage but `resume`). Omitting `selected_applications` means every application, so the daily file needs no `all`.

3. A per-person file needs `extends:`. `config/gaea-c7.yaml` is shared and committed and changes often (the OMP env, modules); a personal copy of it would silently miss those changes. So a run config may name another one: `extends: config/gaea-c7.yaml`. The loader reads the named file first and deep-merges this one over it: mappings merge key by key, scalars and lists replace. A relative `extends` resolves against the harness checkout (where `config/` is). Chains are allowed (a musica-only file extending the daily one), with a cycle an error naming the files. The merged result is what validates, and the effective config records the merged result with no `extends`, so it still reruns alone. (`extends`, not `base`: "base section" already means something in the toolchain overlay.)

4. The transfer destination is a run config key. `transfer_dir: Path | None` at the top level, with a description and `~` expanded. `transfer` reads the root and the destination from the same file: `ufs-chem-assay transfer --config-file <run config> [--name NAME] [--dry-run]`. Without `transfer_dir`, `transfer` errors naming the key.

5. The bootstrap takes exactly one argument:

   ```bash
   [ $# -eq 1 ] || { echo "usage: ops/assay-run.sh <run config yaml>" >&2; exit 2; }
   config="$(cd "$(dirname "$1")" && pwd)/$(basename "$1")"   # before the cd below
   cd "$(dirname "${BASH_SOURCE[0]}")/.."
   # PATH, module reset, git pull as in §5
   ```

## Round 4 (2026-11-23): uv's directories only for the assay

Asked, about the runbook's two `~/.bashrc` exports: "these uv directories should only be for assay related activities. not a common uv across other uv-enabled apps". Right: a profile export (or `~/.config/uv/uv.toml`) points every uv project of that user at the assay's cache and Pythons. Withdrawn from the runbook and `ops/README.md` on implementation.

### What needs the directories

- uv itself, before the harness starts: the bootstrap's `uv run`, and any `uv run ufs-chem-assay ...` you type (`transfer`, a dry run). Without them uv uses `$HOME` (`~/.cache/uv`, `~/.local/share/uv/python`), too small on C7, and downloads a Python there.
- Not the stage scripts: they call `uv run --no-sync` from the checkout, so they use the existing `.venv` and its interpreter and download nothing; their `UV_CACHE_DIR` is the run config's `uv.cache_dir` (default `<root>/uv-cache`), already per root. The test job inherits the same.

So the scope is "every uv call that runs the harness", which is exactly the calls made from the harness checkout.

### Design: `ops/assay`, the one way to run the harness

A small wrapper beside the bootstrap:

```bash
#!/usr/bin/env bash
# ops/assay <ufs-chem-assay arguments>: the harness, with uv's cache and
# Pythons in this checkout (.uv/, gitignored) and nowhere else.
set -euo pipefail
checkout="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
export UV_CACHE_DIR="$checkout/.uv/cache"
export UV_PYTHON_INSTALL_DIR="$checkout/.uv/python"
case ":$PATH:" in *":$HOME/.local/bin:"*) ;; *) export PATH="$HOME/.local/bin:$PATH" ;; esac  # uv
exec uv run --project "$checkout" ufs-chem-assay "$@"
```

- Scoped by construction: the variables exist only in that process and its children (the stages, the test job), never in your shell or another project's uv.
- No per-machine value: the directories derive from the checkout, which on C7 is on GPFS and per person (round 2's Q3), so the "file 2" of the runbook disappears; `c7.local.yaml` is the only file you create.
- Set unconditionally, not as defaults: an exported global `UV_CACHE_DIR` meant for other projects must not leak in, which is the point of this round.
- `--project "$checkout"`: it works from any directory, so `ops/assay transfer --config-file config/c7.local.yaml` and a call from elsewhere behave the same.
- The bootstrap ends with `exec "$checkout/ops/assay" run --watch --config-file "$config"` (after its own `git pull`), so its uv is scoped the same way; its PATH line moves into `ops/assay`.
- `.gitignore`: `.uv/`. ruff, pytest (`testpaths`), mypy (`src`) and pre-commit (tracked files) never look there.
- The laptop can use it too (the same isolation), or keep plain `uv run`; nothing requires it there.

The daily loop becomes:

```bash
ops/assay-run.sh config/c7.local.yaml
ops/assay transfer --config-file config/c7.local.yaml
```

## Round 5 (2026-11-23): the transfer as one zip

Asked: "for "transfer" the logs should really be zipped to save bandwith. zip to created payloaded prior to committing". Implemented directly (a contained change to §4):

- `transfer` writes one payload, `<transfer_dir>/<name>.zip` (deflate), its members under `<name>/`, so unzipping gives the directory the earlier transfers were; only the zip is added and committed (`git add -f <name>.zip`, `git commit -m <name>`). Nothing is staged as a copy: the files go from the root straight into the archive, and the report is rendered into a scratch file first.
- The archive is written as `.<name>.zip.partial` beside its name and renamed when complete; a write that fails (a full disk) removes the partial, logs `transfer: cannot write <zip>: <why>`, exits 1 and pushes nothing.
- An existing `<name>.zip`, or an existing `<name>/` directory (an unzipped payload, or a transfer from before this change), is refused: unzipping would collide.
- The last line gives both sizes: `transfer: pushed <zip> (<zipped>, <unzipped> unzipped)`. `--dry-run` lists each file as `<name>/<path>` and the zip it would write.
- `record-benchmarks --transfer` takes the zip (read in place: unpacked into a scratch directory removed afterwards; the log names `<zip>:<name>/<tests root>`) or the unzipped directory. A zip with more than one top directory, or a file that is not a zip, is refused.
- Tests: `test_transfer.py` (12: the payload's members and compression, one file in the transfer directory, both refusals, the failed write) and `test_record_transfer.py` (9: the zip read in place and left alone, the two refusals).
