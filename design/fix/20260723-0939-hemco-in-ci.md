# Fix: repair the "Run HEMCO parity examples" CI step

## Goal

CECE's `ci.yml` step **"Run HEMCO parity examples"** breaks because the
examples consolidation (`design/feat/20260722-1553-unify-examples-download.md`)
deleted everything it depends on. Rewrite the step around the new
`examples/run-example.py` entrypoint, running a small curated example set
suitable for CI. Local validation goes as far as a container approximation
can; final proof is user-triggered CI runs with a report-back loop (per
the requirements — we cannot run GitHub Actions locally).

## Pre-design audit

The failing step (ci.yml lines 83–102), line by line, against current
reality:

1. `cmake --build build --target cece_nuopc_app` — defensive rebuild of
   the **NUOPC app** (the step predates the standalone driver being the
   examples' engine). Still buildable (CI configures `-DENABLE_ESMF=ON`),
   but the new examples implementation runs the **standalone driver**.
2. `./scripts/setup_hemco_examples.sh` — **deleted** (generator of the
   superseded layout).
3. `./scripts/data_download/download_ex1.sh` — **deleted**.
4. The inline python mock of `data/hourly.nc` with `HOURLY_SCALFACT` —
   built for the *old-schema* ex1 that used `hourly_scalfact`; the
   current ex1 has no such input. Obsolete.
5. `cp examples/cece_config_ex1.yaml cece_config.yaml` + run
   `cece_nuopc_app` — the config moved to `examples/config/`, and
   today's ex1 is the heavyweight HTAP+CAMS example (~470 MB of sector
   data plus CAMS inputs that 404 publicly) — **unsuitable for CI**
   regardless of pathing.

Supporting facts (verified):

- CI's build step runs plain `make -j` — **every target builds,
  including `cece_standalone_driver`**, and with no
  `RUNTIME_OUTPUT_DIRECTORY` override it lands at
  `build/cece_standalone_driver`, exactly the entrypoint's default
  (`CECE_EXAMPLES_DRIVER_PATH` exists as the escape hatch if CI layout
  ever differs).
- The step's "parity" name is historic; what it actually did was run one
  example end-to-end. The honest replacement does the same thing with
  the new machinery.
- `tests/test_scripts.py` (mapping sanity + S3 HEAD checks) already runs
  in CI via the ctest fixtures — the workflow step complements it with a
  real execution.

## Design

Replace the step body (and rename it to what it does — **"Run CECE
examples"**):

```yaml
- name: Run CECE examples
  run: |
    source /opt/spack-environment/activate.sh

    # Defensive: ensure the standalone driver exists even when build
    # artifacts are restored from cache.
    cmake --build build --target cece_standalone_driver -j$(nproc)

    export LD_LIBRARY_PATH="$(pwd)/build/lib:$(pwd)/build${LD_LIBRARY_PATH:+:${LD_LIBRARY_PATH}}"
    python3 examples/run-example.py --example ex3,ex6
```

Decisions:

- **Example set: `ex3,ex6`** (~25 MB of downloads total). ex3 is the
  minimal smoke (MACCity, ~1 MB, 2×2 grid, one step) — the moral
  equivalent of what the old step ran; ex6 adds a second, still-small
  example (EDGAR POW 5 MB + CEDS ALK4 17 MB, 4 steps) covering
  multi-stream ingest. ex1/ex7 are excluded (heavyweight + CAMS
  expected-fail); ex4 excluded (450 MB); ex2/ex5 optional later.
- **One entrypoint invocation does everything**: download (cache-aware,
  fails loudly per file) and execution, with logging and per-example
  PASS/FAIL summary — the mock-file and config-copy hacks disappear
  entirely.
- The NUOPC-app rebuild is dropped from this step (nothing here uses
  it; the main build step still compiles everything, and NUOPC coverage
  belongs to ctest).
- **Data cache (confirmed by the user)**: an `actions/cache` step before
  the examples step:

  ```yaml
  - name: Cache example data
    uses: actions/cache@v4
    with:
      path: data
      key: examples-data-${{ hashFiles('examples/common.py') }}
  ```

  Keyed on the mapping's source file, so the ~25 MB re-downloads only
  when `common.py` changes. **Deliberately no `restore-keys` fallback**:
  a stale cache entry could carry an old file under an unchanged
  filename, and the exists-and-non-empty cache guard would then skip the
  fresh fetch — a full re-download on mapping changes is the cheap,
  correct trade. (The cache also covers whatever the per-file guard
  needs: partially-failed runs re-fetch only what's missing.)

## Verification plan

Local testing of a GitHub workflow is unreasonable (no Actions runtime);
per the requirements the loop is:

1. **Local approximation** (does not need CI): run the step's core
   command inside the dev container —
   `docker run … cece/cece-dev python3 examples/run-example.py
   --example ex3,ex6` — which this repo's `--run-examples` gate already
   exercises per example; plus a YAML-lint sanity pass of the edited
   workflow. This validates everything except the spack environment and
   the CI cmake layout.
2. **User-triggered CI**: the user pushes/dispatches the workflow; I
   read back the run results (user pastes logs or shares the failure
   text) and iterate until the step is green. Each iteration's findings
   land in this doc's implementation notes.

Standing checks: the runner is untouched by this fix (no runner tests to
update); CECE-side change is one workflow file. Pre-commit hooks in the
runner repo remain green (design-doc-only changes there).

## Ripples

- CECE: `.github/workflows/ci.yml` only. No src, no examples, no docs
  changes (the examples README already documents the entrypoint; CECE
  docs stay runner-free per the standing rule).
- Runner: none (this doc + implementation notes are the record).
- The step rename ("Run HEMCO parity examples" → "Run CECE examples")
  is honest labeling; if anything external keys on the old step name
  (branch protection required-checks use *job* names, not step names,
  so this is expected to be safe — verified against the workflow's
  single-job structure).

## Acceptance criteria

- The rewritten step references only surviving paths (`examples/…`), no
  deleted scripts, no mock-file hack, no `cece_config.yaml` copy.
- The `data/` cache step is present, keyed on
  `hashFiles('examples/common.py')` with no restore-keys fallback; a
  warm-cache CI run performs no example-data downloads.
- It builds/uses `cece_standalone_driver` and runs `ex3,ex6` via
  `run-example.py`, exiting non-zero on any failure (the entrypoint
  already guarantees this).
- Local approximation passes in the dev container.
- **CI is green on a user-triggered run** — or every remaining failure
  is documented in the implementation notes with its fix applied and
  re-verified in the next run.

## Implementation notes

- Workflow edited as designed: the "Run HEMCO parity examples" step is
  replaced by "Cache example data" (`actions/cache@v4`, `path: data`,
  key `examples-data-${{ hashFiles('examples/common.py') }}`, no
  restore-keys) + "Run CECE examples" (defensive
  `cece_standalone_driver` build, `LD_LIBRARY_PATH` export preserved,
  `python3 examples/run-example.py --example ex3,ex6`). No stale
  references remain anywhere in the workflow (grep-verified: no
  `setup_hemco`, `data_download`, `cece_nuopc_app`, or `hourly.nc`).
- Local validation: workflow YAML parses and lints clean; the step's
  core command runs green in the dev container — ex3 PASS, ex6 PASS,
  exit 0 (spack env and CI cmake layout remain CI-only unknowns, as
  designed).
- **Awaiting the user-triggered CI run** (verification plan step 2);
  findings from each round land here.
