# Fix: `release-preview / release-verify` fails with 403 on PR #26 — the App token is refused when creating its probe ref; probe the PR's head commit and log the token's shape

Written 2026-10-16 during CI monitoring of https://github.com/benkozi/ufs-chem-assay/pull/26. 1. **Runs on PR #26 today** (`ci.yaml` → `semantic-release.yml` `release-verify`): 13:58 UTC (commit `b0b8e14`, merge commit `9008041e`) — Validate secrets, Generate token, Verify: all success, log `Git ref creation succeeded`, `Ruleset 'base' includes App (ufs-chem-assay-psr) in bypass list for develop`. 14:19 UTC (`e63d642`, merge `197dda9f`) attempt 1 and its 14:30 re-run (attempt 2): Verify fails with the 403 above. 15:31 UTC (`699aae3`, an empty "ci: trigger" commit, merge `2915a5f1`): same 403. Actor on all three: the user (`benkozi`), event `pull_request`. Dependabot's own push (23:12 the day before) skipped the token and verify steps by design (no secrets for the bot actor).
2. **Other runs of the same check**: `verify-secrets.yml` (daily schedule, `check-permissions` against develop's head) passed at 10:12 UTC today and the two days before. No develop push since 23:34 UTC yesterday, so no post-14:10 data point for a non-PR context exists yet.
3. **Ruled out**: the App installation (screenshot from the user: Metadata read, Contents read and write, only `benkozi/ufs-chem-assay`, untouched since installation); the token action (`actions/create-github-app-token@v3` resolved to the same commit `64ab729a`, v3.3.0 of 2026-10-12, in the passing and failing runs); the workflow files (`ci.yaml`, `semantic-release.yml`, the script: unchanged on the branch — the only workflow edit on the branch is `integration.yaml`); the SHA's existence (both merge commits exist via `GET /git/commits`; the 15:31 run used a freshly computed merge commit and still failed); rulesets (one, `base`, branch-targeted, bypass actor Integration 5215033 = the App, updated 2026-10-06; no legacy tag-protection rules); GitHub incidents (none open; the last resolved one is 2026-10-15 18:56 UTC and unrelated); the script's handling of the token (it passes `GH_TOKEN` straight to `gh api`, never inspects it).
4. **What the failing call is**: `gh api repos/benkozi/ufs-chem-assay/git/refs -X POST -f ref=refs/tags/ci-perm-check-<run_id> -f sha=<github.sha>` with `GH_TOKEN` = the App installation token. The read `GET /installation/repositories` with the same token succeeds in the same step.
5. **The token-format rollout** (changelog of 2026-05-15, still rolling out): installation tokens move from opaque strings (no dots) to JWT-format `ghs_` tokens (~520 characters, two dots), per app, server-side, with a temporary per-request header `X-GitHub-Stateless-S2S-Token: enabled|disabled` on `POST /app/installations/:id/access_tokens` to force either format. `actions/create-github-app-token@v3` has no input for request headers (its `action.yml` inputs: client-id, app-id, private-key, owner, repositories, enterprise, skip-token-revoke, github-api-url, permission-*). No issue in that action's tracker and no web report ties this 403 to the new format.
6. **A manual probe with a personal token** (tag the merge commit, delete it) would discriminate (a) from (b) directly; the assistant's attempt was blocked by its permission policy, and the commands were handed to the user. A manual `verify-secrets` dispatch would discriminate too; not run yet.
7. **Impact**: `release-verify` gates `release-psr`. Until it passes, a merge of PR #26 into develop skips the rc release; nothing else is blocked (the preview job is informational on PRs).

## Design

### 0. Decisions

1. **Probe a real commit on pull requests.** `SHA: ${{ github.event.pull_request.head.sha || github.sha }}` in the Verify step. The merge commit is synthetic (it exists only under `refs/pull/<n>/merge`), and nothing about the check needs it: the probe proves that the token can create and delete a ref, which any commit demonstrates. On pushes and dispatches `github.event.pull_request` is empty and `github.sha` applies as before.
2. **Log the token's shape, never the token.** A step after "Generate GitHub App token": length, number of dots, and the 4-character prefix (`ghs_`), from an `env`-passed value (the expression never appears in `run:`). A stateless token shows ~520 characters and 2 dots; a classic one ~40 and 0. Kept permanently — one log line, and the next format change is visible at once.
3. **No override header yet.** Minting the token by hand (JWT signed with the App key via `openssl`, then the access-tokens call with `X-GitHub-Stateless-S2S-Token: disabled`) is the workaround for (b). It is specified under Future work and written only if the next run shows (b): a head-commit probe still refused, with a stateless-shaped token.
4. **No change to the script** (`verify_semantic_release_credentials.py` reads `SHA` from the environment already) and none to `verify-secrets.yml` (dispatch and schedule run on a branch head).

### 1. `semantic-release.yml` — `release-verify`

```yaml
      - name: Generate GitHub App token
        ...unchanged...
      # Shape only, never the token: the stateless-token rollout (GitHub
      # changelog 2026-05-15) changes ghs_ tokens from ~40 opaque characters
      # to ~520-character JWTs with two dots.
      - name: Describe the App token (length, dots, prefix)
        if: steps.check.outputs.skip_verification != 'true'
        env:
          APP_TOKEN: ${{ steps.app-token.outputs.token }}
        run: |
          dots=$(printf '%s' "$APP_TOKEN" | tr -cd '.' | wc -c | tr -d ' ')
          echo "App token: ${#APP_TOKEN} characters, $dots dot(s), prefix ${APP_TOKEN:0:4}"
      - name: Verify repository write and ruleset bypass
        ...
          # The probe ref needs a commit the token can point a ref at; on
          # pull_request events github.sha is GitHub's synthetic test-merge
          # commit (refs/pull/<n>/merge only), so probe the PR's head commit
          # instead (2026-10-16: the merge-commit probe began failing with
          # 403 "Resource not accessible by integration"; see
          # design/fix/20261016-0936-release-verify-403/).
          SHA: ${{ github.event.pull_request.head.sha || github.sha }}
```

## Implementation notes (2026-10-16)

**Outcome: fixed. The first run with the change (commit `778bb81`, ci run 38926633946) is green end to end, and its log answers the open question.**

- "Describe the App token": `App token: 390 characters, 2 dot(s), prefix ghs_` — a **stateless JWT-format token**: the rollout from the 2026-05-15 changelog has reached this App.
- "Verify repository write and ruleset bypass" with `SHA: 778bb81…` (the PR's head commit): `Git ref creation succeeded`, `Ruleset 'base' includes App (ufs-chem-assay-psr) in bypass list for develop`. `release-preview / release-psr` ran and succeeded after it.
- Reading against the §2 table: a stateless token **and** a head-commit probe that succeeds — the row the table did not list, and the most informative one. Under the new token format the App can create refs to ordinary commits but not to GitHub's synthetic test-merge commit (`refs/pull/<n>/merge`), which is what the probe pointed at from 13:58 (last pass, presumably still a classic token) to 15:31 (three 403s). Whether the stricter reachability check is a property of stateless tokens or a coincident server-side change cannot be told from here; either way the head-commit probe is the right probe, and nothing else needs to change. Future work 1 (the `disabled` override header) is not needed.
- Linters: pre-commit all hooks, actionlint in CI's container; both clean before the push.
